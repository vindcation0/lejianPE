## 四、本次关键决策：关闭服务端冲突检查

### 决策内容

把 `config.json` 的 `check_conflict` 从 `true` 改为 `false`，重启程序。

### 为什么

`checkConflict` 是报名前的一次服务端只读校验。
程序原逻辑：**检查接口失败 → 判定"结果未知" → 安全阻断，不提交**。

在 14:09 那个时间点，这导致了一个死循环：

```
列表恢复了 → 找到候选 → 调 checkConflict → 接口 500
          → 安全阻断 → 不提交 → 下一轮
```

而**本地冲突校验其实已经足够**：

- 课表占用（含周次）已在本地算好
- 已报名活动的时段也已并入占用表
- 每日/每周上限也在本地维护

服务端检查只是**冗余的第二道保险**。当它本身成为故障点时，
保留它等于把唯一的通路也堵死。

### 代价与风险

| 项 | 评估 |
|---|---|
| 失去的能力 | 服务端知道的、我们本地不知道的冲突（如有） |
| 实际风险 | 低。前两次实战的冲突都来自课表，本地能覆盖 |
| 若发生冲突 | 服务端大概率会在 `signUp` 时拒绝，仍有一道兜底 |

### 建议

**日常保持 `check_conflict: false`**。
开抢窗口内它的失败率极高，而收益有限。

## 五、本次最大亮点：UNKNOWN 安全屏障

这是本次真正救命的机制。完整链路：

```
提交 → 超时/500（结果未知）
    ↓
立即冻结候选队列（不再打下一个）
    ↓
调用服务端只读接口复核真实状态
    ↓
确认未报名 → 解除冻结，继续
    确认已报名 → 计入成功，继续
    复核也失败 → 继续保持冻结，稍后重试
```

**对照 10-25 的教训**：那次没有这个屏障，
程序把"超时"当成"失败"继续猛打，最终抢了 3 节。

本次出现了 2 次 UNKNOWN、1 次复核失败保持冻结，
**没有产生任何超额**。

> 这是"宁可少发、不可重复"原则的完整落地。

## 六、发现的两个问题

### 6.1 自动报告的故障统计是错的

程序生成的 `logs/reports/2026-11-08-report.md` 第五节写着：

```
请求失败总计：0 次
累计故障中断：0.0 秒
熔断触发次数：0 次
```

**但实际是 18 次列表失败、多次冻结**。

原因推测：报告生成器统计的是某个未被填充的计数器，
而不是读取 `events-*.jsonl`。

**建议**：让报告直接聚合事件日志，而不是依赖内存计数器。

### 6.2 提交次数口径偏差

报告写"提交尝试：8 次"，但实际提交调用是 **6 次**：

| 真实提交 | 结果 |
|---|---|
| 14:11:06 程启航 | UNKNOWN |
| 14:11:09 程启航 | UNKNOWN |
| 14:11:38 程启航 | 失败（已满） |
| 14:11:38 王彤帆 | 成功 |
| 14:11:45 廖华 | RETRYABLE |
| 14:11:45 周天一 | 成功 |

多出的 2 条是"复核确认未报名"的**屏障记录**，被混入提交列表。

**建议**：把「提交记录」与「复核记录」分开计数。
