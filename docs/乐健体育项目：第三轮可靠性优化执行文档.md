# 三、任务一：UNKNOWN 安全屏障

**优先级：最高，必须首先完成。**

## 3.1 当前问题

目前程序在报名提交后，如果发生：

- 请求超时。
- HTTP 503。
- HTTP 504。
- 连接中断。
- 无法解析服务端响应。
- 其他无法确定报名结果的异常。

会将该次报名标记为 UNKNOWN。

但是当前流程仍然可能继续处理下一个候选活动。

这会产生以下风险：

```
提交候选 A
    ↓
请求超时
    ↓
A 实际可能已经报名成功
    ↓
本地标记 UNKNOWN
    ↓
继续提交候选 B
    ↓
B 也可能报名成功
    ↓
继续提交候选 C
```

程序无法确定 A、B 是否已经占用报名名额。

因此必须建立全局安全屏障。

## 3.2 核心规则

**任何时候，只允许存在一个尚未解决的报名提交结果。**

一旦某次报名进入 UNKNOWN：

1. 立即暂停后续所有报名提交。
2. 不允许继续下一个候选。
3. 不允许因为超时而重新提交同一个活动。
4. 优先进行服务端只读状态复核。
5. 只有确认前一个请求的最终结果后，才能决定是否恢复候选队列。

这是本轮最重要的业务规则。

## 3.3 推荐状态流转

```
READY
  |
  v
SUBMITTING
  |
  +------------------+
  |                  |
  v                  v
SUCCESS            FAILED
  |                  |
  v                  v
更新名额          允许下一候选
  |
  v
检查是否达到上限


SUBMITTING
  |
  v
UNKNOWN
  |
  v
冻结整个报名队列
  |
  v
RECONCILING
  |
  +----------------------+
  |                      |
  v                      v
确认报名成功           确认未报名
  |                      |
  v                      v
更新实际名额           释放临时占用
  |                      |
  +----------+-----------+
             |
             v
       重新计算剩余名额
             |
             v
       决定是否恢复队列
```

如果复核仍然无法确定结果：

```
RECONCILING
    |
    v
UNRESOLVED
    |
    v
保持冻结
    |
    v
等待后续只读复核
```

不得把 UNRESOLVED 自动解释为 FAILED。

## 3.4 提交前持久化

必须确保报名请求发出之前，已经将状态持久化为：

```
SUBMITTING
```

执行顺序：

```
1. 检查报名限制
2. 检查是否存在其他未决请求
3. 创建报名请求记录
4. 持久化 SUBMITTING
5. 确认持久化成功
6. 发送报名请求
7. 根据响应更新状态
```

禁止先发送请求，再记录 SUBMITTING。

否则程序可能在请求已经被服务端处理后、但本地尚未记录状态时意外退出。

## 3.5 UNKNOWN 后的复核规则

必须优先使用现有：

- `Client.activities()`
- `verify_registration()`
- `ReconciliationManager`
- 已有服务端报名查询逻辑

复核只允许使用只读接口。

不能为了确认报名结果而再次调用报名接口。

### 情况 A：明确确认成功

例如：

服务端活动列表中出现对应 activityId，并且数据完整、状态有效。

处理：

1. 更新本地状态为最终确认成功。
2. 记录实际报名日期。
3. 更新每日报名数量。
4. 更新每周报名数量。
5. 重新计算剩余名额。
6. 如果达到上限，停止后续报名。
7. 如果仍有名额，才允许恢复候选队列。

### 情况 B：明确确认未成功

只有满足以下条件才能认定未报名：

- 服务端数据完整。
- 查询结果有效。
- 查询接口成功。
- 查询范围覆盖目标活动。
- 不存在明显的数据延迟或其他未解决因素。
- 符合项目已经验证的未报名判定规则。

如果不能满足这些条件，不允许直接认定失败。

明确未报名后：

1. 更新本地最终状态。
2. 释放 UNKNOWN 对应的临时名额占用。
3. 重新计算报名限制。
4. 决定是否允许下一个候选。

### 情况 C：无法确认

例如：

- 活动列表获取失败。
- 活动列表不完整。
- 服务端持续返回 500。
- 查询超时。
- 服务端数据存在不一致。

处理：

1. 保持 UNKNOWN。
2. 保持报名队列冻结。
3. 不提交其他候选。
4. 进行有限的只读复核。
5. 达到等待阈值后提示用户人工处理。

**特别注意：活动列表不完整时，绝不能将活动未出现解释为报名失败。**

## 3.6 每日、每周名额保护

UNKNOWN 对应的活动在结果确定前，必须被视为潜在成功报名。

建议维护：

```
effective_daily_count = (
    confirmed_daily_count
    + unresolved_daily_count
)

effective_weekly_count = (
    confirmed_weekly_count
    + unresolved_weekly_count
)
```

具体字段和数据结构以当前项目为准。

注意：

- UNKNOWN 不计为明确成功。
- UNKNOWN 不计为明确失败。
- 但在安全额度计算中必须预留潜在占用。
- 复核确认成功后转为实际占用。
- 复核确认失败后才能释放占用。

在当前设计下，存在未决 UNKNOWN 时整个报名队列已经冻结，因此不应允许其他候选绕过这个保护。

## 3.7 程序重启恢复

这是必须实现的重点。

考虑以下场景：

```
14:02:26 发出报名请求
14:02:27 服务端可能已经处理
14:02:28 本地请求超时
14:02:29 程序崩溃
14:03:00 用户重新启动程序
```

重启后不能重新提交原来的活动。

必须：

1. 读取 SQLite 中持久化的报名状态。
2. 检查是否存在 SUBMITTING。
3. 对上次遗留的 SUBMITTING 视为结果未知。
4. 转换或恢复为 UNKNOWN。
5. 冻结新的报名提交。
6. 先进行服务端只读复核。
7. 确认最终结果后再恢复正常工作。

如果上次状态已经是 UNKNOWN，也必须恢复冻结状态。

不能因为进程重新启动就清除 UNKNOWN。

# 四、任务二：服务端故障熔断机制

**优先级：P0**

## 4.1 当前问题

11 月 1 日真实运行期间，服务器出现大量异常：

- HTTP -1 超时。
- HTTP 500。
- HTTP 503。
- HTTP 504。

虽然已有完整性守卫和部分退避逻辑，但仍然需要一个统一的故障控制机制。

当前目标不是增加请求次数，而是：

**当服务器持续不可用时，主动停止无意义的请求，并在恢复后安全地恢复程序。**

## 4.2 推荐熔断状态

新增或完善：

```
CLOSED
OPEN
HALF_OPEN
```

### CLOSED：正常状态

- 正常进行只读活动列表查询。
- 正常检查 Token。
- 允许按照现有规则运行。
- 记录连续失败次数。

### OPEN：熔断状态

达到连续失败阈值后：

- 暂停活动列表轮询。
- 禁止新的报名提交。
- 暂停依赖不完整数据的业务决策。
- 按冷却时间等待。
- 输出明确的熔断原因。

### HALF_OPEN：半开状态

冷却结束后：

- 只允许进行一次只读健康检查。
- 不允许并发健康检查。
- 不允许发送报名提交。
- 检查数据是否完整。
- 检查认证状态是否有效。

成功后恢复 CLOSED。

失败后重新进入 OPEN。

## 4.3 熔断触发条件

建议对可恢复的网络和服务端异常进行分类：

- 请求超时。
- 连接拒绝。
- DNS 或连接异常。
- HTTP 500。
- HTTP 502。
- HTTP 503。
- HTTP 504。

需要区分：

- 普通业务错误。
- 认证失效。
- 请求参数错误。
- 服务端暂时不可用。
- 未知错误。

不能把所有 HTTP 非 200 响应都简单算作服务器故障。

对于 Token 失效：

1. 使用现有 Token 刷新机制。
2. 刷新失败时暂停业务请求。
3. 不要无限重试。
4. 不要将认证错误误认为活动列表完整。

## 4.4 退避机制

建议采用有上限的指数退避：

```
delay = min(
    base_delay * (2 ** failure_count),
    max_delay
)
```

并增加随机抖动。

具体参数应根据项目当前请求频率和服务器响应情况设置，不要直接照搬固定数值。

如果服务端提供 Retry-After，应优先遵守。

要求：

- 设置最大等待时间。
- 防止请求频率失控。
- 不进行无限重试。
- 记录每次熔断和恢复。
- 不绕过学校接口限流规则。

## 4.5 熔断与 UNKNOWN 的关系

两套机制必须协同。

例如：

```
报名请求超时
    ↓
UNKNOWN
    ↓
冻结报名队列
    ↓
服务器同时进入 OPEN
    ↓
停止所有新的报名提交
    ↓
等待服务器恢复
    ↓
进入 HALF_OPEN
    ↓
只读健康检查
    ↓
确认数据完整
    ↓
复核 UNKNOWN
    ↓
确认最终结果
    ↓
重新计算名额
    ↓
决定是否恢复报名
```

重要：

**熔断恢复不代表 UNKNOWN 自动解除。**

即使服务器恢复正常，也必须先解决已有的未决报名请求。

## 4.6 只读健康检查

半开状态只能使用已经存在的只读接口。

例如：

- 活动列表。
- 用户基本信息。
- 已报名活动查询。

不允许：

- 报名测试。
- 退课测试。
- 通过真实提交接口探测服务器状态。

健康检查成功必须同时满足：

1. HTTP 请求成功。
2. 业务响应合法。
3. 数据完整。
4. 必要认证有效。
5. 没有明显的数据结构异常。

如果只是 HTTP 200，但活动列表内容不完整，不能恢复抢课。

## 4.7 测试要求

| 编号 | 测试内容                 | 预期                 |
| ---- | ------------------------ | -------------------- |
| C01  | 单次网络超时             | 记录失败             |
| C02  | 连续达到熔断阈值         | 进入 OPEN            |
| C03  | OPEN 状态                | 不发送新报名请求     |
| C04  | OPEN 状态                | 不频繁轮询           |
| C05  | 冷却结束                 | 进入 HALF_OPEN       |
| C06  | HALF_OPEN 成功           | 恢复 CLOSED          |
| C07  | HALF_OPEN 失败           | 重新进入 OPEN        |
| C08  | HALF_OPEN 只允许一次检查 | 无并发探测           |
| C09  | 健康检查返回不完整列表   | 不恢复业务           |
| C10  | Token 失效               | 使用现有刷新机制     |
| C11  | RefreshToken 失效        | 暂停业务并提示       |
| C12  | UNKNOWN + 熔断           | 两个安全屏障同时生效 |

# 五、任务三：抢课结果统计与自动报告

**优先级：P1**

## 5.1 当前问题

本次真实运行中，日志最终显示：

```
本次抢到 0 节
```

但服务端最终确认实际报名成功 2 节。

原因是：

目前计数器主要统计明确成功的报名提交。

UNKNOWN 没有计入成功数，也没有在最终报告中完整区分。

这导致用户无法直接判断真实结果。

本轮需要将提交过程统计与最终报名结果统计分开。

## 5.2 统一状态定义

建议明确以下状态：

| 状态               | 含义                 |
| ------------------ | -------------------- |
| SUBMITTING         | 正在提交             |
| SUCCESS            | 提交响应明确成功     |
| FAILED             | 提交响应明确失败     |
| UNKNOWN            | 提交结果无法确定     |
| RECONCILING        | 正在服务端复核       |
| RECONCILED_SUCCESS | 服务端复核确认成功   |
| RECONCILED_FAILED  | 服务端复核确认未成功 |
| UNRESOLVED         | 复核后仍然无法确定   |

具体实现可以复用当前 SQLite 状态结构，不要求为了显示统计而大规模修改数据库。

## 5.3 统计口径

必须区分两类数据。

### A. 提交过程统计

例如：

```
本次提交尝试：5 次

明确成功：0 次
明确失败：0 次
结果未知：5 次
```

### B. 最终服务端结果

```
最终对账：

服务端确认报名：2 节
服务端确认未报名：3 节
尚未解决：0 节
```

不得将：

- UNKNOWN 直接计入成功。
- UNKNOWN 直接计入失败。
- RECONCILED_SUCCESS 再重复计入一次新的成功报名。

提交尝试数量和最终报名数量必须使用独立统计口径。

## 5.4 最终报告格式

建议每次抢课结束后输出：

```
==================================================
                  抢课结果报告
==================================================

一、基本信息

运行日期：2026-11-01
当前教学周：第 9 周
目标教学周：第 10 周
运行模式：单进程

二、提交过程统计

提交尝试：5 次

明确成功：0 次
明确失败：0 次
UNKNOWN：5 次

三、服务端最终对账

确认报名成功：2 节
确认未报名：3 节
尚未解决：0 节

四、实际报名情况

普通活动：2 / 2
特殊活动：0
每日限制：未超出
每周限制：未超出

五、服务器异常

列表请求失败：22 次
HTTP -1：9 次
HTTP 500：10 次
HTTP 503：2 次
HTTP 504：1 次
```

# 七、数据持久化与兼容性要求

```
    ↓
```

# 十三、本轮开发最终原则

本轮最重要的不是让程序在服务器异常时继续运行，而是确保它在异常情况下不会做出危险决定。

必须遵守以下三条：

**第一：结果未知，不代表报名失败。**

**第二：存在未决报名请求时，不允许继续提交其他候选。**

**第三：服务器恢复，不代表之前的 UNKNOWN 自动解除，必须经过服务端复核。**

最终目标：

即使出现请求超时、HTTP 500、HTTP 503、HTTP 504、Token 失效、服务器长时间不可用，或者程序意外退出，也不能因为不确定的结果而重复报名或突破报名限制。

**宁可暂停抢课，也不能冒险超额。**
