> 对应《真正零模拟器登录协议研究与实现工作流程》第三阶段。
> 目标：把「已经验证的事实」和「尚未证实的假设」严格分开，避免后续基于错误前提开发。

## 一、当前协议流程（已验证）

```
用户输入 (账号, 密码)
        │
        ▼
计算签名   signDigital = hs(userName + password + entrance)     ← 在客户端原生库内完成
        │                                                          （我们无法独立生成）
        ▼
构造信封   {"t": 毫秒时间戳, "pyd": base64(AES-128-ECB(明文))}
        │   密钥 = f(t, 固定盐) —— 已还原
        ▼
POST https://cpes.legym.cn/authorization/user/v2/manage/login
        │   Content-Type: application/json
        ▼
响应信封   {"code":0, "data":{"t":..., "pyd":...}}
        │   用响应自带的 t 派生密钥解密
        ▼
明文包含   accessToken / refreshToken / accessTokenExpires
          schoolId / campusId / organizationId / realName 等
          **semesterId = null**（登录接口不返回，需另查）
        │
        ▼
GET  education/semester/getCurrent   ← 补全 semesterId / yearRange
        │
        ▼
原子写入 state.json
```

## 三、已验证实验

| 编号 | 实验 | 结果 | 结论 |
|---|---|---|---|
| E1 | 重放 1.6 分钟前的原信封 | HTTP 200 / code=0 | 服务端不校验会话一次性 |
| E2 | 用 1 小时前的 `t` 重新封装 | `40003 无法读取请求参数` | **`t` 有新鲜度窗口** |
| E3 | 用 1 天 / 7 天 / 30 天前的 `t` | 同上 | 窗口上限 < 1 小时 |
| E4 | 用当前 `t` + 已存签名登录 | HTTP 200 | **签名可复用** |
| E5 | 改密码后用旧签名登录 | `50004 签名不正确` | **服务端校验签名；签名绑定密码** |
| E6 | 模拟器同步 token 后登录 | 仍 `50004` | 同步 token ≠ 更新签名 |
| E7 | 端到端命令行登录 | 成功，token 可用 | 当前方案可用 |
| E8 | 信封理论测试 | 200 次往返一致 | 加密实现正确 |

## 四、已排除的假设

### H1：签名是简单的字符串哈希拼接 —— ❌ 已排除

穷举 **24,840** 种组合：

| 维度 | 取值 |
|---|---|
| 字段顺序 | 14 种（`upe` / `up` / `eup` / `upea` / `upeb` / `upeabd` …） |
| 分隔符 | 空、`:`、`\|`、`,`、`_`、`-` |
| 编码 | UTF-8 / UTF-16-LE / UTF-16-BE / GBK |
| 盐 | 空、`lgAI2021key~*21B`、动态密钥盐、`legym` 等 8 种 |
| 算法 | SHA1 / SHA256 / MD5，大小写各一 |
| 设备维度 | android_id、机型、品牌、包名 |

**全部不中。** 说明输入中还存在未识别的成分，或使用了非标准实现。

### H2：可以长期保存并重放原始信封 —— ❌ 已排除

见 E2 / E3，1 小时即失效。

### H3：静态反编译可还原 `hs()` —— ❌ 已排除

| 证据 | 数据 |
|---|---|
| `libsportaction.so` R-X 段整体熵 | 7.19 |
| 高熵窗口占比 | 33 / 67，峰值 7.94（近随机上限 8.0） |
| 对照组 `libsecurity.so` | 6.76，0 / 6 高熵窗口（明文代码） |
| 节区表 | 被破坏，整个文件标为 `SHT_NOBITS`，仅剩 4 个假节区 |

结论：签名实现位于 **DexVMP 加固区**，静态分析在不解包的前提下不可达。

### H4：`[a]` 模拟器同步可以修复签名 —— ❌ 已排除

见 E6。

## 六、当前可复用的模块

规范中假设的文件均已存在，与实际一致：

| 文件 | 职责 | 与签名问题的关系 |
|---|---|---|
| `core/auth_manager.py` | 登录、学期查询、state 原子保存 | **不依赖签名生成**，只接收已算好的签名 |
| `core/credential_storage.py` | DPAPI 加密存储、账号/密钥脱敏 | 与签名生成无关 |
| `core/auth_error.py` | 认证异常体系（含 50004 分类） | 已能区分「业务失败」与「网络失败」 |
| `tools/login_envelope.py` | 信封编解码 | **已稳定，不需要重写** |
| `tools/login_cli.py` | 命令行登录入口 | 当前基于「已有签名」 |
| `tools/capture_login.py` | 一键重抓签名 | 现阶段的兜底手段 |

### 关键认识

**AES 信封这部分已经完全解决，与 `signDigital` 是两件事。**
规范特别提醒过这一点，这里再次确认：
- 信封：可复现、已验证、无需模拟器
- 签名：不可复现、未验证、目前依赖客户端

任何后续设计都不得把两者混为一谈。

## 七、下一阶段可行性评估的入口

基于以上证据，进入 M1 需要回答的核心问题只有一个：

> **在不破解 DexVMP 加固、不绕过客户端保护性校验的前提下，
> 是否存在受支持的途径，让纯账号密码输入生成合法的 `signDigital`？**

这个问题直接决定 M1 是结论 A / B 还是 C。

现有证据指向的初步判断：

- 没有公开的官方登录 SDK 或第三方接入文档
- 签名逻辑被主动加固保护，说明厂商将其视为**安全边界**而非普通业务逻辑
- 因此「独立生成」在技术上等价于「还原被保护的安全边界实现」

M1 将据此展开正式评估。
