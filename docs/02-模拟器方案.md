# 模拟器方案：分工与路线

## 一句话

代码和环境脚本全部由我写；你只负责三件事：**装东西、登录 App、点一次选课**。

## 为什么必须有一次真实操作

我不知道乐健体育的接口长什么样——提交选课要传哪些字段、有没有 `sign` 签名、token 怎么来。
这些信息只存在于「模拟器 ↔ 学校服务器」的一次真实对话里。

所以流程是：**你制造一次真实对话 → 我把它录下来 → 我据此写程序**。

这一次之后，就再也不用你了。

## 谁做什么

| 环节 | 谁做 | 具体动作 |
|---|---|---|
| 装模拟器 | 你 | 双击安装包，设置里开 root |
| 装乐健体育 | 你 | 下载 APK，拖进模拟器窗口 |
| 配抓包环境 | 我（脚本） | 双击 |
| 登录 App | 你 | 手机号 + 短信验证码，这个谁也代替不了 |
| 点一次「选课」 | 你 | 就是平常操作 |
| 导出 HAR | 我（脚本） | 双击 |
| 分析接口 | 我 | 无 |
| 写抢课程序 | 我 | 无 |
| 每周日运行 | 你 | 双击一个 bat |

## 两条路线

### 路线 A：抓包 → 纯 HTTP 抢课（优先）

```
模拟器抓包一次 → HAR → 我写脚本 → 14:00 直接发 POST
```

- 速度：几十毫秒，接近理论极限
- 稳定：App 改版不影响，只要接口不变
- 代价：需要一次成功的抓包

### 路线 B：模拟器 UI 自动化（兜底）

```
程序通过 adb 对着屏幕点击
```

- 完全不需要抓包，不需要懂任何网络知识
- 速度：慢 1–2 秒，且要等界面刷新才知道成功没有
- 脆弱：App 一改版就失效
- 优点：**几乎保证能跑起来**

**先试 A，走不通再退 B。**

## 三个可能踩的坑

### 1. 模拟器检测
部分校园 App 检测到模拟器会闪退或提示「环境异常」。
判断方法：装完打开，能正常进选课页就没问题。
真被拦，只能回真机（那就需要 root 或改用路线 B）。

### 2. 证书绑定（pinning）
App 只信任内置证书时，抓包会看到一片 unknown。
模拟器有 root，可以用 Magisk 模块「Move Certificates」或 Frida 解绑。
麻烦，但可解。

### 3. 请求签名（最麻烦）
如果提交选课的请求里有个随请求变化的 `sign`，就不能简单重放。
真遇到这种，路线 A 成本显著上升，需要评估值不值得继续。

**这三种情况，抓一次包就全清楚了。**

## 澄清：抓包 ≠ 逆向

「抓包」是让你的设备记录它和服务器之间的对话，属于**观察**。
不需要反编译、不需要读汇编、不需要懂加密算法。

真正需要逆向的是「发现 sign 之后去看它怎么算」——那是下一步的事，
现在不用怕，大概率用不上。
