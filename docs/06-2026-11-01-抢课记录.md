## 四、这次做对的地方

### 4.1 单进程
上周超额的直接原因是两个进程并发。本次全程只有 1 个进程，实测未再出现超额。

### 4.2 完整性守卫
拉取失败时**拒绝基于残缺数据做决策**，直接跳过本轮：

```
[列表完整性警告] 活动列表不完整 (第 1 页拉取失败 (HTTP 500))，
仅拉取到 0/0 条，禁止基于不完整数据进行抢课决策，跳过本次轮询
```

这避免了上周「把空列表当成没有候选」或「把残缺列表当成全部」的误判。

### 4.3 UNKNOWN 不重试
提交超时后标记为 `[UNKNOWN]`，**不再对同一条重复提交**：

```
报名 户外跑 程启航 -> [UNKNOWN] 提交异常且无法复核状态(请求超时（结果未知）)，保持 UNKNOWN
```

上周正是因为把超时当失败、反复重试，才多抢了一节。

### 4.4 全局对账兜底
抢满或窗口结束时拉一次服务端真实状态，与实际报名核对：

```
================ 最终报名结果全局核对 ================
服务端实际已报名 2 节（普通 2 节，特殊 0 节）：
  - 11-06 18:35  周五 18:35~19:25  户外跑 程启航
  - 11-05 18:35  周四 18:35~19:25  户外跑 王彤帆
核对通过：实际报名未超出配置上限。
```

### 4.5 故障自证
新增的事件日志把每次中断的起止和耗时都记下来了，事后不需要靠回忆还原。

## 五、仍然存在的风险

### 5.1 跨候选快速连发

本次实际提交了 **5 个不同候选**（程启航、王彤帆、廖华、周天一、陈源森），
因为前几次都返回 UNKNOWN，程序继续试下一个。

**最终只落地 2 个**，是因为其余 3 次请求本身失败了。
如果那 3 次恰好都成功，就会出现 **5 节** —— 对账能发现，但发现时已经晚了。

> 建议：UNKNOWN 之后应**先复核一次状态再决定要不要换候选**，
> 而不是立刻打下一个。这是下周最该补的一环。

### 5.2 「本次抢到 0 节」的计数口径

日志结尾写「本次抢到 0 节」，是因为计数器只统计**明确成功**的提交，
而本次所有成功都是 UNKNOWN 状态。真实结果由对账补上。

这个口径容易误读，建议改成「明确成功 N 节，对账确认 M 节」。

### 5.3 token 依然只能撑 12 小时

今天上午 10:06 就已经在报 500，token 是临时续上的。
若哪天 refreshToken 失效而人不在电脑前，就会整场空转。

## 八、事后架构改进与 UNKNOWN 安全屏障落地（当前代码行为）

> **说明**：上述章节一至七为 2026-11-01 真实抢课现场的历史实况记录，保留事故原貌。本节记录事后在架构层实施的闭环改进与验证情况。

针对 11-01 抢课中暴露的「首个候选超时进入 UNKNOWN 后，程序未能先确认状态便盲目切换并提交后续候选」的核心缺陷，系统现已全面引入 **UNKNOWN 全局安全屏障与未决请求状态机**：

### 1. 核心状态机架构 (`core/registration_manager.py`)
- **严格未决屏障**：当任何报名提交遭遇超时或 500/502/503/504 等未决状态时，立即将该请求持久化标记为 `UNKNOWN`，并直接中断候选队列轮询，**绝对禁止继续提交下一个候选**。
- **只读复核优先**：在下一次轮询或程序重启时，必须优先对历史未决记录执行只读拉取与对账（`resolve_unknown`），不发起任何修改类请求。
- **名额闭环与状态解冻**：
  - 若复核确认服务端已报名成功，状态转为 `SUCCESS`，计入当周/当日配额，并根据配额决定是否继续或终止抢课；
  - 若复核确认未报名成功，状态转为 `RETRYABLE`，安全释放预占名额，允许队列推进下一候选；
  - 若复核遭遇异常或拉取的活动列表不完整，状态**保持 UNKNOWN 持续冻结**，坚决不盲目放行。

### 2. 自动化测试套件完整覆盖 (`tests/test_unknown_barrier.py`)
针对上述行为，项目构建了专有测试套件并实现 100% 通过（U01～U12）：
- **U01**: 第一个候选超时 -> 自动进入 UNKNOWN 并冻结
- **U02**: 第一个候选 503 -> 自动进入 UNKNOWN 并冻结
- **U03**: UNKNOWN 产生后队列中仍有其他候选 -> 安全屏障严格阻断后续候选提交
- **U04**: UNKNOWN 只读复核确认成功 -> 状态更新为 SUCCESS 并累加配额
- **U05**: UNKNOWN 只读复核明确未成功 -> 释放预占名额并允许下一候选
- **U06**: UNKNOWN 复核拉取到不完整活动列表 -> 严禁误判，持续保持冻结
- **U07**: UNKNOWN 复核网络超时 -> 持续保持冻结
- **U08**: 程序重启时发现遗留 SUBMITTING 记录 -> 自动恢复为 UNKNOWN 并触发只读复核
- **U09**: 程序重启时发现遗留 UNKNOWN 且复核未果 -> 严禁直接抢课，保持冻结
- **U10**: UNKNOWN 确认成功达到本周/本日上限 -> 自动终止后续队列
- **U11**: UNKNOWN 确认失败且配额未满 -> 允许提交下一候选
- **U12**: 并发调用保护 -> 存在未决记录时拒绝第二个提交

通过上述改进，历史实战中出现的「盲目击穿候选」风险已在状态机与代码执行链路上被彻底消除。
