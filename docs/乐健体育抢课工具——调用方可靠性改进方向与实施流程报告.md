# 乐健体育抢课工具——调用方可靠性改进方向与实施流程报告

**项目仓库：** https://github.com/vindcation0/lejianPE

**目标：** 提高抢课工具在服务端高并发、接口异常、请求超时等不稳定环境下的可靠性，重点解决重复报名、报名状态误判、多进程并发提交、程序异常退出后状态丢失等问题。

**实施原则：** 保持现有业务规则和功能不变，优先改善调用方的可靠性、状态管理、异常处理与故障恢复能力。

# 一、项目背景与本次改进目标

## 1.1 故障背景

2026-10-25 首次实战抢课期间，学校服务器在 14:00 开放报名时出现明显过载。

主要表现：

1. HTTP 500、502、503 混合出现。
2. 部分请求耗时从正常的 0.2 秒上升至 15 秒超时。
3. 网关可能在业务处理完成后返回 502/503。
4. 客户端将已经成功的报名误判为失败，继续提交请求。
5. 旧的抢课进程和应急脚本同时提交，进一步放大重复报名风险。
6. 客户端无法准确区分业务失败、请求失败和请求结果未知。

最终实际报名 3 节，超过目标的 2 节，需要人工退掉多余课程。

本次故障表明：当前系统最大的问题不是请求速度不够，而是调用方无法在不可靠的网络环境下保证业务操作的正确性。

## 1.2 核心改进目标

本次改进围绕以下目标展开：

1. 避免同一活动重复提交报名。
2. 请求超时或网关报错后，能够核实服务器真实报名状态。
3. 防止多个程序实例同时提交。
4. 程序意外退出后能够恢复之前的报名状态。
5. 将查询请求与有副作用的提交请求分开处理。
6. 服务端异常时采用合理的退避策略。
7. 建立完整的请求审计日志。
8. 抢课结束后通过服务器实际报名状态核对最终结果。

最终设计原则：

**宁可少发，不可重复；发完必复核。**

# 二、当前代码存在的问题

接手后先检查当前 main 分支，确认实际代码状态，不要仅根据历史故障报告判断修改是否已经完成。

重点检查以下位置：

## 2.1 HTTP 请求层

文件：`lejian.py`

当前 `_request()` 使用固定的 15 秒超时：

```
with urllib.request.urlopen(req, timeout=15, context=SSL_CTX) as r:
    return r.status, dec(r.read())
```

问题：

- 超时设置固定。
- 没有统一的请求分类。
- 查询和报名请求缺少差异化处理。
- 没有清晰区分请求失败与业务操作结果未知。

## 2.2 报名接口

重点检查：

```
Client.sign_up()
```

当前逻辑主要根据 HTTP 状态和业务响应判断是否成功。

问题：

- HTTP 503 可能发生在服务器完成报名之后。
- 超时被直接当作失败。
- 没有完整的报名结果复核流程。
- 不确定结果可能导致重复提交。

## 2.3 抢课主循环

重点检查：

```
cmd_grab()
```

当前部分状态依赖内存变量：

```
week_done = {}
last_try = {}
```

问题：

- 程序重启后状态丢失。
- 多进程之间无法共享状态。
- 无法可靠恢复中断前的提交记录。
- 报名请求与最终报名结果缺少完整闭环。

## 2.4 多进程控制

当前没有可靠的单实例保护机制。

多个进程可以同时执行抢课逻辑，导致重复提交。

## 2.5 日志系统

当前已有基础运行日志，但还需要建立独立的请求审计记录，能够完整还原每一次报名操作。

## 2.6 配置与故障报告不一致

需要重点核实：

- 故障报告记录的 6 秒超时是否已经进入当前主程序。
- 配置文件中的轮询间隔与实际运行间隔是否一致。
- 失败后快速重试策略是否已经实现。
- 是否仍然存在旧的请求重试逻辑。

统一代码、配置和故障报告，避免出现修改已经完成但实际运行代码没有更新的情况。

# 三、总体改进架构

建议将当前抢课程序逐步调整为以下结构。

```
                    cmd_grab()
                        |
                        v
                  单实例锁检查
                        |
                        v
                  初始化状态管理
                        |
                        v
                  活动列表查询
                        |
                        v
                  业务规则过滤
                        |
                        v
                  报名资格检查
                        |
                        v
                  检查持久化状态
                        |
                        v
                  检查服务器报名状态
                        |
                        v
                  提交报名请求
                        |
             +----------+----------+
             |          |          |
             v          v          v
           成功       明确失败    结果未知
             |          |          |
             v          v          v
          SUCCESS    FAILED      UNKNOWN
                                   |
                                   v
                              状态复核
                                   |
                         +---------+---------+
                         |                   |
                         v                   v
                   已经报名              尚未报名
                         |                   |
                         v                   v
                      SUCCESS          重新评估资格
                                             |
                                             v
                                      RETRYABLE / FAILED
```

最终所有结果进入统一的状态管理模块。

建议新增以下模块：

| 模块                  | 职责                      |
| --------------------- | ------------------------- |
| RequestManager        | HTTP 请求、超时、错误分类 |
| RegistrationManager   | 报名提交与结果复核        |
| StateStore            | 持久化报名状态            |
| InstanceLock          | 单实例运行控制            |
| RetryPolicy           | 请求退避与重试策略        |
| AuditLogger           | 请求审计日志              |
| RecoveryManager       | 程序启动及异常恢复        |
| ReconciliationManager | 最终报名结果核对          |

可以继续保留 `lejian.py` 作为主入口，但应尽量将具体职责拆分，避免主程序越来越臃肿。

不要求为了拆分而大规模重写现有业务逻辑。

# 四、具体改进方向与实施要求

## 方向一：建立报名状态机

**优先级：最高**

这是本次改进的核心。

不再使用简单的成功/失败布尔值管理报名操作。

为每个活动建立独立的报名状态。

### 4.1 状态定义

| 状态       | 含义                                   |
| ---------- | -------------------------------------- |
| PENDING    | 已发现符合条件的活动，尚未提交         |
| SUBMITTING | 正在提交报名请求                       |
| SUCCESS    | 已确认报名成功                         |
| FAILED     | 已确认业务失败                         |
| UNKNOWN    | 请求结果未知，不能确定服务器是否处理   |
| VERIFYING  | 正在通过服务端核实报名状态             |
| RETRYABLE  | 已确认尚未报名，重新评估后可以再次提交 |

### 4.2 状态流转规则

PENDING → SUBMITTING：

准备提交报名。

SUBMITTING → SUCCESS：

收到明确的业务成功响应。

SUBMITTING → FAILED：

收到明确的业务失败响应，例如名额已满。

SUBMITTING → UNKNOWN：

出现以下情况：

- HTTP -1 超时。
- HTTP 502。
- HTTP 503。
- 无法解析响应。
- 响应内容无法确定业务执行结果。

UNKNOWN → VERIFYING：

开始检查服务器真实报名状态。

VERIFYING → SUCCESS：

服务端确认 `isRegister = true`。

VERIFYING → RETRYABLE：

服务端明确确认 `isRegister = false`，并且活动仍处于报名窗口、仍满足全部业务规则。

VERIFYING → UNKNOWN：

复核请求本身失败，无法确认报名状态。

注意：

**UNKNOWN 状态绝对不能直接进入自动重试。**

只有取得可信的服务端未报名结果后，才允许重新评估提交资格。

如果活动列表没有返回目标活动、数据不完整或者查询结果不可靠，也不能据此判定未报名。

### 4.3 状态持久化

建议采用 SQLite 管理报名状态。

建议建立 `registration_records` 表：

| 字段             | 类型    | 说明              |
| ---------------- | ------- | ----------------- |
| activity_id      | TEXT    | 活动 ID，唯一标识 |
| activity_name    | TEXT    | 活动名称          |
| status           | TEXT    | 当前报名状态      |
| attempts         | INTEGER | 提交尝试次数      |
| last_error       | TEXT    | 最近错误          |
| updated_at       | TEXT    | 最后更新时间      |
| verified_at      | TEXT    | 最后复核时间      |
| last_http_status | INTEGER | 最近 HTTP 状态码  |

要求：

1. 每次提交前先持久化 SUBMITTING。
2. 收到响应后更新状态。
3. 请求超时后更新 UNKNOWN。
4. 复核完成后更新最终状态。
5. 使用 SQLite 事务保证状态更新的一致性。
6. 使用 activity_id 保证同一个活动不会创建重复记录。

特别注意：

程序在 SUBMITTING 状态突然崩溃时，重启后必须将该记录视为结果未知，先复核，不能直接重新提交。

本地状态去重不等于服务端幂等。不要假设学校接口支持 Idempotency-Key。

## 方向二：建立报名结果复核机制

**优先级：最高**

接口文档已经确认：

```
education/app/activity/getActivityList
```

返回的活动对象包含：

```
{
  "id": "activity_id",
  "isRegister": true
}
```

`isRegister` 是判断本人是否已经报名的重要字段。

### 4.4 提交前检查

每次准备报名时：

1. 检查本地状态。
2. 如果本地状态是 SUCCESS，禁止重复提交。
3. 如果本地状态是 UNKNOWN 或 SUBMITTING，必须先复核。
4. 如果服务器已经显示 `isRegister = true`，直接更新 SUCCESS。
5. 只有确认未报名且满足业务规则，才允许提交。

### 4.5 提交后检查

收到报名结果后：

- 明确成功：更新 SUCCESS。
- 明确业务失败：更新 FAILED。
- 超时、502、503：更新 UNKNOWN。

对于 UNKNOWN：

1. 暂停该活动的后续提交。
2. 重新拉取活动列表。
3. 找到对应 activity_id。
4. 检查 `isRegister`。
5. 已报名则更新 SUCCESS。
6. 未报名且数据可靠则重新评估资格。
7. 复核失败则继续保留 UNKNOWN。

不能把复核接口失败理解为未报名。

### 4.6 全局核对

当达到每周报名上限后：

1. 暂停所有提交。
2. 拉取最新活动列表。
3. 按教学周统计 `isRegister`。
4. 按日期统计普通活动报名数量。
5. 与 `max_normal`、`max_per_day` 比较。
6. 输出实际报名结果。

第一阶段只要求发现超额、停止提交和告警。

**不要直接自动退课。**

退课也是有副作用的操作，应该保留人工确认环节。

## 方向三：增加单实例锁

**优先级：最高**

解决多个抢课进程同时提交的问题。

建议使用 Windows 操作系统级文件锁。

### 4.7 启动流程

程序进入正式抢课流程前：

1. 尝试获取全局锁。
2. 获取成功，继续运行。
3. 获取失败，提示已有抢课进程正在运行。
4. 拒绝启动第二个抢课实例。

### 4.8 锁的要求

- 使用操作系统级锁，而不是单纯判断 lock 文件是否存在。
- 程序正常退出后释放锁。
- 程序异常退出后，操作系统能够自动释放锁。
- 不允许因为残留锁文件导致程序永久无法启动。
- 锁的作用范围必须覆盖报名提交和状态恢复流程。

建议对 `grab` 和 `grab now` 都启用相同的锁。

`list`、`status` 等只读操作可以根据实现决定是否允许并行，但不得绕过正式抢课进程的锁保护。

## 方向四：区分查询请求与报名请求

**优先级：高**

当前请求层需要进一步抽象。

将请求分为两种：

### 4.9 查询请求

例如：

- getActivityList
- getActivityDetail
- checkConflict

特点：

- 不直接产生报名副作用。
- 可以在符合规则的情况下重试。
- 服务端异常时使用退避策略。
- 需要设置最大重试次数。

### 4.10 提交请求

例如：

- signUp

特点：

- 有实际业务副作用。
- 不允许简单地因为 HTTP 失败就重新提交。
- 超时后必须进入 UNKNOWN。
- 优先通过服务端状态复核。
- 只有明确确认未报名后才可以重新评估是否提交。

建议将接口职责分开：

```
request_query()
submit_once()
verify_registration()
```

不要为所有请求统一添加自动重试装饰器。

### 4.11 错误分类

| 情况                    | 处理                                   |
| ----------------------- | -------------------------------------- |
| HTTP 200，业务成功      | SUCCESS                                |
| HTTP 200，名额已满      | FAILED                                 |
| HTTP 200，每日/每周上限 | 核对当前报名情况                       |
| HTTP 401                | 按现有 Token 刷新机制处理              |
| HTTP 429                | 遵守服务端限流要求                     |
| HTTP 500                | 根据接口性质判断，提交请求优先复核     |
| HTTP 502/503            | 查询请求退避，提交请求进入 UNKNOWN     |
| HTTP -1                 | 根据请求类型分类，提交请求进入 UNKNOWN |

注意：HTTP 状态码不能独立决定报名结果。

## 方向五：增加指数退避机制

**优先级：高**

当前轮询和失败处理主要依赖固定间隔。

服务端发生持续故障时，应该主动降低请求频率。

建议采用指数退避：

```
delay = min(max_delay, base_delay * (2 ** retry_count))
```

例如：

| 连续失败次数 | 等待时间示例 |
| ------------ | ------------ |
| 1            | 0.5 秒       |
| 2            | 1 秒         |
| 3            | 2 秒         |
| 4            | 4 秒         |
| 5            | 8 秒         |

再加入随机抖动，避免多个请求固定时间同时发出。

要求：

1. 查询失败时使用退避。
2. 查询成功后逐步恢复正常轮询。
3. 429 等限流响应必须尊重服务端要求的等待时间。
4. 提交失败不能通过提高提交频率来解决。
5. 对超时设置合理上限。
6. 查询和提交使用不同的重试策略。

不要为了提高竞争速度而无限提高请求密度。

## 方向六：建立独立请求审计日志

**优先级：高**

保留当前运行日志，同时增加独立的 JSONL 请求审计文件。

建议路径：

```
logs/
├── run-YYYYMMDD.log
├── events-YYYYMMDD.jsonl
└── requests-YYYYMMDD.jsonl
```

每次报名操作生成独立记录。

建议格式：

```
{
  "request_id": "20261025-001",
  "activity_id": "123456",
  "action": "sign_up",
  "started_at": "2026-10-25T14:00:01.123",
  "finished_at": "2026-10-25T14:00:07.123",
  "http_status": 503,
  "business_success": null,
  "registration_verified": true,
  "final_state": "SUCCESS",
  "attempts": 1
}
```

记录字段至少包括：

- 请求唯一 ID。
- 活动 ID。
- 活动名称。
- 请求类型。
- 请求开始时间。
- 请求结束时间。
- 请求耗时。
- HTTP 状态码。
- 业务响应码。
- 错误信息。
- 是否进行了状态复核。
- 复核结果。
- 最终状态。
- 提交尝试次数。

注意：

1. 不记录完整 accessToken。
2. 不记录 refreshToken。
3. 不泄漏手机号、学号等个人敏感信息。
4. 日志应该能够关联同一个活动的整个报名流程。
5. 日志写入失败不能导致报名流程继续重复提交。

## 方向七：建立启动恢复与最终核对机制

**优先级：高**

### 4.12 启动恢复

程序启动后：

1. 加载 SQLite。
2. 检查上次运行留下的状态。
3. 找出 SUBMITTING、UNKNOWN、VERIFYING 等未完成记录。
4. 对这些记录逐个进行服务端复核。
5. 已经报名的更新 SUCCESS。
6. 仍然无法确认的保留 UNKNOWN。
7. 确认未报名的重新评估资格。

不得直接清空上一次的状态重新开始。

### 4.13 服务端恢复检测

建议增加运行状态：

| 状态       | 含义                       |
| ---------- | -------------------------- |
| NORMAL     | 查询接口工作正常           |
| DEGRADED   | 连续出现 5xx 或超时        |
| RECOVERING | 查询接口恢复，正在核对状态 |

运行逻辑：

- NORMAL：正常执行。
- DEGRADED：减少查询请求，暂停不确定报名的重复提交。
- RECOVERING：重新获取活动列表，核对所有未完成报名。
- 核对完成后恢复正常流程。

## 方向八：增加完整测试体系

**优先级：高**

不能等到下一次正式开抢才验证改进效果。

所有核心逻辑都应该通过模拟响应进行测试。

测试不应通过向学校服务器制造重复报名请求来完成。

### 4.14 必须覆盖的测试场景

| 编号 | 测试场景                            | 预期结果                      |
| ---- | ----------------------------------- | ----------------------------- |
| T01  | 提交返回 200 成功                   | SUCCESS                       |
| T02  | 提交返回 503，复核 isRegister=true  | SUCCESS                       |
| T03  | 提交超时，复核请求也超时            | UNKNOWN                       |
| T04  | 提交返回 503，复核 isRegister=false | RETRYABLE，重新评估后才可提交 |
| T05  | 复核活动列表缺失目标活动            | UNKNOWN                       |
| T06  | 两个抢课程序同时启动                | 只有一个获得锁                |
| T07  | 报名成功后程序突然崩溃              | 重启后能够恢复 SUCCESS        |
| T08  | 提交过程中程序崩溃                  | 重启后先复核，不直接重试      |
| T09  | 连续查询失败                        | 触发指数退避                  |
| T10  | 收到 HTTP 429                       | 遵守限流要求                  |
| T11  | 抢到第三节                          | 检测超额并停止提交            |
| T12  | 程序重复运行                        | 不重复提交已经 SUCCESS 的活动 |
| T13  | SQLite 写入失败                     | 不得继续进行不安全的提交      |
| T14  | Token 过期                          | 使用原有刷新机制恢复鉴权      |
| T15  | 活动报名窗口已关闭                  | 不允许重新提交                |

特别关注：

T02、T03、T06、T07、T08。

这几个测试直接对应本次故障暴露的关键问题。

# 五、实施顺序与交付阶段

不要一次性大规模重构。

建议按以下顺序实施，每个阶段完成后进行独立测试。

## 第一阶段：保证报名正确性

目标：解决重复提交与报名结果误判。

任务：

# 十、最终设计原则

本项目下一阶段的重点不是让程序发出更多请求，而是让每一次请求都能够得到正确处理。

需要从原来的：

```
发现活动 → 提交请求 → 根据响应判断成功失败
```

升级为：

```
发现活动
    ↓
检查本地状态
    ↓
检查服务器状态
    ↓
提交一次请求
    ↓
判断响应是否可信
    ↓
不确定时进入 UNKNOWN
    ↓
通过服务器真实状态复核
    ↓
持久化最终结果
    ↓
核对整体报名数量
```

**最终目标：即使学校服务器发生持续 5xx、请求超时、网关回程失败，甚至本地程序意外崩溃，调用方也能够最大限度地避免重复报名，并准确恢复真实报名状态。**

本次改进的核心不是追求更快，而是追求正确、可恢复、可验证。
