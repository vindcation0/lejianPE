# 乐健体育抢课系统第四轮优化执行方案

**项目仓库：** `vindcation0/lejianPE`
**目标：** 提升服务器异常场景下的系统可靠性、状态一致性和故障恢复能力。
**实施原则：** 优先修复真实缺陷，保护现有正确机制，不进行无关重构。

# 一、项目背景

本轮优化基于上一轮代码审查结果。

当前项目已经具备以下模块：

- `core/circuit_breaker.py`：熔断器
- `core/reconciliation.py`：服务端全局对账
- `core/registration_manager.py`：报名管理
- `core/request_manager.py`：请求管理
- `core/recovery_manager.py`：异常恢复
- `core/result_reporter.py`：结果统计与报告
- `core/audit_logger.py`：审计日志
- `core/state_store.py`：状态持久化
- `core/retry_policy.py`：请求退避策略

目前主要问题不是缺少功能模块，而是部分模块之间没有形成完整的可靠性闭环。

## 1.1 本轮核心目标

1. 修复活动列表请求失败与熔断器之间的集成问题。
2. 保证 UNKNOWN 安全屏障在所有异常情况下有效。
3. 修复请求次数、故障次数、复核次数的统计口径。
4. 修复最终对账失败被错误统计为零报名的问题。
5. 实现服务端冲突检查的安全降级机制。
6. 增加抢课前健康预热机制。
7. 建立真实故障场景的集成测试。

## 1.2 重要约束

以下机制必须保留：

- 报名请求只能提交一次，禁止盲目自动重试。
- 提交前必须持久化 `SUBMITTING`。
- 请求超时、网关异常等不明确结果必须进入 `UNKNOWN`。
- UNKNOWN 未解决时必须冻结其他候选提交。
- 只有完整、有效的服务端数据才能确认未报名。
- 熔断器恢复不能自动解除 UNKNOWN。
- 所有报名数量必须以服务端最终对账结果为准。
- 不允许因网络故障释放潜在名额。
- 不允许因程序崩溃丢失未决报名状态。

**注意：本方案中的代码行号和审查结论来自上一轮对 main 分支的检查。实施前必须重新检查目标分支，确认问题仍然存在，不要机械地按照旧行号修改。**

# 二、P0：修复核心可靠性问题

这是本轮最高优先级，必须首先完成。

## 任务一：修复活动列表请求与熔断器的集成

### 涉及文件

- `lejian.py`
- `core/circuit_breaker.py`
- `core/retry_policy.py`
- 相关测试文件

### 现存问题

上一轮审查发现：

`Client.activities()` 内部连续请求失败后，会返回：

```
ActivityList(
    items,
    complete=False,
    total=total,
    fetched=len(out),
    error=err_msg
)
```

主循环收到不完整列表后，调用：

```
circuit_breaker.record_success(is_complete=False)
```

但当前 `CircuitBreaker.record_success()` 在 CLOSED 状态下会清零失败计数。

导致：

```
服务器连续返回 500
       |
       v
activities() 连续请求失败
       |
       v
complete = False
       |
       v
record_success(False)
       |
       v
CLOSED 状态失败计数被清零
       |
       v
下一轮继续请求
```

因此，真实业务中的连续列表请求失败可能无法触发预期熔断。

### 修改要求

#### 1. 统一故障分类

明确区分：

| 故障类型       | 熔断处理                     |
| -------------- | ---------------------------- |
| 网络连接超时   | 记录基础设施故障             |
| HTTP 500       | 记录基础设施故障             |
| HTTP 502       | 记录基础设施故障             |
| HTTP 503       | 记录基础设施故障             |
| HTTP 504       | 记录基础设施故障             |
| HTTP 401       | Token 处理，不直接触发熔断   |
| HTTP 403       | 独立权限异常处理             |
| HTTP 400       | 不直接触发熔断               |
| 正常业务错误   | 不触发熔断                   |
| 列表数据不完整 | 禁止业务决策，不视为健康恢复 |

注意：HTTP 状态码和业务响应码必须分别判断，不能只看 HTTP 200 就认为请求成功。

#### 2. 调整活动列表失败处理

建议将底层请求结果和故障信息传递到统一故障处理层。

要求：

- 每次 HTTP 请求失败都能被准确记录。
- 连续基础设施故障达到阈值时进入 OPEN。
- OPEN 状态禁止正常业务请求。
- 冷却结束后进入 HALF_OPEN。
- HALF_OPEN 只允许一次只读健康探测。
- 只有取得完整列表才能恢复 CLOSED。
- 不完整列表不能恢复熔断器。
- 半开探测失败必须重新进入 OPEN。

#### 3. 避免重试叠加

目前活动列表内部存在快速重试。

需要评估：

- 内部重试次数。
- 外层轮询次数。
- RetryPolicy 退避。
- CircuitBreaker 冷却时间。

防止多层重试叠加，造成服务器恢复期间请求压力过大。

建议由统一策略控制请求退避。

#### 4. 日志要求

至少记录：

```
list_request_started
list_request_failed
list_request_incomplete
circuit_open
circuit_half_open
circuit_closed
list_request_recovered
```

每个事件需要包含必要的时间、故障类型、HTTP 状态码、失败次数和状态转换信息。

### 验收标准

- 连续三次基础设施故障能够触发 OPEN。
- OPEN 状态不允许正常活动列表轮询。
- HALF_OPEN 只允许一次健康探测。
- 半开探测失败重新进入 OPEN。
- 不完整列表不能恢复 CLOSED。
- 完整列表恢复后才能重新执行正常业务。
- 401、403、400 不会被错误归类为基础设施故障。
- 所有请求次数与日志记录一致。

## 任务二：强化 UNKNOWN 安全屏障

### 涉及文件

- `core/registration_manager.py`
- `core/request_manager.py`
- `core/state_store.py`
- `core/recovery_manager.py`
- `lejian.py`

### 现有正确机制

以下设计必须保留：

1. 提交前持久化 SUBMITTING。
2. 提交请求不自动重试。
3. 超时或不明确响应进入 UNKNOWN。
4. 通过服务端列表进行只读复核。
5. 确认成功后更新 SUCCESS。
6. 确认未报名后更新 RETRYABLE。
7. 复核失败继续保持 UNKNOWN。
8. UNKNOWN 未解决时禁止新的报名请求。

### 本轮需要加强的地方

#### 1. 熔断器与 UNKNOWN 独立

必须保证：

```
UNKNOWN 未解决
       |
       v
服务器恢复
       |
       v
熔断器 CLOSED
       |
       v
UNKNOWN 仍然存在
       |
       v
继续冻结候选队列
```

熔断器恢复只代表服务器健康，不代表报名结果已经确定。

#### 2. 完整性校验

复核未报名必须同时满足：

- 活动列表请求成功。
- 分页数据完整。
- 找到目标活动。
- 目标活动明确显示 `isRegister=False`。

以下情况都不能判定为未报名：

- 请求超时。
- HTTP 5xx。
- 列表为空但完整性未知。
- 目标活动没有出现在列表中。
- 活动列表分页失败。
- 服务端返回数据结构异常。

#### 3. 持久化与崩溃恢复

重点验证：

```
写入 SUBMITTING
       |
       v
发送 signUp
       |
       v
程序突然崩溃
       |
       v
重新启动
       |
       v
发现 SUBMITTING
       |
       v
只读复核
       |
       v
SUCCESS / RETRYABLE / UNKNOWN
```

禁止程序启动后直接重新提交遗留 SUBMITTING 请求。

#### 4. 配额更新

UNKNOWN 复核确认成功后：

- 正确更新每周普通活动数量。
- 正确更新每日普通活动数量。
- 正确更新特殊活动数量。
- 重新计算剩余名额。
- 重新评估是否允许继续候选队列。

### 验收标准

- UNKNOWN 未解决时，其他候选不能提交。
- 熔断器恢复不能解除 UNKNOWN。
- UNKNOWN 确认成功后不重复报名。
- UNKNOWN 确认未报名后才允许重新评估。
- 复核数据不完整时必须继续冻结。
- 程序重启后能够恢复未决状态。

# 三、P1：修复日志与结果统计

## 任务三：重构请求审计日志

### 涉及文件

- `core/audit_logger.py`
- `core/request_manager.py`
- `core/registration_manager.py`
- `core/result_reporter.py`

### 现存问题

目前提交尝试统计与实际 HTTP 提交行为没有完全对应。

例如：

主循环中记录：

```
reporter.record_attempt(...)
```

既用于真实报名，也用于 UNKNOWN 复核结果。

这会导致复核操作被误计为提交尝试。

此外，规则拦截也不应算作真实 HTTP 报名请求。

### 修改要求

将统计拆分为四类：

| 类型           | 含义                 |
| -------------- | -------------------- |
| Candidate      | 候选评估次数         |
| Submission     | 实际 signUp 请求次数 |
| Verification   | UNKNOWN 复核次数     |
| Reconciliation | 最终全局对账次数     |

建议设计统一的事件字段：

```
{
  "event_id": "unique-id",
  "timestamp": "ISO-8601",
  "event_type": "submission",
  "activity_id": "1001",
  "status": "UNKNOWN",
  "http_status": 503,
  "reason": "gateway timeout"
}
```

以上仅为字段设计示例，实际实现需要结合当前项目日志结构。

### 关键要求

1. 实际调用 `submit_once()` 才记录真实提交请求。
2. 复核操作单独记录。
3. 候选规则拦截不算真实提交。
4. 每次请求都有独立事件 ID。
5. 同一个请求的状态变化能够关联。
6. 不允许因重复复核而重复累计提交次数。
7. 日志必须严格脱敏。

禁止记录：

- AccessToken。
- RefreshToken。
- 手机号。
- 学号。
- 姓名等敏感个人信息。

## 任务四：修复故障统计与故障持续时间

### 现存问题

上一轮审查发现，`activities()` 失败通常通过 `complete=False` 返回，而不是抛出异常。

导致主循环中的：

```
reporter.record_http_failure(http_code)
```

无法完整覆盖真实列表请求失败。

另外，当前 `_note_fail()` 对相同 HTTP 状态码进行事件去重，因此事件日志数量不能直接作为 HTTP 请求失败次数。

### 修改要求

将以下统计分开：

| 统计项            | 统计方式           |
| ----------------- | ------------------ |
| HTTP 请求失败次数 | 每次失败请求记录   |
| 故障事件次数      | 故障状态变化时记录 |
| 故障恢复次数      | 故障恢复时记录     |
| 累计中断时间      | 故障开始至恢复     |
| 熔断触发次数      | 每次进入 OPEN      |
| 半开探测次数      | 每次执行探测       |
| 半开成功次数      | 探测成功次数       |

建议统一通过 AuditLogger 写入事件日志，避免 `lejian.py` 和其他模块重复实现 JSONL 写入。

### 验收标准

模拟：

- 9 次超时。
- 10 次 HTTP 500。
- 2 次 HTTP 503。
- 1 次 HTTP 504。

最终报告必须准确显示：

```
HTTP -1：9 次
HTTP 500：10 次
HTTP 503：2 次
HTTP 504：1 次

请求失败总数：22 次
```

注意：这是统计单元测试示例，不能把故障开始事件与失败请求次数混为一谈。

## 任务五：修复最终对账失败语义

### 涉及文件

- `lejian.py`
- `core/reconciliation.py`
- `core/result_reporter.py`

### 现存问题

上一轮发现最终报告阶段存在类似逻辑：

```
reconciled_items=report.get("items", [])
    if report.get("success") else []
```

当最终对账失败时，仍然将空列表传入统计器。

这样可能把：

```
无法取得服务端报名数据
```

错误解释为：

```
服务端确认报名数量为 0
```

### 修改要求

引入明确的对账状态：

```
SUCCESS
FAILED
UNVERIFIED
```

建议语义：

- SUCCESS：取得完整且可信的服务端对账结果。
- FAILED：对账请求明确失败。
- UNVERIFIED：无法确认真实报名状态。

对账失败时：

1. 不允许将空列表作为真实报名结果。
2. 不允许输出确定的零报名结论。
3. 不允许覆盖已有可靠的服务端统计结果。
4. 未解决 UNKNOWN 必须继续保留。
5. 报告必须明确显示对账未完成。

### 报告示例

```
最终对账状态：UNVERIFIED

无法取得完整服务端报名数据。
当前无法确认真实报名数量。

未决请求：1
禁止重复提交。
请在服务恢复后重新执行只读对账。
```

### 验收标准

- 对账成功：正常统计。
- 对账失败：显示未验证。
- 对账数据不完整：显示未验证。
- 未决 UNKNOWN：必须显示安全警告。
- 不允许用空列表覆盖真实的未知状态。

# 五、P2：冲突检查自动降级

## 任务七：改进 check_conflict 配置机制

### 涉及文件

- `lejian.py`
- `config.json`
- 相关规则测试文件

### 现存问题

当前配置：

```
{
  "check_conflict": false
}
```

虽然能够关闭服务端冲突检查，但旧配置文件如果没有这个字段：

```
cfg.get("check_conflict", True)
```

就会默认开启。

此外，服务端冲突接口异常时，目前主要依靠手动关闭配置解决。

### 修改要求

建议支持三种模式：

```
{
  "conflict_check_mode": "auto"
}
```

模式定义：

| 模式   | 行为                                   |
| ------ | -------------------------------------- |
| strict | 必须通过服务端冲突检查                 |
| local  | 只使用本地冲突校验                     |
| auto   | 优先服务端检查，满足安全条件时允许降级 |

### Auto 降级条件

只有以下条件全部满足，才允许使用本地规则降级：

1. 服务端明确返回基础设施故障。
2. 本地课表数据完整。
3. 服务端已报名活动列表完整。
4. 每日配额计算有效。
5. 每周配额计算有效。
6. 不存在未解决 UNKNOWN。
7. 本地冲突计算具备完整依据。

以下情况禁止降级：

- Token 失效。
- 权限异常。
- 数据格式错误。
- 本地课表缺失。
- 活动列表不完整。
- UNKNOWN 未解决。
- 无法确定当前报名数量。

### 日志要求

记录：

```
conflict_check_remote_success
conflict_check_remote_failed
conflict_check_fallback
conflict_check_blocked
```

必须明确记录本次使用了哪种校验方式。

### 验收标准

- strict 模式不允许自动降级。
- local 模式不调用服务端冲突接口。
- auto 模式在安全条件满足时可以降级。
- 安全条件不满足时必须阻断。
- 自动降级不修改磁盘配置。
- 日志能够追踪降级原因。

# 六、P2：抢课前预热机制

## 任务八：增加低频健康预热

### 涉及文件

- `lejian.py`
- `config.json`
- `core/circuit_breaker.py`

### 背景

此前观察到服务器可能在正式开抢前已经出现异常。

建议提前进行低频只读健康探测。

### 建议配置

```
{
  "watch_from": "13:55:00",
  "watch_until": "16:00:00",
  "preflight_interval_seconds": 20
}
```

### 阶段一：预热

13:55–13:59：

- 检查 Token。
- 检查活动列表接口。
- 检查分页完整性。
- 检查服务器状态。
- 记录 HTTP 异常。
- 不执行任何报名提交。

建议预热请求间隔为 15–30 秒，具体值应通过实际数据调整。

### 阶段二：正式运行

13:59 以后：

- 正常执行候选扫描。
- 按照现有规则检查报名资格。
- 使用完整服务端数据进行配额计算。
- 执行报名。
- 发生 UNKNOWN 立即冻结。
- 发生服务器故障由熔断器统一控制。

### 验收标准

- 预热阶段绝不调用 signUp。
- 预热阶段不能修改报名状态。
- 预热失败可以触发熔断。
- 服务器恢复后必须取得完整列表。
- 正式开抢时间不受预热逻辑错误影响。

# 七、测试体系建设

本轮不能只依赖单元测试。

需要同时验证模块逻辑与完整业务链路。

## 7.3 综合场景测试

### 场景 A：首次提交超时，实际已经成功

```
候选 A 提交
    |
HTTP 超时
    |
UNKNOWN
    |
冻结 B、C
    |
服务端恢复
    |
复核发现 A 已报名
    |
更新 SUCCESS
    |
重新计算配额
```

验收：

- 只发生一次 signUp。
- 不提交 B、C。
- A 被确认成功。
- 不超额。

### 场景 B：首次提交超时，实际没有成功

```
候选 A 提交
    |
HTTP 超时
    |
UNKNOWN
    |
冻结 B、C
    |
服务端恢复
    |
完整列表确认 A 未报名
    |
更新 RETRYABLE
    |
重新计算配额
    |
允许评估 B
```

验收：

- A 不会盲目重新提交。
- B 经过重新校验后才允许提交。

### 场景 C：服务器持续故障

```
活动列表失败
    |
连续故障达到阈值
    |
OPEN
    |
暂停请求
    |
冷却结束
    |
HALF_OPEN
    |
只读探测
    |
探测失败
    |
重新 OPEN
```

验收：

- 不进行高频请求。
- 不提交报名。
- 不使用不完整数据。
- 能够准确记录故障。

### 场景 D：提交后程序崩溃

```
写入 SUBMITTING
    |
发起 signUp
    |
程序崩溃
    |
重启
    |
恢复 SUBMITTING
    |
只读复核
```

验收：

- 不重复提交。
- 能恢复状态。
- 复核失败继续冻结。

### 场景 E：最终对账失败

```
存在 UNKNOWN
    |
最终对账请求失败
    |
UNVERIFIED
    |
保留状态数据库记录
    |
报告明确报警
    |
下次启动继续恢复
```

验收：

- 不输出确定的零报名。
- 不释放潜在名额。
- 不允许重复提交。
- 下次启动能够继续复核。

### 场景 F：Token 失效

验收：

- Token 失效与基础设施故障区分。
- 按现有刷新机制处理。
- 刷新失败不允许盲目继续报名。
- 提交结果不明确时仍进入 UNKNOWN。
- 最终状态通过服务端复核确定。

## 7.4 新增统计一致性测试

重点测试：

```
实际提交：6 次
UNKNOWN 复核：2 次
列表请求失败：22 次
```

预期：

```
Submission = 6

```

复核不能增加提交次数。

# 八、实施顺序

Agent 必须按以下顺序实施，不要并行修改所有模块。

## Phase 0：重新检查代码

1. 获取当前目标分支。
2. 检查 Git 工作区状态。
3. 检查当前配置文件。
4. 检查已有测试。
5. 确认本方案指出的问题是否仍然存在。
6. 输出问题确认清单。

## Phase 1：修复熔断集成

1. 统一列表请求故障分类。
2. 修复 CLOSED 状态下失败计数被清零的问题。

4. 检查 UNKNOWN 与熔断器独立性。
5. 检查程序崩溃恢复。
6. 增加端到端测试。

完成后先运行全部相关测试。

1. 分离候选、提交、复核、对账事件。

# 九、Agent 执行规范

以下规则必须遵守。

## 9.1 禁止行为

- 不允许为了通过测试而删除已有测试。
- 不允许降低 UNKNOWN 安全保护。
- 不允许自动重试 signUp。
- 不允许将复核失败解释为未报名。
- 不允许将对账失败解释为零报名。
- 不允许使用不完整活动列表执行候选决策。
- 不允许将 401、403 等所有异常统一视为服务器故障。
- 不允许修改无关业务逻辑。
- 不允许大规模重写现有架构。
- 不允许在真实账号环境执行测试报名。
- 不允许修改用户的真实 Token 或个人信息。
- 不允许在未验证前宣称功能已经完成。

## 9.2 开发规范

1. 优先复用现有模块。
2. 尽量使用依赖注入，方便 Mock。
3. 对时间、网络请求、重试过程使用可控测试替身。
4. 避免测试依赖真实服务器。
5. 避免测试依赖真实时间长时间等待。
6. 日志统一走 AuditLogger。
7. 统计数据必须有明确来源。
8. 配置项必须有默认值和兼容性处理。
9. 关键状态转换必须有测试。
10. 每个 Phase 完成后检查 Git Diff。

## 9.3 修改范围控制

如果发现需要修改本方案未提及的模块：

1. 先说明原因。
2. 说明与本轮目标的关系。
3. 评估是否存在兼容性影响。
4. 尽可能缩小修改范围。

不能为了追求代码整洁而进行大规模重构。

# 十一、最终完成标准

本轮只有同时满足以下条件才算完成：

- 

  列表接口故障可以正确触发熔断。

- 

  熔断器状态转换正确。

- 

  不完整数据不会恢复服务健康状态。

- 

  UNKNOWN 安全屏障完整有效。

- 

  不会重复提交报名请求。

- 

  程序重启能够恢复未决状态。

- 

  请求审计与实际请求一致。

- 

  提交次数和复核次数分离。

- 

  HTTP 故障统计准确。

- 

  对账失败不会被当成零报名。

- 

  冲突检查降级满足安全条件。

- 

  预热阶段不执行报名。

- 

  全部相关测试通过。

- 

  不存在未说明的高风险问题。

**最终原则：宁可明确告诉用户当前报名结果未知，也不能为了输出一个看起来完整的报告而给出错误的成功或失败结论。**

本轮开发的第一目标不是提高请求频率，而是在服务器异常、网络超时、程序崩溃等情况下，保证报名状态不会失真、不会重复提交、不会发生错误的配额判断。
