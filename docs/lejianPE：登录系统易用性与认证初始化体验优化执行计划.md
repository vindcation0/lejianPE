# lejianPE：登录系统易用性与认证初始化体验优化执行计划

> 项目：lejianPE
>
> 阶段：登录系统产品体验优化
>
> 优先级：P0 → P1 → P2
>
> 目标：在不改变现有认证协议、不破坏现有登录能力的前提下，完善登录失败诊断、一键重新初始化认证、首次配置向导。
>
> 执行方式：分阶段实施，每个阶段独立测试、独立提交。

# 一、项目背景

## 1.1 当前已经具备的能力

根据此前的登录协议研究和 M1 可行性评估，目前项目已经实现：

1. 命令行账号密码输入。
2. 使用已有 signDigital 完成登录。
3. 动态生成 AES 登录信封。
4. 获取 AccessToken 和 RefreshToken。
5. 获取学校及学期信息。
6. state.json 原子保存。
7. Token 自动刷新。
8. DPAPI 凭据加密存储。
9. 认证异常分类。
10. 识别服务端返回的 `50004` 签名错误。
11. 提供 `[b]` 一键重新抓取签名的能力。

当前存在的主要问题不是底层登录能力，而是用户操作体验。

## 1.2 当前用户面临的问题

### 问题一：登录失败后不知道怎么办

例如：

```
登录失败：50004 签名不正确
```

普通用户可能不知道：

- 是密码错误？
- 是签名失效？
- 是 Token 过期？
- 是模拟器状态异常？
- 是否需要重新抓取签名？

### 问题二：重新初始化操作不够连贯

目前虽然存在 `[b]` 一键重新抓取签名功能，但用户仍然需要理解：

- 为什么需要重新抓取。
- 如何启动模拟器。
- 如何完成官方客户端登录。
- 如何完成签名采集。
- 如何确认新凭据有效。
- 是否需要重新登录命令行。

希望将这些步骤整合成完整的引导流程。

### 问题三：首次使用门槛较高

新用户可能不知道：

- 第一次应该执行什么命令。
- 是否需要先安装模拟器。
- 是否需要先登录官方 App。
- 如何生成 credential.json。
- 如何验证登录是否成功。
- 如何进入抢课功能。

因此需要一个完整的首次配置向导。

# 三、第一阶段：登录失败自动诊断

优先级：P0

这是本轮最优先实现的功能。

## 3.1 目标

将底层异常转换成用户能够理解的错误信息。

不能只输出 HTTP 状态码、Python 异常或者服务端原始响应。

## 3.2 统一错误分类

先检查现有 `core/auth_error.py` 和 `core/auth_manager.py`。

尽量复用现有异常类型，不要重新创建一套重复的错误体系。

建议覆盖以下情况：

| 错误类型          | 判断依据                       | 用户提示                     | 建议操作           |
| ----------------- | ------------------------------ | ---------------------------- | ------------------ |
| 签名错误          | 业务码 50004                   | 登录签名可能失效             | 引导重新初始化     |
| 密码错误          | 服务端明确返回密码错误         | 账号或密码不正确             | 检查输入           |
| Token 过期        | Token 生命周期或服务端明确错误 | 登录状态已过期               | 尝试刷新或重新登录 |
| RefreshToken 失效 | 刷新接口明确拒绝               | 会话已失效                   | 重新登录           |
| 网络异常          | DNS、连接超时、断网            | 无法连接服务器               | 检查网络           |
| HTTP 服务器错误   | HTTP 5xx                       | 服务端暂时异常               | 稍后重试           |
| 请求参数错误      | HTTP 4xx 或业务参数错误        | 请求信息不正确               | 检查配置           |
| 信封解密失败      | AES 响应解析失败               | 服务端响应无法解析           | 保存诊断信息       |
| 响应结构异常      | 缺少必要字段                   | 登录响应不完整               | 停止保存会话       |
| 凭据损坏          | 本地凭据无法读取               | 本地认证材料异常             | 引导重新初始化     |
| DPAPI 平台限制    | 非 Windows 环境                | 当前平台不支持此凭据解密方式 | 提示对应平台限制   |
| 未知错误          | 无法分类                       | 登录遇到未知问题             | 提供脱敏诊断报告   |

重要：

不能仅根据 HTTP 200 判断登录成功。

必须同时检查 HTTP 状态、业务状态码、响应解密结果以及必要的 Token 字段。

## 3.3 统一错误输出

建议统一为：

```
========== 登录诊断 ==========

登录结果：失败

错误类型：认证签名错误
服务端代码：50004

可能原因：
1. 登录密码已经修改。
2. 本地 signDigital 已经失效。
3. 客户端认证上下文发生变化。

建议操作：
重新初始化认证凭据。

是否现在重新初始化？

[1] 是，开始重新初始化
[2] 否，返回主菜单
[3] 查看详细诊断信息
```

对于无法确定的错误，必须明确说明原因尚未确定，不允许误导用户。

## 3.4 安全要求

诊断信息禁止包含：

- 明文密码。
- 完整 signDigital。
- AccessToken。
- RefreshToken。
- 完整 credential.json。
- AES 密钥。
- 未脱敏的认证请求体。

可以记录：

- 错误类型。
- HTTP 状态码。
- 业务错误码。
- 时间。
- 请求阶段。
- 脱敏账号标识。
- 客户端版本。
- 诊断 ID。

## 3.5 测试要求

使用 Mock 服务端测试：

1. 50004 签名错误。
2. 明确密码错误。
3. HTTP 401。
4. HTTP 429。
5. HTTP 500。
6. 连接超时。
7. DNS 失败。
8. 响应解密失败。
9. 响应缺少 Token。
10. credential.json 损坏。
11. DPAPI 解密失败。
12. 未知业务错误码。

验收标准：

- 所有已知错误都有明确提示。
- 未知错误能够安全兜底。
- 不记录敏感信息。
- 不因错误诊断自动重复发送登录请求。

# 四、第二阶段：一键重新初始化认证

优先级：P0

## 4.1 目标

复用现有 `[b]` 签名采集能力，整合完整的重新初始化流程。

本阶段不重新开发抓包、签名提取和 AES 信封。

## 4.2 设计统一入口

建议增加：

```
重新初始化认证
```

可以从以下位置进入：

1. 主菜单手动选择。
2. 登录诊断后自动引导。
3. 首次配置向导。
4. 用户主动执行认证修复。

统一调用同一个初始化流程。

## 4.3 初始化步骤

### 步骤一：检查当前状态

检查：

- credential.json 是否存在。
- 当前账号是否存在。
- 当前凭据是否可以解密。
- 是否已有有效 state.json。
- 是否存在其他未完成认证操作。

输出：

```
当前认证状态：

账号：已配置
签名凭据：存在
凭据解密：成功
Token：已过期

可以开始重新初始化。
```

不要展示签名和 Token 原文。

### 步骤二：提示用户准备官方客户端

```
请按照提示完成认证初始化：

1. 确认模拟器已经启动。
2. 打开官方乐健体育 App。
3. 使用当前账号完成正常登录。
4. 等待程序采集登录认证材料。

请勿关闭模拟器。
```

注意：

- 不自动尝试绕过官方客户端认证。
- 不自动输入或保存明文密码。
- 不共享其他用户的认证材料。

### 步骤三：调用现有采集功能

复用现有 `[b]` 流程。

要求：

- 保留现有抓包实现。
- 保留现有签名提取逻辑。
- 复用现有凭据存储。
- 避免重复创建第二套采集工具。

如果采集失败，显示具体失败阶段和下一步建议。

### 步骤四：验证新凭据

新凭据采集完成后，必须先验证。

检查：

1. 文件是否存在。
2. 文件结构是否正确。
3. 凭据是否能够正常解密。
4. 账号是否与当前操作账号一致。
5. signDigital 是否满足已有格式校验。
6. 是否能够通过现有 CLI 登录流程。
7. 是否成功获取 Token。

只有全部通过后，才允许将新凭据正式替换旧凭据。

### 步骤五：安全替换旧凭据

必须采用临时文件和原子替换。

建议流程：

```
当前 credential.json
          |
          v
生成临时认证文件
          |
          v
检查结构与完整性
          |
          v
验证新凭据登录
          |
          v
登录成功？
    /        \
   是         否
   |          |
   v          v
原子替换     删除临时文件
   |          |
   v          v
保留新凭据   保留旧凭据
```

不能先删除旧凭据，再尝试写入新凭据。

如果新凭据验证失败，必须保证原有可用凭据不受影响。

### 步骤六：更新会话

登录成功后：

- 获取 AccessToken。
- 获取 RefreshToken。
- 获取学校信息。
- 获取当前学期。
- 原子保存 state.json。
- 使用现有会话管理模块完成后续初始化。

不得改变现有 state.json 的数据结构。

## 4.4 完成提示

```
========== 认证初始化完成 ==========

账号：认证成功
签名凭据：已更新
AccessToken：获取成功
RefreshToken：获取成功
学校信息：获取成功
当前学期：获取成功

本地凭据：已安全保存
会话状态：已更新

现在可以正常使用 lejianPE。
```

## 4.5 异常回退

必须测试：

- 抓包失败。
- 未获取到签名。
- 凭据格式错误。
- 凭据解密失败。
- 登录返回 50004。
- 登录返回网络错误。
- Token 获取失败。
- 学期信息获取失败。
- state.json 写入失败。

任何失败都不能导致原有有效凭据被破坏。

# 五、第三阶段：首次配置向导

优先级：P1

## 5.1 目标

让从未使用过 lejianPE 的用户能够按照命令行提示完成首次配置。

不要求用户理解认证协议。

## 5.2 首次启动检测

程序启动时检查：

```
credential.json
state.json
本地配置
数据库
```

根据情况决定下一步。

| 当前状态                | 处理方式           |
| ----------------------- | ------------------ |
| 没有任何认证材料        | 进入首次配置       |
| 有凭据，没有 state.json | 执行命令行登录     |
| 有凭据，有 state.json   | 检查登录状态       |
| 凭据无法解密            | 引导重新初始化     |
| state.json 损坏         | 提示恢复或重新登录 |
| 已有有效会话            | 直接进入主菜单     |

注意：

不能仅根据文件存在与否判断认证有效。

必须检查文件结构、凭据解密以及必要的会话状态。

## 5.3 向导流程

建议采用分步骤引导。

### 第一步：欢迎页面

```
================================
欢迎使用 lejianPE

首次使用需要完成认证初始化。

本程序将引导你完成：
1. 环境检查
2. 官方客户端认证
3. 登录凭据初始化
4. 登录验证
5. 学校及学期信息初始化

按回车开始。
================================
```

### 第二步：环境检查

检查：

- Python 版本。
- 操作系统。
- 必要依赖。
- 网络连接。
- 配置目录。
- SQLite 数据库。
- state.json 可写入性。
- 模拟器及 ADB 环境（仅检查需要的部分）。

对于可选环境，不要直接判定为初始化失败。

例如：

如果当前已经有有效 credential.json，就不应该强制要求重新配置模拟器。

### 第三步：账号配置

```
请输入乐健账号：
请输入密码：
```

要求：

- 密码使用 getpass。
- 不回显密码。
- 不写入日志。
- 不写入普通配置文件。
- 不持久化保存明文密码。

如果当前方案需要官方客户端采集签名，应明确告诉用户原因。

### 第四步：认证初始化

调用第二阶段统一初始化流程。

不要在首次配置向导中重复实现签名抓取逻辑。

### 第五步：登录验证

执行：

1. CLI 登录。
2. 响应业务校验。
3. Token 校验。
4. 学校信息获取。
5. 学期信息获取。
6. state.json 保存。

### 第六步：配置完成

```
================================
首次配置完成！

账号认证：成功
学校信息：成功
当前学期：成功
本地会话：已保存

你现在可以：

[1] 查看当前课表
[2] 查看可报名活动
[3] 配置抢课任务
[4] 进入主菜单

================================
```

具体菜单项必须与当前项目真实功能保持一致，不允许凭空增加不存在的功能。

# 六、第四阶段：增加认证诊断命令

优先级：P2

在前三个功能稳定后，再考虑增加独立诊断入口。

建议：

```
python lejian.py --doctor
```

或者复用项目现有 CLI 菜单形式。

## 6.1 诊断内容

| 检查项目        | 检查方式             |
| --------------- | -------------------- |
| Python 环境     | 本地检查             |
| 配置文件        | 本地检查             |
| credential.json | 结构与解密检查       |
| state.json      | 结构检查             |
| SQLite          | 数据库连接检查       |
| Token           | 必要时进行只读验证   |
| RefreshToken    | 根据现有会话逻辑检查 |
| 学期信息        | 只读查询             |
| 网络            | 连接检查             |

诊断过程应尽量只读。

未经用户确认，不允许：

- 重新抓取签名。
- 覆盖凭据。
- 删除 state.json。
- 重置数据库。
- 提交报名请求。

## 6.2 诊断报告

输出：

[√] AccessToken

# 最终原则

这次改造的核心不是让登录系统变得更复杂，而是让它对用户更加友好。

我们已经拥有可用的命令行认证方案。

现在需要做的是：

- 登录失败时告诉用户发生了什么。
- 凭据失效时帮助用户完成修复。
- 首次使用时引导用户完成所有必要配置。
- 出现异常时保护已有凭据和会话。
- 保证所有改进不影响原有抢课业务。

**最终目标：让 lejianPE 的认证系统从「开发者自己会用」，升级为「普通用户按照提示就能使用」。**
