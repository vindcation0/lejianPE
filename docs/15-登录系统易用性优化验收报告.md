### 2.1 核心步骤与安全可靠性设计

1. **步骤一：检查当前认证状态 (`check_status`)**：
   - 只读核查 `credential.json`（是否存在、是否 DPAPI 受保护、是否能正常解密）与 `state.json`（Token 是否过期、学期与学校代码）。
   - **优先开机自检**：调用 `recover_pending_transaction()`，如果检测到上次因异常断电或强杀遗留的未决事务，自动回滚恢复旧凭据与旧会话。
   - 严格脱敏输出，绝不向终端或日志展示明文密钥与签名材料。

2. **步骤二：准备官方客户端提示 (`prompt_client_preparation`)**：
   - 明确提示用户确认模拟器已 Root、启动官方乐健体育 App；
   - 明确标出当前绑定的操作账号（掩码格式），告知用户**必须在 App 中使用该账号登录**，系统会自动执行账号一致性校验。
   - 申明三项安全原则：不绕过官方协议、绝不保存明文密码、验证完全通过后才原子替换。

3. **步骤三：从抓包日志提取认证材料 (`extract_from_flows`)**：
   - 复用现有 `login_envelope.unwrap` 与抓包日志解析逻辑，提取 `account`, `signDigital`, `entrance`。
   - 若未检索到成功的登录记录，抛出 `InvalidCredentialError`，友好提示用户检查 App 登录操作。

4. **步骤四：严格验证新凭据 (`verify_new_credential`)**：
   - **账号一致性强校验（防串号污染）**：若本地已有配置账号，核验采集到的账号是否完全一致。如果用户在模拟器中误登了他人的账号，立即触发安全拦截，抛出明确错误并拒绝采纳，**杜绝误用他人账号污染本地配置**！
   - **在线真实登录核验**：调用 `AuthManager.login` 发起请求，确保新签名的有效性。若返回 50004、密码错误、网络超时或缺少 Token，立即拦截。
   - **只有校验全部通过，才允许进入落盘替换阶段**。

5. **步骤五：开启带预写事务日志 (WAL) 的跨文件复合事务并原子替换旧凭据 (`begin_transaction` + `apply_new_credential_atomically`)**：
   - 开启跨文件复合事务：旧凭据以二进制镜像落盘备份为 `credential.json.tx_bak`；旧会话在 Windows 下通过 `dpapi_protect` 加密封装为 `state.json.tx_bak`（杜绝明文 Token 裸露）；
   - 备份文件落盘经由 `flush` + `fsync` 确保真实写入介质，并显式设置安全访问权限 (DACL / 0o600)；
   - 事务日志先行落盘（Write-Ahead Logging）：原子写入 `credential.json.tx.json`（状态 `INITIALIZED`）并 `fsync`；
   - 凭据通过 `.tmp` 临时文件写入、`fsync`、回读校验及 DPAPI 加密比对，随后通过 `os.replace` 原子替换；
   - 写入成功后，立即更新事务日志状态为 `CRED_APPLIED` 并强制 `fsync` 落盘，确保状态领先于下一步动作。

6. **步骤六：拉取学期上下文并原子更新会话 (`update_session_atomically`)**：
   - 验证成功后通过 `AuthManager.save_state_atomically` 拉取当前学期，以原子方式更新 `state.json` 并显式设置权限；
   - **关键回滚屏障（保证复合操作整体一致性）**：若拉取学期或写入 `state.json` 发生任何异常（如网络中断 502、解析失败），**立即触发 `rollback_transaction()`**，将步骤 5 已经替换的凭据自动还原，恢复旧凭据与旧会话，绝不留下「新凭据对应旧会话」的不一致状态！

7. **步骤七：复合事务提交与完成确认 (`commit_transaction`)**：
   - 凭据与会话两个文件均成功安全落地后，标记事务完成；
   - 清理 `.tx_bak` 备份文件与 `.tx.json` 事务日志文件；
   - 打印清晰的就绪状态横幅与当前学期信息。

## 三、文件安全性与权限控制机制详细评估

针对审查中发现的敏感 Token 保护与 Windows DACL 权限问题，进行了全方位加固与实测修正：

### 3.1 `state.json` 存储现状与备份保护
- **现状分析**：`state.json` 包含 `accessToken`、`refreshToken`、`mobile`、`realName` 等字段，由于业务模块（选课、查课表、自动刷新）需要高频直接读取，其原文件为标准 JSON 格式。
- **备份安全隐患消除**：在执行重新初始化事务备份时，如果直接明文复制会造成磁盘上出现多份明文 Token。为此在 `AuthInitializer._backup_file_securely` 中引入 **DPAPI 密文包装保护**：
  - 在 Windows 环境下，读取 `state.json` 二进制内容后，立即调用 `dpapi_protect` 加密为密文；
  - 将密文打包为结构化受保护容器落盘（`backupType: "DPAPI_PROTECTED_STATE_BACKUP"`，密文经 Base64 编码保存）；
  - **即使他人直接打开 `state.json.tx_bak`，也仅能看到乱码密文字符串，绝对无法窃取明文 AccessToken / RefreshToken**；
  - 回滚时，`_restore_file_securely` 自动调用 `dpapi_unprotect` 解密还原出原有的明文 JSON 结构。

### 3.2 纠正 DACL 权限继承结论：引入显式访问控制强化
- **结论纠偏**：Python 的 `shutil.copy2` 仅复制文件数据与常规元数据（如修改时间），**不会完整复制 Windows ACL / DACL**。在 Windows NTFS 下，创建的新文件或普通复制文件默认继承目标父目录的 DACL。若系统环境或父目录权限存在宽松配置，新生成文件将存在越权访问风险。
- **显式权限加固实现 (`secure_file_permissions`)**：
  - **Windows 系统**：调用 Windows 内置安全管理工具 `icacls`，执行：
    ```cmd
    icacls <filepath> /inheritance:r /grant:r "%USERNAME%:(F)" /grant:r "SYSTEM:(F)" /grant:r "Administrators:(F)"
    ```
    强制移除继承权限（`/inheritance:r`），显式将文件完全控制权（`(F)`）严格限定为当前登录用户（`%USERNAME%`）以及特权系统账户（`SYSTEM`、`Administrators`），彻底拒绝同机器上其他非受信本地用户或沙箱用户组（如 `CodexSandboxUsers`、`Guests`）的读取权限！
  - **POSIX 系统**：调用 `os.chmod(filepath, 0o600)`，仅允许文件所有者读写。
  - **覆盖范围**：所有敏感凭据（`credential.json`）、会话（`state.json`）、临时文件（`*.tmp`）、事务日志（`*.tx.json`）及事务备份（`*.tx_bak`）在落盘时均强制应用显式权限加固。

### 3.3 事务清理策略与免责说明
- **清理事务文件 (Unlink)**：在事务成功提交（Commit）或完全回滚（Rollback）后，程序调用 `os.remove()` 清理 `.tx_bak` 备份文件与 `.tx.json` 日志文件。
- **客观技术声明**：常规文件系统 `unlink` 操作是将文件在目录项中解挂并标记其占用的数据块为可用，受底层操作系统调度、文件系统元数据日志及固态硬盘（SSD）FTL / TRIM 垃圾回收机制支配。**此机制保证了操作系统逻辑层面的文件清理，但不等同于物理磁盘上的安全擦除（Secure Erase）**。程序严格做到不留存未受保护的明文敏感数据，并最小化文件存续时间。

## 四、真实异常断电可靠性与抗二次中断设计 (Reliability & WAL)

针对审查中指出的异常断电恢复可靠性，系统从以下五个维度构建了防护机制：

### 4.1 持久化落盘与预写日志 (WAL)
- **严格落盘 (`_write_and_sync_bytes`)**：所有文件写入操作在关闭前必须显式调用 `f.flush()` 与 `os.fsync(f.fileno())`，穿透操作系统页缓存，确保数据真实持久化至物理存储介质，随后再通过 `os.replace` 原子替换；
- **目录元数据同步 (`_sync_parent_dir`)**：替换完成后，在支持的 POSIX 平台上尝试对父目录文件描述符执行 `os.fsync`，确保目录项变更持久化（Windows 下安全忽略）；
- **WAL 状态先行**：
  1. 旧凭据与旧会话备份（`*.tx_bak`）**完全持久化并落盘**；
  2. 事务日志写入并持久化（`status = "INITIALIZED"`）；
  3. 推进步骤 5 替换凭据；
  4. 事务日志状态更新并持久化（`status = "CRED_APPLIED"`）；
  5. 推进步骤 6 更新会话。
  保证若在任意时刻发生断电，磁盘上只要存在事务记录，其引用的备份文件必定已在磁盘上完整可用，绝不存在“日志记录了备份但备份尚未写入物理介质”的竞态漏洞。

### 4.2 幂等回滚与抗二次断电中断
- **回滚幂等性**：多次连续调用 `rollback_transaction()` 绝不抛出异常。首次调用完成还原并清理事务，后续调用安全返回 `False`；
- **抗恢复中途中断**：在执行回滚还原时，**不提前删除备份文件**（`_restore_file_securely` 先将备份解密并原子写回原文件，保留备份仍在磁盘）。只有当凭据与会话两方文件均已完全处于恢复就绪状态后，最后才调用 `commit_transaction()` 清理备份与日志；
- **二次中断自愈能力**：若在回滚凭据之后、恢复会话之前发生二次断电，下次开机时 `recover_pending_transaction()` 再次触发，因事务日志与会话备份依然完整存留，自检程序将继续平滑自愈并最终完成清理（已由 `I20` 专项测试实测通过）。

## 六、统一入口集成协同

为方便用户在各个场景下无缝发起重新初始化，M2 提供了四大统一入口调用：
1. **主菜单集成**：`menu.py` 中的 `[b]` 项更新为 `重新初始化认证（一键修复凭据与会话）`，直接调用 `lejian.py reinit`。
2. **命令行入口**：`lejian.py` 新增 `reinit` 子命令，支持直接在终端运行 `python lejian.py reinit`。
3. **登录失败诊断自动引导**：`core/auth_diagnostics.py` 的 `handle_login_failure` 在用户选择 `[1] 是，开始重新初始化认证凭据` 时，直接触发 `AuthInitializer().reinitialize()`。
