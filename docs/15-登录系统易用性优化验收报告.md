### 2.1 核心步骤与安全机制设计

1. **步骤一：检查当前认证状态 (`check_status`)**：
   - 只读核查 `credential.json`（是否存在、是否 DPAPI 受保护、是否能正常解密）与 `state.json`（Token 是否过期、学期与学校代码）。
   - **优先开机自检**：调用 `recover_pending_transaction()`，如果检测到上次因异常断电或强杀遗留的未决事务，自动回滚恢复旧凭据与旧会话。
   - 严格脱敏输出，绝不向终端或日志展示明文密钥与签名材料。

2. **步骤二：准备官方客户端提示 (`prompt_client_preparation`)**：
   - 明确提示用户确认模拟器已 Root、启动官方乐健体育 App；
   - 明确标出当前绑定的操作账号（掩码格式），告知用户**必须在 App 中使用该账号登录**，系统会自动执行账号一致性校验。
   - 申明三项安全原则：不绕过官方协议、绝不保存明文密码、验证完全通过后才原子替换。

3. **步骤三：从抓包日志提取认证材料 (`extract_from_flows`)**：
   - 复用现有 `login_envelope.unwrap` 与抓包日志解析逻辑，提取 `account`, `signDigital`, `entrance`。
   - 若未检索到成功的登录记录，抛出 `InvalidCredentialError`，友好提示用户检查 App 登录操作。

4. **步骤四：严格验证新凭据 (`verify_new_credential`)**：
   - **账号一致性强校验（防串号污染）**：若本地已有配置账号，核验采集到的账号是否完全一致。如果用户在模拟器中误登了他人的账号，立即触发安全拦截，抛出明确错误并拒绝采纳，**杜绝误用他人账号污染本地配置**！
   - **在线真实登录核验**：调用 `AuthManager.login` 发起请求，确保新签名的有效性。若返回 50004、密码错误、网络超时或缺少 Token，立即拦截。
   - **只有校验全部通过，才允许进入落盘替换阶段**。

5. **步骤五：开启跨文件复合事务并原子替换旧凭据 (`begin_transaction` + `apply_new_credential_atomically`)**：
   - 开启两阶段复合事务，将当前的 `credential.json` 与 `state.json` 制作独立隔离镜像备份（`.tx_bak`）；
   - 写入事务状态记录文件（`.tx.json`，初始状态 `INITIALIZED`）；
   - 复用 `CredentialStorage.save_credential`，写入 `.tmp` 临时文件，执行回读校验与 Windows DPAPI 往返解密比对，随后通过 `os.replace` 原子替换；
   - 更新事务日志状态为 `CRED_APPLIED`。

6. **步骤六：拉取学期上下文并原子更新会话 (`update_session_atomically`)**：
   - 验证成功后通过 `AuthManager.save_state_atomically` 拉取当前学期，以事务方式原子更新 `state.json`；
   - **关键回滚屏障（解决复合原子性缺陷）**：若拉取学期或写入 `state.json` 发生异常（如网络中断 502、解析失败），**立即触发 `rollback_transaction()`**，将步骤 5 已经替换的凭据从 `.tx_bak` 自动还原，恢复旧凭据与旧会话，绝不留下「新凭据对应旧会话」的不一致状态！

7. **步骤七：复合事务提交与完成确认 (`commit_transaction`)**：
   - 凭据与会话两个文件均成功安全落地后，标记事务完成；
   - 安全删除 `.tx_bak` 备份文件与 `.tx.json` 事务日志文件；
   - 打印清晰的就绪状态横幅与当前学期信息。

## 三、凭据与备份文件安全性评估报告

针对备份文件可能带来的安全风险，进行了专门的安全审查与防护固化：

### 3.1 DPAPI 密文保护一致性
- **零明文泄露**：备份操作（无论是 `CredentialStorage` 的 `.bak` 还是事务管理器 `AuthInitializer` 的 `.tx_bak`）均使用 Python 标准库的 `shutil.copy2` 进行底层物理字节级复制。
- **密文原样保留**：在 Windows DPAPI 保护模式下，`credential.json` 磁盘存储的原本就是经过 `CryptProtectData` 加密并 Base64 编码的密文字符串；备份过程不调用解密接口，因此备份文件中的密钥内容与原文件一样，**100% 保持为 DPAPI 密文**，绝对不发生明文降级。

### 3.2 权限隔离与反篡改
- `shutil.copy2` 会自动继承原凭据文件的安全属性与 Windows DACL 权限，非系统当前登录用户无法访问；
- 即使物理复制 `.bak` 或 `.tx_bak` 到其他计算机或其他 Windows 用户账户下，调用 DPAPI 的 `CryptUnprotectData` 也会因缺少当前用户的 Session 主密钥而直接报错拒绝（`NTE_BAD_KEY_STATE`）。

### 3.3 严格的单备份保留与生命周期清理策略
- **禁止多版本膨胀**：系统采用固定单备份路径（`credential.json.bak` 以及事务期间的 `*.tx_bak`），绝不自动产生递增编号的 `.bak.1`、`.bak.2` 等无管控的历史旧备份。
- **用后即焚的事务备份**：事务产生的 `.tx_bak` 与 `.tx.json` 仅在重新初始化期间存续。事务成功提交（Commit）或失败回滚（Rollback）时，均会调用 `commit_transaction()` 立即将其彻底删除（`unlink`），磁盘不留冗余敏感镜像。

### 3.4 仓库版本控制安全屏障
在项目根目录 `.gitignore` 中，已显式固化对凭据、备份及事务文件的全面屏蔽：
```gitignore
# ===== 凭据安全：绝对不要提交 =====
state.json
state.json.*
credential.json
credential.*
!credential.example.json
credentials/
*.key

# 临时与备份产物
*.tmp
*.bak
*.tx.json
*.tx_bak
```
确保无论在任何情况下，凭据文件、备份文件以及事务状态文件都不会被 git 追踪或误提交到代码仓库。
