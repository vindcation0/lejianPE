## 一、改进维度对比一览表

| 维度 | 改进前 (2026-10-25 实战状态) | 改进后 (本次可靠性工程实施后) | 解决的痛点 / 效果 |
| :--- | :--- | :--- | :--- |
| **报名状态管理** | 内存变量 `week_done` / `last_try`，仅简单布尔值判断 | 引入 SQLite 状态机持久化 (`registration_records`)，7 状态生命周期 | 状态跨进程、跨重启持久保留，具备 ACID 事务保护 |
| **结果判定信度** | 依赖单次 HTTP 状态码；502/503 或超时直接误判为失败 | 明确区分成功/失败/未知；遇到 5xx/超时进入 `UNKNOWN` 并**立即通过 `isRegister` 复核** | 彻底消除「服务端已扣名额，客户端以为失败而盲目重复提交」的问题 |
| **重试行为边界** | 失败后间隔固定轮询立即重新提交 | **UNKNOWN 绝对禁止自动重试**；仅在服务端确认未报且活动有效时才标记 `RETRYABLE` | 避免因网络抖动和服务器过载造成的雪崩放大效应 |
| **多进程并发控制** | 无单实例保护，旧进程与应急脚本并发运行造成突破每周上限 | 引入 Windows 操作系统级文件锁 (`msvcrt.locking`)，覆盖提交与恢复 | 确保全局只能运行一个抢课进程，杜绝多进程并发并发超额 |
| **请求层抽象** | 所有接口使用通用 `_request()`，缺乏职责区分 | 明确区分**查询请求** (`request_query`) 与**提交请求** (`submit_once`) | 查询可安全重试与退避，有副作用的提交严格执行单次与复核 |
| **服务过载退避** | 仅依赖固定间隔睡眠，过载时高频冲击服务端 | 引入系统健康状态 (`NORMAL`/`DEGRADED`/`RECOVERING`) 与指数退避 + 抖动 | 服务端 5xx 或超时自适应降低频率，支持 HTTP 429 `Retry-After` 遵从 |
| **异常崩溃恢复** | 进程退出后内存状态全失，重启盲目从零开始 | `RecoveryManager` 在启动时扫描未决记录，自动向服务端对账核实 | 即使提交中途掉电/崩溃，重启也能准确定位并恢复真实状态 |
| **最终结果核对** | 仅靠人工事后探测与手工退课 | `ReconciliationManager` 在满额与结束时自动核实实际 `isRegister` 分布 | 自动检测超额报名并发出显著告警，主动阻断后续提交，引导人工确认退课 |
| **请求审计与可观测性**| 仅有控制台文本 log，故障时段请求难追溯 | 独立 JSONL 审计文件 (`requests-YYYYMMDD.jsonl`)，全程敏感信息脱敏 | 完整记录每一次操作起止毫秒、状态码、复核结果、尝试次数与错误信息 |
| **测试与验证体系** | 无单元测试，需依赖真实开抢环境或直接调校外接口 | 独立自动化测试套件 (`tests/test_reliability.py`)，15 个模拟场景 | 无需真实 Token 和网络即可验证所有极端异常与并发分支 |

## 二、核心架构升级详解

### 2.1 状态机模型与流转规则

```
                      [发现目标活动]
                            │
                            ▼
                    检查本地持久化状态
                            │
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
已存在 SUCCESS 记录                        无记录 / 已标记 RETRYABLE
 (直接阻断，禁止提交)                              │
                                                ▼
                                        写入本地 SUBMITTING
                                                │
                                                ▼
                                         发送提交请求 (POST)
                                                │
                 ┌──────────────────────────────┼──────────────────────────────┐
                 ▼                              ▼                              ▼
          HTTP 200 (业务成功)            HTTP 200 (业务拒绝)            HTTP 5xx / 超时 / 异常
                 │                              │                              │
                 ▼                              ▼                              ▼
             SUCCESS                         FAILED                         UNKNOWN
                                                                               │
                                                                               ▼
                                                                     写入 VERIFYING 状态
                                                                               │
                                                                               ▼
                                                                  向服务端查询 isRegister 复核
                                                                               │
                                                ┌──────────────────────────────┴──────────────────────────────┐
                                                ▼                                                             ▼
                                       isRegister == True                                            isRegister == False
                                                │                                                             │
                                                ▼                                                             ▼
                                             SUCCESS                                            重新校验资格与窗口
                                      (确认虽报网关异常但已成功)                                                │
                                                                                ┌─────────────────────────────┴─────────────────────────────┐
                                                                                ▼                                                           ▼
                                                                            合规有效                                                    已失效/超限
                                                                                │                                                           │
                                                                                ▼                                                           ▼
                                                                            RETRYABLE                                                    FAILED
```

### 2.2 启动恢复时序 (Crash Recovery)

当程序在提交中途崩溃（状态停留在 `SUBMITTING`、`UNKNOWN` 或 `VERIFYING`）时：
1. 程序下次启动，`RecoveryManager` 首先读取 SQLite 中未决状态记录；
2. 针对每个未决记录，调用 `getActivityList` 请求服务端真实活动数据；
3. 若列表中查得目标活动且 `isRegister = true`，自动更新为 `SUCCESS`；
4. 若列表中查得目标活动且 `isRegister = false`，更新为 `RETRYABLE`，重置 attempts；
5. 若服务端接口异常或列表未返回目标活动，继续维持 `UNKNOWN`，严禁擅自判定未报名。

### 2.3 操作系统级单实例锁

- 采用 `msvcrt.locking(fileno, msvcrt.LK_NBLCK, 1)`（Windows）与 `fcntl.flock`（POSIX 降级备用）；
- 锁文件写入当前进程 PID (`data/grab.lock`)；
- 当另一个抢课进程试图启动时，系统调用直接返回拒绝，程序输出告警并安全退出；
- 进程正常退出、Ctrl+C、被任务管理器杀死或机器掉电时，操作系统内核会自动释放文件句柄所持有的字节锁，绝不会因为留下 `.lock` 文件而导致以后再也打不开。

## 三、实战演练与测试套件验证结果

自动化测试套件位于 `tests/test_reliability.py`，完整覆盖《实施流程报告》第 4.14 节的所有场景：

| 用例编号 | 测试场景说明 | 注入条件 | 预期与实测结果 | 状态 |
| :--- | :--- | :--- | :--- | :--- |
| **T01** | 正常报名成功 | HTTP 200, code=0, success=true | 状态流转为 `SUCCESS`，写入 attempts=1 | ✅ PASS |
| **T02** | 提交 503 但服务端已成功 | signUp 返回 503，复核 `isRegister=true` | 成功复核，状态流转为 `SUCCESS` | ✅ PASS |
| **T03** | 提交超时且复核也超时 | signUp 超时 (-1)，复核超时抛异常 | 状态保持为 `UNKNOWN`，拒绝进入重试 | ✅ PASS |
| **T04** | 提交 503 且复核确认未报 | signUp 返回 503，复核 `isRegister=false` | 状态流转为 `RETRYABLE`，允许重新评估 | ✅ PASS |
| **T05** | 复核活动列表缺失目标活动 | signUp 超时，复核列表无目标活动 | 状态保持为 `UNKNOWN`，不误判未报 | ✅ PASS |
| **T06** | 两个抢课进程并发启动 | 两个 `InstanceLock` 竞争同一锁文件 | 实例 1 获取成功，实例 2 被拒并报错 | ✅ PASS |
| **T07** | 报名成功后程序崩溃 | 本地已有 SUCCESS，重启后重试 | 状态恢复 SUCCESS，阻断后续网络提交 | ✅ PASS |
| **T08** | 提交中途崩溃恢复 | 状态停在 SUBMITTING，重启对账 | 启动复核识别已报名，恢复为 SUCCESS | ✅ PASS |
| **T09** | 连续查询失败退避 | 模拟连续 500/502 错误 | 状态转入 DEGRADED，指数增加延时 | ✅ PASS |
| **T10** | 收到 HTTP 429 限流 | 返回 429 并携带 Retry-After=3.0 | 分类为 RATE_LIMITED，退避 3.0s | ✅ PASS |
| **T11** | 抢到第三节超额告警 | 服务端已报 3 节同一周活动 | 全局核对报 `exceeded=True` 并告警阻断 | ✅ PASS |
| **T12** | 重复运行防重提交 | 活动状态已是 SUCCESS | 直接跳过，模拟器提交接口调用次数为 0 | ✅ PASS |
| **T13** | SQLite 写入失败防护 | 模拟磁盘满或 SQLite 无法写入 | 抛出 StateStoreError，阻断无状态提交 | ✅ PASS |
| **T14** | Token 过期自动刷新 | 首次返回 401，后续返回 200 | 触发 client.refresh() 并自动重试成功 | ✅ PASS |
| **T15** | 报名时间窗口已关闭 | 活动 endRegisterTime 早于当前时间 | 规则回调校验拒绝，禁止发起提交请求 | ✅ PASS |
