# 乐健体育项目——统一时间占用数据结构改造执行说明

**任务类型：** 数据模型重构
**优先级：** P0
**改造范围：** 课表数据结构、解析结果标准化、时间冲突判断的数据读取兼容
**暂不涉及：** PDF、PNG、OCR、AI 课表识别

## 一、项目需求重新定义

### 1.1 核心需求

本项目不需要完整的课程管理功能。

抢课程序只需要判断：

**某个体育活动在指定日期和时间举行时，用户是否存在课程冲突。**

因此，我们不关心：

- 课程名称
- 教师姓名
- 教室
- 学分
- 课程类型
- 教学班级

我们真正关心：

1. 星期几。
2. 开始时间。
3. 结束时间。
4. 课程在哪些教学周有效。

本次需要将原来的 Course（课程）数据模型，调整为 TimeSlot（时间占用段）数据模型。

### 1.2 设计原则

1. 只保存冲突判断所必需的信息。
2. 不保留没有实际用途的课程元数据。
3. 所有输入格式最终转换为统一的数据结构。
4. 时间统一使用 24 小时制。
5. 星期统一使用数字表示。
6. 周次信息必须保留。
7. 数据结构必须能够兼容原有课表。
8. 不允许因为数据结构调整而改变现有抢课业务规则。

## 二、统一数据结构设计

### 2.1 新版 JSON 结构

建议将原有 `timetable.json` 调整为：

```
{
  "schema_version": 2,
  "week1_monday": "2026-08-31",
  "busy_slots": [
    {
      "weekday": 1,
      "start": "08:00",
      "end": "09:35",
      "weeks": [[1, 16]]
    },
    {
      "weekday": 2,
      "start": "10:00",
      "end": "11:35",
      "weeks": [[1, 8]]
    },
    {
      "weekday": 3,
      "start": "14:00",
      "end": "15:35",
      "weeks": [[2, 16]]
    }
  ]
}
```

### 2.2 字段定义

| 字段           | 类型    | 说明                 |
| -------------- | ------- | -------------------- |
| schema_version | Integer | 数据结构版本         |
| week1_monday   | String  | 第一教学周的周一日期 |
| busy_slots     | Array   | 所有时间占用记录     |
| weekday        | Integer | 星期，1=周一，7=周日 |
| start          | String  | 开始时间，HH         |
| end            | String  | 结束时间，HH         |
| weeks          | Array   | 有效教学周区间       |

### 2.3 周次表示

继续使用现有区间表达方式：

```
"weeks": [[1, 16]]
```

表示第 1-16 周每周都有课。

```
"weeks": [[1, 8]]
```

表示第 1-8 周有课。

```
"weeks": [[1, 8], [10, 16]]
```

表示第 1-8 周和第 10-16 周有课。

单双周需要转换成明确的周次集合或单周区间，例如：

```
"weeks": [[1, 1], [3, 3], [5, 5], [7, 7]]
```

表示第 1、3、5、7 周有课。

所有周次区间均为包含起止周的闭区间。

不允许因为无法识别单双周而擅自默认为每周都有课。

## 三、时间占用数据模型的约束

### 3.1 星期

只允许：

- 1：周一
- 2：周二
- 3：周三
- 4：周四
- 5：周五
- 6：周六
- 7：周日

### 3.2 时间

统一使用：

```
HH:MM
```

例如：

```
08:00
09:35
14:00
```

必须满足：

- 时间格式合法。
- 开始时间早于结束时间。
- 不允许缺少开始或结束时间。
- 暂不支持跨午夜课程。

### 3.3 周次

必须满足：

- 周次大于等于 1。
- 起始周不能大于结束周。
- 周次不能超出配置的教学周范围。
- 不允许空周次集合。
- 不允许无法确定有效周次的数据直接进入正式课表。

### 3.4 时间段重复

如果两条记录表示完全相同的星期、时间和周次，可以去重。

如果时间段重叠，应检查是否属于重复识别。

不要简单合并所有重叠时间段，必须确保合并后不改变原来的有效周次。

## 四、学校课时配置

不同学校的课程节次时间可能不同。

需要支持学校自定义课时配置。

例如：

```
{
  "period_times": {
    "1": ["08:00", "08:45"],
    "2": ["08:50", "09:35"],
    "3": ["09:55", "10:40"],
    "4": ["10:45", "11:30"]
  }
}
```

如果原始课表提供的是：

```
周一，第1-2节
```

解析器应根据学校配置转换为：

```
{
  "weekday": 1,
  "start": "08:00",
  "end": "09:35"
}
```

要求：

1. 节次映射配置不能写死在解析器中。
2. 不同学校可以使用不同课时配置。
3. 原始文件直接提供具体时间时，优先使用原始时间。
4. 只有节次、没有具体时间时，才使用 period_times。
5. 没有课时配置时，不允许自行猜测时间。

最终 `busy_slots` 只保存具体开始和结束时间，不需要额外保存节次编号。

## 五、原有数据兼容与迁移

这是本次改造的重要内容。

当前项目可能存在以下旧版结构：

```
{
  "week1_monday": "2026-08-31",
  "courses": [
    {
      "name": "高等数学",
      "weekday": 1,
      "start": "08:00",
      "end": "09:35",
      "weeks": [[1, 16]]
    }
  ]
}
```

需要实现旧版到新版的转换：

```
courses
   |
   v
读取 weekday
   |
   v
读取 start / end
   |
   v
读取 weeks
   |
   v
忽略 name、teacher 等非必要字段
   |
   v
生成 busy_slots
```

具体要求：

1. 读取旧版 `courses`。
2. 提取时间占用信息。
3. 转换成新版 `busy_slots`。
4. 保留原来的 `week1_monday`。
5. 新版结构增加 `schema_version`。
6. 不允许丢失有效的时间和周次信息。
7. 原始文件必须备份。
8. 迁移失败不能覆盖旧版文件。

所有现有读取 `timetable.json` 的代码都需要检查。

如果仍有旧模块依赖 `courses`，应增加统一兼容读取层，或者同步调整调用方。

不要让不同模块分别实现一套转换逻辑。

## 六、课表冲突判断逻辑

新版数据结构最终服务于课程冲突判断。

需要检查当前项目的冲突判断函数，保证其能够使用 `busy_slots`。

判断逻辑：

### 6.1 日期转换

通过 `week1_monday` 计算指定日期对应的教学周。

例如：

```
week1_monday = 2026-08-31
activity_date = 2026-09-07
```

对应第 2 教学周。

### 6.2 星期判断

体育活动日期的星期必须与时间占用记录的 weekday 相同。

### 6.3 周次判断

当前活动日期对应的教学周必须包含在 `weeks` 中。

### 6.4 时间重叠判断

使用标准时间区间重叠判断：

```
activity_start < slot_end and activity_end > slot_start
```

如果成立，则存在时间冲突。

### 6.5 最终判断

只有同时满足：

1. 星期相同。
2. 教学周匹配。
3. 时间段重叠。

才能认定存在课程冲突。

注意：不允许只根据星期和时间判断而忽略周次。

## 七、解析器改造要求

本阶段只处理统一数据结构，不开发新的多格式识别能力。

保留现有 Markdown 导入方式。

需要将现有 Markdown 解析结果转换成 `busy_slots`。

例如原始 Markdown：

```
| 课程名称 | 星期 | 时间 | 周次 |
|---|---|---|---|
| 高等数学 | 周一 | 08:00-09:35 | 1-16周 |
| 大学英语 | 周二 | 10:00-11:35 | 单周 |
```

最终输出：

```
{
  "schema_version": 2,
  "week1_monday": "2026-08-31",
  "busy_slots": [
    {
      "weekday": 1,
      "start": "08:00",
      "end": "09:35",
      "weeks": [[1, 16]]
    }
  ]
}
```

课程名称仅用于解析输入时定位记录，不进入最终数据结构。

如果当前 Markdown 格式没有提供课程名称以外的有效时间信息，不允许自行推断。

本阶段不要求支持所有学校的 Markdown 排版。

## 八、数据校验模块

建议增加独立的 validator。

校验内容：

1. schema_version 是否支持。
2. week1_monday 是否为合法日期。
3. busy_slots 是否为数组。
4. weekday 是否在 1-7 范围内。
5. start 是否为合法时间。
6. end 是否为合法时间。
7. start 是否早于 end。
8. weeks 是否为合法区间。
9. 是否存在重复记录。
10. 是否存在无法确定的课程时间。

如果校验失败：

- 明确输出错误位置。
- 指出具体哪个字段存在问题。
- 禁止覆盖现有 timetable.json。
- 不允许静默忽略错误记录。

## 十二、最终验收标准

完成后必须满足：

- 最终数据结构只保存冲突判断所需的时间占用信息。
- 不再依赖课程名称进行冲突判断。
- 不再依赖教师姓名进行冲突判断。
- 星期、开始时间、结束时间、教学周次完整。
- 原有 Markdown 导入仍然可用。
- 原有 timetable.json 能够安全迁移。
- 原有抢课业务过滤规则保持不变。
- 现有冲突判断结果与旧版本一致。
- 所有测试通过。
- 更新 README 和数据结构文档。

**最终目标：把课表从「课程信息集合」简化为「个人时间占用集合」，让后续任何格式的课表都只需要负责提取时间占用信息，而不需要理解和管理课程本身。**
