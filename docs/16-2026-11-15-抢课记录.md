## 四、本次暴露的 5 个问题

### 问题 1：Preflight 在服务器故障时必然阻断

**现象**

```
[FAIL] snapshot [P0核心] : 活动列表快照不完整 (complete=False)，禁止依据残缺数据进行决策 (P07)
```

**影响**：开抢窗口内服务器必然不健康，于是程序**永远无法启动**。

**本质**：一个"健康检查"把"已知不健康但必须工作"的场景判成了禁止启动。

**本次处置**：新增环境变量 `LJ_SKIP_PREFLIGHT=1` 覆盖阻断。

**建议**：开抢模式应默认允许降级启动，只在日志里标记 `DEGRADED`。

---

### 问题 2：熔断器参数不适合开抢窗口

**现象**

```
[熔断: OPEN, 失败计数: 3/3]，退避 8.21 秒
[熔断保护] OPEN 熔断冷却中，剩余 16.58 秒
```

轮询退化为 **37 秒一次**。

**根因**：`CircuitBreaker(failure_threshold=3, base_cooldown=2.0, max_cooldown=30.0)`。

**本次处置**：改为 `threshold=20, base_cooldown=1.0, max_cooldown=3.0`。

**理由**：开抢窗口内 3 次失败是常态（服务器本来就挂），
熔断的意义是防雪崩，不是防"正常的高失败率"。

---

### 问题 3：重试退避上限仍限制频率

**现象**：熔断放宽后，轮询仍被 `RetryPolicy(base_delay=0.5, max_delay=8.0)` 卡在 **8 秒一次**。

**本次处置**：改为 `base_delay=0.4, max_delay=1.5`，实测轮询提升到 **1.6 秒一次**。

**效果**：从 37 秒 → 8 秒 → 1.6 秒，数量级改善。

---

### 问题 4：名额计数把 RETRYABLE 算成"已占"

**现象**

```
>>> 成功！第12周 已报 1/2
本周 2 节名额已满，开始最终全局对账…
确认报名成功：1 节
```

**矛盾**：报告自己写着 1/2，却判定"2 节已满"并退出。

**根因推测**：本地状态库里有 4 条 `RETRYABLE` 记录，
配额计算把它们当作"可能已占用"，于是 1 + 4 ≥ 2。

**影响**：**直接导致本次只抢到 1 节**。如果不提前退出，14:14:30 到 14:16:36
之间仍有机会抢到第 2 节（当时确实还有 4 个余量）。

**这是本次最严重的问题。**

**建议**：配额计算应只统计 `SUCCESS` + `UNKNOWN`，
`RETRYABLE` 不应占用名额；或至少在退出前做一次强制复核。

---

### 问题 5：快照过期守卫产生大量无效阻断

**现象**：14:13:36–14:14:28 之间，日志刷满

```
[FAILED] 规则校验未通过: 本地数据不完整安全阻断:
本地数据获取后状态发生变化 (活动 ... 于 14:13:36.749 发生状态变更)，必须重新刷新数据
```

**统计**：`candidate_rejected: 146`、`local_conflict_check_blocked: 146`。

**分析**：任何一次状态变化（哪怕是我们自己的失败响应）都会让整个候选池失效。
在服务器抖动期，快照几乎每秒都在"变化"，
于是**每一次尝试都被自己的守卫拦下**。

**这是保守设计的副作用**：为了防"用陈旧数据决策"，
结果在快照本来就无法稳定时完全无法行动。

**建议**：区分"数据真的变了"与"我们自己的请求导致了变更"；
或允许在时间窗口内用带版本号的快照做决策。

## 五、一个需要说明的统计异常

事件日志里 `submission_succeeded: 2`，但服务端只确认 **1 节**。

可能原因：

1. 同一个活动被重复提交，第二次返回幂等成功
2. 一次成功响应实际未落地（网关回包与写库不一致）

**与 10-25 的教训一致**：响应码不可信，**只有 `isRegister` 是事实**。

建议后续在 `submission_succeeded` 事件里带上 activityId，
便于与对账结果逐条比对。
