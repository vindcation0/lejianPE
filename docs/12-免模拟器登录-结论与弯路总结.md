# 免模拟器命令行登录：结论与弯路总结

> 本文回答一个问题：**现在这套东西，到底算不算"真正不依赖模拟器"？**
> 以及为了达到这一步，走过哪些死路。
>
> 阅读顺序建议：先看第 0、1 节，再看第 3 节的弯路（避免重复踩），
> 最后看第 6 节决定要不要继续投入。

---

## 0. 一页结论

| 问题 | 答案 |
|---|---|
| 日常登录需要模拟器吗 | ❌ 不需要 |
| 首次使用需要模拟器吗 | ✅ 需要（一次） |
| 改密码后需要模拟器吗 | ✅ 需要（一次） |
| 是否达成了「真正零模拟器」 | ❌ **没有** |
| 是否破解了 `signDigital` | ❌ 没有，也不需要 |
| 命令行登录本身是否可用 | ✅ 已验收 |

---

## 1. 一句话结论

**我们达成的不是「免模拟器」，而是「模拟器从每天用变成一次性用」。**

准确表述：

> 登录动作本身完全在命令行完成，不需要模拟器；
> 但支撑登录的那个**签名**，来源只能是官方客户端，所以每换一次密码就要回模拟器取一次。

这个差别很关键：如果对外说"不需要模拟器"，是不准确的。

## 2. 当前能力矩阵

| 操作 | 需要模拟器 | 说明 |
|---|---|---|
| 账号密码登录 | ❌ | `[9]`，输入密码即可 |
| 查询活动 / 抢课 / 退课 | ❌ | 纯 HTTP |
| Token 刷新 | ❌ | `[8]` |
| 首次配置 | ✅ | 抓一次包取签名 |
| 改密码后恢复 | ✅ | `[b]` 重抓 |
| Token 彻底失效且签名还在 | ❌ | `[8]` 刷新即可 |

**换算成实际频率：一学期大概 1–2 次需要开模拟器。**

## 3. 走过的弯路

按"花了多少精力 / 有多容易想当然"排序。

### 弯路 1：静态反编译原生库找 `hs()`

**最初的判断**：`signDigital = hs(账号+密码+entrance)`，函数在 `libsportaction.so`，
反编译出来就能自己算。

**实际做了什么**

- 解析 ELF 符号表找 `Java_cn_legym_ai_util_Rengis_hs`
- 从 JNI 注册字符串还原出调用链：
  `Java_cn_legym_ai_util_Rengis_hs` → `ToHS` → `SHA1::process_block/add/finalize` → `ByteToHexStr`
- 用程序头做段熵分析

**为什么失败（两条硬证据）**

1. **代码段是加密的**

   | 库 | R-X 段整体熵 | 高熵窗口 | 峰值 |
   |---|---|---|---|
   | `libsportaction.so` | 7.19 | **33 / 67** | 7.94（近随机上限） |
   | `libsecurity.so` | 6.76 | 0 / 6 | 6.74（正常编译代码） |

   这正好解释了为什么 `getDynamicKey` 能被还原，而 `hs` 不能——
   **前者在明文库，后者在加固库**。

2. **节区表被故意破坏**

   整个文件被标成 `SHT_NOBITS`，只剩 4 个假节区。
   任何基于节区的工具（IDA/Ghidra 默认视图）都会失效，必须改用程序头。

**结论**：静态分析此路不通，除非先脱壳（DexVMP）。

---

### 弯路 2：穷举哈希组合

**想法**：既然知道是 SHA1，那输入要么是 `账号+密码`，要么再加上 `entrance`，
再试几个盐，总能撞上。

**实际做了什么**：写了一个组合穷举器，维度包括

- 拼接顺序：`upe / up / eup / upea / upeb / upeabd / …`（14 种）
- 分隔符：空、`:`、`|`、`,`、`_`、`-`
- 编码：UTF-8 / UTF-16-LE / UTF-16-BE / GBK
- 盐：空、`lgAI2021key~*21B`、动态密钥盐、`legym` 等 8 种
- 算法：SHA1 / SHA256 / MD5，大小写各一
- 设备维度：android_id、机型、品牌、包名

**共 24,840 种，全部不中。**

**收获**：这至少排除了"简单拼接"这一类假设，
说明 `hs()` 内部还掺了设备指纹或包签名摘要。

---

### 弯路 3：把信封存起来反复重放

**想法**：抓到的登录请求里已经带着密码（加密的），那存下来每期重放不就行了？

**实验做了两件事**

1. 直接重放原信封 → ✅ 成功，拿到新 token
2. 用不同年龄的 `t` 重新封装 → 结果：

| 信封年龄 | 结果 |
|---|---|
| 刚刚 | ✅ 成功 |
| 1 小时前 | ❌ `40003 无法读取请求参数` |
| 1 天 / 7 天 / 30 天前 | ❌ 同上 |

**为什么失败**：服务端对 `t` 有新鲜度窗口。
"存信封"这条最省事的路，1 小时就废了。

**但这个失败很有价值**——它反过来说明：
`t` 有时效，而 `signDigital` 没有。**这才是真正的突破口。**

---

### 弯路 4：以为 `[a]`（模拟器同步）能救改密码

**实际发生的事**（2026-11-01 实测）：

```
14:23  改密码前抓的签名
14:40  跑 [a] 从模拟器同步 token → 只换了 token，签名还是旧的
14:42  跑 [9] 用新密码 + 旧签名 → HTTP 400 {"code":50004,"message":"签名不正确"}
```

**教训**：`[a]` 和 `[b]` 看起来都是"刷新登录态"，语义完全不同：

| | 换 token | 换签名 |
|---|---|---|
| `[a]` 模拟器同步 | ✅ | ❌ |
| `[b]` 重抓签名 | ✅ | ✅ |

**改密码后必须 `[b]`**，这一点已经写进菜单提示和错误提示里。

**附带收获**：这条错误同时证明了**服务端确实会校验 `signDigital`**
（在此之前只是推测）。

---

### 弯路 5（评估后放弃）：Frida Hook

**想法**：既然静态分析不通，就在运行时 Hook 它。

**做法**：装 frida-server → Hook `cn.legym.ai.util.Rengis.hs` 的入参与返回值。

**放弃理由**

- 需要 root（有）+ 推 frida-server（可做）+ 再登录一次（要用户配合）
- 但**它解决的问题已经被绕开了**，再做就是纯沉没成本
- 唯一剩余价值是"彻底免抓包"，而这只在改密码时才用得上

**保留为备选**，如果哪天密码策略变更、签名不再可复用，再启动。

## 4. 转折点

整理一下逻辑链，这是整个项目的关键推理：

```
signDigital = hs(账号 + 密码 + entrance)     ← 三个入参都不含时间 → 常量
信封 = {"t": 时间戳, "pyd": AES(明文)}       ← 只有 t 有时效

∴ 存签名（常量），每次用新的 t 现场封装 → 可长期登录
   存信封（含 t）→ 1 小时就失效
```

**一句话：不要存"那一整条请求"，要存"请求里那个不随时间变的签名"。**

这个结论不是猜的，是弯路 3 的实验数据反推出来的。

## 5. 现在的架构

```
首次 / 改密码后（需要模拟器，一次性）
    [b] capture_login.py
        连接模拟器 → 注入证书 → 重启 zygote → 配代理
        → 清空 App → 你在 App 里登录
        → 抓包 → 解出 signDigital → credential.json
                                          ↑ 只存账号 + 签名，不存密码

日常（不需要模拟器）
    [9] login_cli.py
        读 credential.json + 你输入密码
        → 用当前时间 t 封装信封 → POST v2/manage/login
        → 拿到 accessToken / refreshToken
        → 查 semester/getCurrent 补 semesterId
        → 写 state.json → 抢课程序正常工作

运行期
    [8] 刷新 token（纯 HTTP）
    [1] 查看状态
```

## 6. 想做到「真正零模拟器」，还差什么

三条路，按性价比排：

### 路线 A：分发 `credential.json`

把签名当成配置项，随程序一起分发（等于一串很长的"密钥"）。

| 项 | 评估 |
|---|---|
| 成本 | 极低，现在就能做 |
| 效果 | 换台电脑也能登录，无需模拟器 |
| 代价 | **凭据扩散**。签名 + 密码就能登录，等于把半把钥匙给了每个人 |
| 结论 | 自己用可以，**给别人用不行** |

### 路线 B：Frida 取 `hs()` 真身

运行时把入参和返回值 dump 出来，反推公式。

| 项 | 评估 |
|---|---|
| 成本 | 中高：装 frida-server、再抓一次、分析 ARM 指令 |
| 效果 | 彻底免抓包，密码随便改 |
| 代价 | 需要 root 设备；一旦签名算法随版本更新就重来 |
| 结论 | 只有当"频繁改密码"成为真实痛点才值得 |

### 路线 C：维持现状

| 项 | 评估 |
|---|---|
| 成本 | 零 |
| 效果 | 一学期 1–2 次开模拟器 |
| 代价 | 改密码时记得走 `[b]` |
| 结论 | **当前推荐** |

### 决策建议

> 先按路线 C 用一段时间。
> 如果实际用下来，"改密码要开模拟器"这件事让你烦躁到超过每学期两次，
> 再考虑路线 B。路线 A 只在自己一个人的机器上成立。
