# Phase 1 补充验收：熔断器边界条件检查

Phase 1 主体实现已经完成，当前全量测试 287 项通过。

请不要重新设计或大规模重构熔断器，仅针对以下两个边界问题进行检查和补充测试。

## 任务一：HALF_OPEN 状态下的客户端异常

检查以下场景：

1. 熔断器进入 OPEN。
2. 冷却结束，进入 HALF_OPEN。
3. 健康探测返回 HTTP 401。
4. 健康探测返回 HTTP 403。
5. 健康探测返回 HTTP 400。

要求：

- 不能将 401、403、400 计入基础设施故障次数。
- 不能因为 Token 失效而错误增加基础设施故障退避次数。
- 不能在没有完整健康数据的情况下恢复 CLOSED。
- 必须正确释放 HALF_OPEN 探测锁，避免探测状态永久挂起。
- 401 应交给现有 Token 刷新机制处理。
- 403 应明确提示权限异常。
- 恢复探测必须重新验证完整列表。

如果需要调整状态机，优先采用最小修改。

新增测试：

- HALF_OPEN + 401。
- HALF_OPEN + 403。
- HALF_OPEN + 400。
- 认证处理后重新进行健康探测。
- 客户端异常不会造成无限退避。

## 任务二：核实 max_retries 语义

检查 `Client.activities()` 中 `max_retries` 的真实含义。

明确回答：

- max_retries=1 实际发起几次 HTTP 请求？
- max_retries=0 是否允许？
- 主轮询实际使用几次底层请求？
- 内部重试是否会导致请求次数和熔断统计不一致？

要求：

为主轮询增加明确的测试，验证一次外层轮询的实际底层请求次数。

不要只检查熔断器 failure_count，还必须检查 Mock HTTP 调用次数。

如果 max_retries 表示重试次数，请明确区分首次请求与额外重试。

必要时修改参数命名或注释，避免后续维护者产生歧义。
