## 结论：绕开了 `signDigital`，而不是破解它

文档的结论是「部分可行，`hs()` 被 DexVMP 加固卡住」。我没有去啃加固，而是发现了一个更省事的入口。

**关键推理：**

代码块



```
signDigital = hs(账号 + 密码 + entrance)   ← 三个入参都不含时间 → 是常量
信封 {"t": 毫秒时间戳, "pyd": AES(...)}    ← 只有 t 有时效
```

所以：**抓一次包存下签名，之后每次用新的 `t` 重新封装**就行。

## 三个实验把这件事钉死了

**① 重放原信封** → HTTP 200，拿到新 token。服务端不校验信封"新旧"，只看 `t` 本身。

**② 信封时效性**

| 信封年龄              | 结果                       |
| --------------------- | -------------------------- |
| 刚刚                  | ✅ 成功                     |
| 1 小时前              | ❌ `40003 无法读取请求参数` |
| 1 天 / 7 天 / 30 天前 | ❌ 同上                     |

→ **存信封没用，但存签名有用**。

**③ 端到端登录**

代码块



```
✅ 登录成功  姓名: 陈佳荣  schoolId: 8a9780478...
已写入 state.json（semesterId=8a97802fa...）

token 剩余 30188 秒（8.4 小时）
[1] 户外跑 周天一  周二 17:40  余8/200
```

新 token 直接能调业务接口。

## 顺带验证：`hs()` 确实啃不动

我没有直接接受文档结论，独立复核了三件事：

- R-X 段熵 **7.19**，33/67 窗口超过 7.2、峰值 7.94 → 代码确实加密存放
- 节区表被破坏，整个文件标成 `SHT_NOBITS`，只剩 4 个假节区
- 穷举 **24,840 种**组合（拼接×哈希×盐×编码×分隔符×设备号）→ 全部不中

**所以继续投入是纯沉没成本，而这个绕开方案成本几乎为零。**

## 三条限制，说清楚

**① 改密码后签名失效** `hs(u+p+e)` 绑死密码。改了就重新抓一次包 `--setup`。

**② 每次登录要输一次密码** 这是刻意的——**不保存密码**，`getpass` 读入、不回显、不入日志。想免输就得存密码，那违背项目红线。

**③ 首次仍需一次抓包** 「装个 Python 就能用」还差这一步。可以把 `credential.json` 当配置分发，但那等于把凭据扩散出去，要不要这么做你权衡。
