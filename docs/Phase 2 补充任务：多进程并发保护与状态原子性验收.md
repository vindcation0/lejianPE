## 二、任务一：检查单实例运行保护

重点检查：

- `lejian.py`
- `core/state_store.py`
- `core/registration_manager.py`
- `core/recovery_manager.py`

确认：

1. 两个独立 Python 进程能否同时启动。
2. 两个进程能否同时获得报名执行权。
3. 是否存在进程内锁代替系统级锁的情况。
4. 进程异常退出后锁能否自动释放。
5. 第二个进程能否明确知道第一个进程正在运行。

如果缺少单实例保护，请增加操作系统级锁。

要求：

- Windows 环境可用。
- 不依赖第三方守护进程。
- 进程异常退出后锁能够释放。
- 不使用固定 PID 文件作为唯一锁定依据。
- 锁必须在报名执行期间持续有效。

## 三、任务二：检查 SQLite 状态原子性

重点检查以下操作：

```
state_store.has_unresolved()
state_store.set_status(...)
```

确认是否存在：

```
进程 A 检查：没有 UNKNOWN
进程 B 检查：没有 UNKNOWN

进程 A 写入 SUBMITTING
进程 B 写入 SUBMITTING

进程 A signUp
进程 B signUp
```

这种竞态必须被禁止。

建议使用 SQLite 事务或原子预留机制，保证：

检查全局未决状态和创建新 SUBMITTING 记录不能被其他进程插入操作。

要求：

- 事务具有明确的原子性。
- 写入失败必须回滚。
- 不能因为事务异常而继续提交报名。
- 不能出现两个不同活动同时处于可提交状态。
- 现有数据库数据必须兼容。

## 四、任务三：增加真实多进程测试

必须使用 multiprocessing 创建两个独立 Python 进程，而不是两个线程。

测试场景：

### M01：两个进程同时启动

两个进程同时尝试获得执行权。

预期：

- 只有一个获得报名执行权。
- 另一个明确被拒绝。
- 不产生重复报名请求。

### M02：进程 A 持有锁时，进程 B 启动

预期：

- B 无法获得执行权。
- B 不执行报名。
- A 不受影响。

### M03：进程 A 异常退出

预期：

- 系统级锁自动释放。
- 进程 B 能够获得执行权。
- 原有持久化状态不丢失。

### M04：两个进程同时预留不同活动

预期：

- SQLite 原子保护生效。
- 只有一个进程能创建有效 SUBMITTING。
- 不会同时提交两个活动。

### M05：进程 A 已存在 UNKNOWN，进程 B 启动

预期：

- B 无法绕过 UNKNOWN 屏障。
- B 不允许提交任何新候选。

### M06：进程 A 提交后崩溃，进程 B 启动

预期：

- B 发现遗留 SUBMITTING。
- 只读复核。
- 不重复 signUp。

### M07：达到每周上限后的并发尝试

预期：

- 多进程不能绕过每周配额。
- 最终服务端报名数不超额。

所有测试使用临时 SQLite 数据库和 Mock HTTP。

禁止访问真实抢课接口。

## 五、任务四：补充 UNKNOWN 状态转换验证

检查并补充：

1. 完整列表确认未报名，持久化 RETRYABLE。
2. 不完整列表不能转为 RETRYABLE。
3. 目标活动缺失不能转为 RETRYABLE。
4. RETRYABLE 状态重复处理不会重复增加配额。
5. RETRYABLE 重新提交前必须重新执行规则检查。
6. SUCCESS 不会重复累计配额。
7. 状态写入失败禁止继续提交。

注意区分：

- 复核确认未报名。
- 复核请求失败。
- 服务端没有返回目标活动。
- 数据格式异常。

这些情况不能混为一谈。
