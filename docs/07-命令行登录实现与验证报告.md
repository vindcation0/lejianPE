## 二、突破点：签名是常量，只有时间戳有时效

### 2.1 关键推理

`signDigital = hs(userName + password + entrance)`

三个入参**都不含时间**，所以只要密码不变，这个签名就是**固定值**。
而信封里的 `t` 才有新鲜度要求。

因此：**抓一次包 → 存下签名 → 每次用新的 `t` 重新封装**即可长期登录。

### 2.2 三个实验验证

**实验一：重放原信封**

```
原始信封 t = 1793514043462（1.6 分钟前）
HTTP 200  code=0
✅ 重放成功，拿到新 token
```

**实验二：信封时效性**

用同一份明文，分别以不同年龄的 `t` 重新封装：

| 信封年龄 | 结果 |
|---|---|
| 刚刚 | ✅ 成功 |
| 1 小时前 | ❌ `code=40003 无法读取请求参数` |
| 1 天前 | ❌ 同上 |
| 7 天前 | ❌ 同上 |
| 30 天前 | ❌ 同上 |

> 说明服务端对 `t` 有新鲜度窗口。**不能把信封存起来反复用**，
> 但可以**存签名，每次现场生成新信封**。

**实验三：端到端登录**

```
✅ 登录成功
  姓名      : 陈**
  schoolId  : 8a978047...
  有效期至  : 2026-11-01 22:46:26

已写入 state.json（semesterId=8a97802f...）
```

随后用新 `state.json` 调业务接口，活动列表正常返回。

## 三、最终方案

```
第一次（一次性）
    模拟器 + 抓包 → 提取 (账号, signDigital, entrance) → credential.json
                                                    ↑ 不含密码

之后每次
    credential.json + 用户输入的密码
        ↓
    用当前 t 封装信封 → POST v2/manage/login
        ↓
    解出 accessToken / refreshToken
        ↓
    查 semester/getCurrent 补全 semesterId
        ↓
    写入 state.json → 抢课程序正常工作
```

### 涉及文件

| 文件 | 作用 |
|---|---|
| `tools/login_envelope.py` | 动态密钥 + AES 信封编解码（含自测） |
| `tools/login_cli.py` | 命令行登录；`--setup` 从抓包生成凭据 |
| `tools/analyze_login_capture.py` | 抓包分析器（解密 + 算法穷举） |
| `tools/replay_login.py` | 重放验证 |
| `tools/test_envelope_age.py` | 时效性测试 |
| `credential.json` | 账号 + 签名（**已加入 .gitignore**） |

### 使用

```bash
# 一次性：从抓包提取凭据
python tools\login_cli.py --setup captures\login_flows.jsonl

# 日常：输入密码登录
python tools\login_cli.py
```

菜单里对应 **`[9]` 账号密码登录**；模拟器同步降为 **`[a]` 备用**。

## 四、为什么没有继续破解 hs()

三种可行性都做过评估：

| 路径 | 障碍 | 结论 |
|---|---|---|
| 静态反编译 `libsportaction.so` | R-X 段约一半窗口熵 7.94（接近随机），代码加密存放；节区表被破坏成 4 个假节区 | 不可行 |
| 穷举哈希组合 | 已试 24,840 种（拼接顺序 × 哈希算法 × 盐 × 编码 × 分隔符 × 设备号） | 均不匹配，输入含未知成分 |
| Frida Hook | 需要 frida-server + 再登录一次 | **备选，但已无必要** |

**因为绕开方案成本几乎为零，继续破解纯属沉没成本。**

## 五、限制与风险

### 5.1 密码修改后签名失效（已实测确认）

`credential.json` 里的签名绑定 `(账号, 密码, entrance)`。
改密码 → 签名对不上 → 登录报错 → 需重新抓包。

**2026-11-01 实测**：用户改了密码后用新密码登录，服务端返回

```
HTTP 400  {"code":50004,"message":"签名不正确","data":null}
```

这条错误同时证明了两件事：

1. **服务端确实校验 `signDigital`**（此前只是推测）
2. 本文的绕开方案成立，但**前提是密码保持不变**

> ⚠️ 常见误区：菜单 `[a]`（从模拟器同步 Token）**只搬运 token，不会更新签名**。
> 改密码后必须走 `[b]` 重新抓取签名，`[a]` 解决不了。

工具在收到这类错误时会直接提示去跑 `python tools\capture_login.py`。

### 5.2 每次登录要输一次密码

这是刻意的：**不保存密码**。输入用 `getpass`，不回显、不入日志、不落盘。

若希望免输密码，只能把密码存下来——这违背项目安全红线，不做。

### 5.3 credential.json 的敏感级别

它含手机号和一个能通过服务端校验的签名值。
虽然不等于密码，但**足以配合密码完成登录**，因此：

- 已加入 `.gitignore`
- 不要发给他人
- 与 `state.json` 同等对待

### 5.4 首次仍需一次抓包

「装个 Python 就能用」的终极目标还差一步：第一次必须从官方客户端取一次签名。
缓解办法：把这个 `credential.json` 作为配置项分发（等同于一串很长的"密钥"），
但这会把凭据扩散到更多地方，是否值得需要权衡。

## 八、验收记录（2026-11-01）

### 8.1 触发场景

用户修改了密码，然后：

```
14:23  改密码前抓的签名，已失效
14:40  菜单 [a] 从模拟器同步 token → 只换了 token，签名仍是旧的
14:42  菜单 [9] 用新密码 + 旧签名 → 50004 签名不正确
14:47  菜单 [b] 重新抓包 → 新签名已成功抓取并生成凭据
14:47  手工 [9] 输入新密码 → ✅ 登录成功
        [1] 查看状态 → ✅ token 有效
```

### 8.2 结论

| 验收项 | 结果 |
|---|---|
| 手工输入密码（getpass 路径） | ✅ 通过 |
| 新签名与服务端校验 | ✅ 通过 |
| `state.json` 生成且被业务代码接受 | ✅ 通过 |
| 改密码后重新抓取流程 | ✅ 通过（一条命令） |
| 免模拟器的日常登录 | ✅ 通过 |

### 8.3 本次修复的两个缺陷

1. **`capture_login.py` 崩溃**：`shell()` 把 `timeout` 当位置参数传给 `run()`，
   `60` 被拼进 adb 命令行，导致第一步提权检查即抛 `TypeError`。
   菜单 `[b]` 当时正因此无法启动。
2. **子进程输出乱码**：`subprocess.run(text=True)` 在中文 Windows 下按 GBK 解码，
   而子进程输出 UTF-8，中文全部变成 `宸茬敓鎴`。已显式指定 `encoding="utf-8"`。

### 8.4 当前认证方式优先级

```
[9] 账号密码登录（推荐，无需模拟器）
     ↓ 失败且报 50004 签名不正确
[b] 重新抓取签名（需要模拟器，一次性）
     ↓ 临时救急
[a] 从模拟器同步 Token（只换 token，不换签名）
```
