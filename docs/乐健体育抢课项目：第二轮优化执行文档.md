**本轮目标：** 修复现有系统的四项可靠性问题，不进行大规模重构，不改变学校接口协议，不随意增加新功能。

**执行原则：** 先检查当前代码，再制定修改方案，最后实施修改和测试。所有修改必须兼容现有数据和使用流程。

# 三、任务一：修复每日报名上限漏洞

**优先级：P0，必须首先完成。**

## 3.1 问题描述

涉及：

- `lejian.py`
- `pick_targets()`
- `cmd_grab()` 中的候选活动处理逻辑

当前配置中存在：

```
{
  "max_normal": 2,
  "max_per_day": 1
}
```

其中：

- `max_normal`：每周普通活动报名上限。
- `max_per_day`：每天普通活动报名上限。
- `special`：特殊活动关键词，不占普通活动名额。

目前 `pick_targets()` 在筛选候选活动时，会根据已经报名的活动计算 `day_count`。

但是，将候选活动加入 `picked` 后，没有同步增加临时计数。

因此，同一天多个普通活动可能同时通过筛选。

在后续报名循环中，虽然会更新 `DAY_DONE`，但没有充分执行每日上限的提交前二次校验。

可能出现同一天报名两节普通活动的情况。

## 3.2 修改要求

### 要求 A：候选筛选时维护临时每日计数

在 `pick_targets()` 中：

1. 统计服务端已经报名的普通活动。
2. 统计本次运行已经成功报名的普通活动。
3. 合并计算每天已使用的名额。
4. 筛选候选活动时，使用临时计数。
5. 普通活动被选中后，立即占用当天的一个临时名额。
6. 同一天后续普通活动不得继续进入候选列表。

注意：

候选被选中不等于实际报名成功，因此应区分：

- 候选筛选阶段的临时计数。
- 实际报名成功后的持久运行计数。

不能将未成功报名的候选永久记入实际成功数量。

### 要求 B：提交前再次校验

在 `cmd_grab()` 真正调用：

```
reg_mgr.register_activity(...)
```

之前，再次检查：

- 当前活动是否为普通活动。
- 当天普通活动数量是否已经达到 `max_per_day`。
- 当前周普通活动数量是否已经达到 `max_normal`。

如果达到限制：

- 禁止提交。
- 输出明确的跳过原因。
- 不产生报名请求。

### 要求 C：保持特殊活动语义

特殊活动仍然遵守现有规则：

- 不占普通活动每周名额。
- 不占普通活动每日名额。
- 保留现有特殊活动优先级。
- 不改变现有特殊活动识别方式。

不得因为修复每日上限而改变特殊活动逻辑。

## 3.3 必须新增测试

建议新增：

**T27：同一天多个普通候选活动**

初始状态：

- 当天没有已报名活动。
- 有两个符合条件的普通活动。
- `max_per_day = 1`。

预期：

- 只有一个普通活动可以进入可提交候选。
- 最多成功提交一个。

**T28：不同日期候选活动**

初始状态：

- 两个普通活动分别位于不同日期。
- `max_per_day = 1`。

预期：

- 两个活动均可正常报名。

**T29：特殊活动不占每日名额**

初始状态：

- 同一天存在一个特殊活动和一个普通活动。

预期：

- 特殊活动成功后，普通活动仍可报名。
- 普通活动每日上限依然有效。

**T30：提交前二次校验**

模拟候选生成后，其他流程已经使当天达到报名上限。

预期：

- 二次校验阻止报名。
- 不产生网络提交请求。

# 四、任务二：活动列表分页完整性保护

**优先级：P1**

## 4.1 问题描述

涉及：

```
lejian.py
```

函数：

```
Client.activities()
```

当前代码通过分页获取活动：

```
while page <= 10:
    ...
```

当某一页连续请求失败时，会直接：

```
break
```

最后返回：

```
return out
```

问题是：

即使只获取到第一页，函数也可能将部分活动数据返回给调用方。

调用方无法区分：

- 活动列表完整。
- 活动列表只获取了一部分。
- 活动列表获取失败。

这会影响：

- 已报名活动统计。
- 每周报名上限。
- 活动候选筛选。
- UNKNOWN 状态复核。
- 最终报名对账。

## 4.2 修改要求

### 要求 A：明确活动列表获取状态

为活动列表获取过程增加完整性信息。

可以设计统一结果对象，例如：

```
{
    "items": [],
    "complete": True,
    "total": 300,
    "fetched": 300
}
```

具体实现可以使用 dataclass 或其他合适结构。

但必须满足：

1. 能区分完整获取和不完整获取。
2. 能记录服务端总数。
3. 能记录实际获取数量。
4. 能明确表示请求失败。
5. 不允许调用方把部分数据误认为完整数据。

### 要求 B：保护所有重要调用方

检查所有调用：

```
Client.activities()
```

重点检查：

- `cmd_list()`
- `cmd_grab()`
- `cmd_timetable()`（如果有相关调用）
- `ReconciliationManager`
- `RequestManager` 或 `verify_registration()`
- 其他使用活动列表判断报名状态的模块。

需要根据调用用途分别处理：

**抢课决策：**

活动列表不完整时：

- 禁止基于部分列表进行报名决策。
- 禁止发起新的报名提交。
- 输出明确错误信息。
- 允许有限重试。

**服务端状态复核：**

如果活动列表不完整：

- 不得把未找到活动解释为未报名。
- 保持 UNKNOWN 状态。
- 不得因为列表缺失而盲目重新提交。

**菜单展示：**

可以选择展示已获取的部分数据，但必须明确标注：

```
警告：当前活动列表获取不完整，仅显示部分结果。
```

不得显示为正常完整结果。

### 要求 C：失败处理

保留现有请求超时和重试机制。

本任务不允许：

- 无限重试。
- 高频请求。
- 盲目增加报名请求。
- 改变学校接口参数。
- 在数据不完整时继续抢课。

分页失败应当有明确的错误状态，而不是静默返回部分数据。

## 4.3 必须新增测试

**T31：第一页成功，第二页失败**

预期：

- 活动列表标记为不完整。
- 抢课流程禁止提交。

**T32：全部分页成功**

预期：

- 返回完整数据。
- 总数和获取数量一致。

**T33：复核时列表不完整**

预期：

- 不得判断为未报名。
- 保持 UNKNOWN。
- 不得重复提交。

**T34：菜单展示部分数据**

预期：

- 明确提示数据不完整。
- 不误导用户。

# 五、任务三：修复旧版课表迁移校验遗漏

**优先级：P1**

## 5.1 问题描述

涉及：

```
timetable/compatibility.py
```

重点函数：

```
from_schema1_dict()
```

目前旧版 Schema v1 数据转换为新版 Timetable 对象时，会直接创建对象并返回。

但没有明确保证转换后的数据经过新版完整 Validator。

因此，旧版数据可能绕过新版日期校验。

例如：

```
{
  "week1_monday": "2026-09-01"
}
```

2026-09-01 是星期二，而不是星期一。

如果该数据绕过校验，后续教学周计算就可能整体偏移。

## 5.2 修改要求

迁移过程必须遵循：

```
旧版 JSON
    |
    v
识别 Schema v1
    |
    v
转换为 Schema v2 数据结构
    |
    v
执行新版完整 Validator
    |
    +---- 通过 ----> 创建 Timetable 对象
    |
    +---- 失败 ----> 抛出明确异常
```

### 要求 A：统一校验入口

迁移完成后必须检查：

- `week1_monday` 格式是否合法。
- `week1_monday` 是否为星期一。
- `total_weeks` 是否符合范围。
- `busy_slots` 数据是否合法。
- `weekday` 是否有效。
- 时间范围是否合法。
- 周次区间是否合法。

不要只校验日期字段。

### 要求 B：旧版兼容

必须保留现有旧版字段映射逻辑。

不得因为增加校验就直接删除：

- `courses`
- 旧版课程名称映射。
- 旧版周次区间转换。
- 原有去重逻辑。

### 要求 C：缺失 week1_monday 的处理

目前旧版兼容逻辑可能根据 `current_week` 推算第一教学周日期。

这一行为需要保留兼容能力，但必须明确：

1. 使用了什么日期推算。
2. 使用了什么教学周作为基准。
3. 是否属于自动推算数据。
4. 在日志或提示中说明推算结果。

不能在用户不知情的情况下将不确定的日期当成准确日期。

### 要求 D：文件安全

迁移校验失败时：

- 原始 JSON 不得被覆盖。
- 不得自动清空旧数据。
- 不得静默忽略错误课程记录。
- 输出明确错误位置和原因。

## 5.3 必须新增测试

**T35：旧版合法数据迁移**

预期：

- 正常迁移。
- 课程信息完整。
- 新版对象合法。

**T36：旧版星期二作为第一周锚点**

预期：

- 抛出 ValidationError。

**T37：旧版非法周次**

预期：

- 迁移失败。
- 明确提示错误课程记录。

**T38：缺失 week1_monday**

预期：

- 使用兼容推算逻辑。
- 明确记录推算结果。

**T39：迁移失败时保护原始文件**

预期：

- 文件内容完全不变。

# 六、任务四：完善 Markdown 课表转换工具

**优先级：P1**

## 6.1 涉及文件

```
tools/build_timetable.py
timetable/models.py
timetable/validator.py
timetable/compatibility.py
```

重点检查：

```
main()
parse()
```

## 6.2 当前存在的问题

### 问题 A：默认教学周不够安全

目前：

```
week = int(sys.argv[2]) if len(sys.argv) > 2 else 8
```

直接默认第 8 周。

如果用户忘记传入实际教学周，就可能生成错误的 `week1_monday`。

### 问题 B：学期总周数缺少明确参数

当前生成的数据没有完整支持学期总周数的命令行配置。

### 问题 C：无周次课程固定默认为 16 周

目前：

```
if not weeks:
    weeks = [(1, 16)]
```

不应该在学期总周数已经可配置的情况下继续固定写死 16。

### 问题 D：直接覆盖课表文件

目前：

```
with open(OUT, "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False, indent=2)
```

没有充分利用已经存在的课表校验、备份和安全保存机制。

## 6.3 修改要求

### 要求 A：增加明确的命令行参数

建议使用 argparse。

支持：

```
python tools/build_timetable.py course_schedule.md --week1-monday 2026-08-31 --total-weeks 16
```

也可以支持：

```
python tools/build_timetable.py course_schedule.md --current-week 8 --total-weeks 16
```

其中：

- `--week1-monday`：第一教学周周一。
- `--current-week`：当前日期对应的教学周。
- `--total-weeks`：学期总周数。

两个日期锚点参数应明确互斥。

如果使用 `--current-week`，根据当前日期所在星期计算当前周周一，再反推第一教学周周一。

不得继续静默默认第 8 周。

### 要求 B：学期总周数统一

`--total-weeks` 应支持合法学期周数。

必须与项目现有 Validator 的范围保持一致。

默认值可以保留 16 周，但必须明确显示，并允许用户覆盖。

对于没有明确周次的课程：

```
weeks = [(1, total_weeks)]
```

不得继续硬编码：

```
weeks = [(1, 16)]
```

### 要求 C：保存流程统一

必须复用现有课表保存 API：

```
save_timetable_file(...)
```

实际函数签名需要先检查，不得自行假设。

保存之前：

1. 构建 Schema v2 数据。
2. 执行完整校验。
3. 检查周次和时间区间。
4. 使用现有备份及原子保存机制。
5. 保存成功后输出文件位置。

不能直接覆盖原文件。

### 要求 D：输入错误处理

以下情况必须明确报错：

- Markdown 文件不存在。
- 日期格式错误。
- 第一教学周不是星期一。
- 学期周数超出范围。
- 当前教学周不合法。
- 课程时间格式错误。
- 周次区间非法。
- 解析结果为空。

不能生成看似成功但实际错误的课表。

### 要求 E：保留解析兼容

不能随意重写现有 Markdown 解析算法。

应尽量保留：

- 星期解析。
- 时间段解析。
- 课程名称提取。
- 单周课程解析。
- 连续周次解析。
- 周次区间合并。

只修复输入配置和输出保存流程。

## 6.4 必须新增测试

**T40：显式指定第一教学周日期**

预期：

- 正确生成 Schema v2。
- 第一教学周日期正确。

**T41：使用当前教学周反推**

预期：

- 推算结果正确。
- 与显式日期方式结果一致。

**T42：自定义学期总周数**

预期：

- 正确保存 total_weeks。
- 无周次课程使用完整学期周数。

**T43：非法日期**

预期：

- 拒绝生成。
- 原课表不受影响。

**T44：非法学期周数**

预期：

- 明确报错。

**T45：保存前校验失败**

预期：

# 最终原则

本轮开发的核心目标不是增加功能数量，而是提高抢课系统的可靠性。

尤其要保证：

**宁可因为数据不完整而暂停抢课，也不能因为错误判断而突破报名限制或产生重复提交。**

所有修改必须以现有代码为基础，优先采用最小、安全、可测试的改动。

完成四项任务后，再考虑下一轮的抢课前自检、候选过滤原因诊断和日志分析功能。
