# 乐健体育账号密码登录协议分析与命令行登录改造执行文档

**项目地址：** https://github.com/vindcation0/lejianPE

**任务类型：** 认证系统研究、可行性验证及渐进式改造

**核心目标：** 研究是否能够通过官方登录协议直接使用账号密码登录，从而逐步摆脱 MuMu 模拟器及 ADB 获取 Token 的方式。

**优先级：** P1

**开发原则：** 先研究、后验证、再实现；最小改动、保持兼容、不破坏现有认证和抢课系统。

# 一、任务背景

## 1.1 当前认证流程

项目目前采用以下方式获取登录凭据：

```
启动 MuMu 模拟器
    ↓
打开乐健体育 App
    ↓
用户在 App 中登录
    ↓
通过 ADB 连接模拟器
    ↓
读取 App 本地数据库
    ↓
提取 accessToken、refreshToken
    ↓
获取 schoolId、semesterId 等必要信息
    ↓
生成 state.json
    ↓
执行抢课功能
```

该方案已经可以正常工作，但存在明显的使用成本：

1. 用户必须安装 Android 模拟器。
2. 必须安装并登录乐健体育 App。
3. 需要 ADB 环境。
4. 首次配置较为复杂。
5. Token 失效后可能需要重新操作模拟器。
6. 不利于项目在其他用户的 Windows 电脑上部署。

因此，希望研究是否可以直接使用账号密码完成认证。

## 1.2 期望的新认证流程

```
启动 lejianPE
    ↓
选择账号密码登录
    ↓
输入账号
    ↓
安全输入密码
    ↓
调用官方认证接口
    ↓
完成必要的验证码或二次认证
    ↓
获取登录 Token
    ↓
获取运行所需的学校、学期信息
    ↓
生成 state.json
    ↓
使用现有抢课程序
```

首次登录成功后，继续复用现有 Token 刷新机制。

用户不应每次启动程序都重新输入密码。

# 三、阶段一：登录协议分析

**本阶段是必须完成的前置任务。**

在没有充分证据前，不得开始替换现有认证流程。

## 3.1 审计现有项目

首先阅读：

```

```

重点分析：

1. 当前 Token 如何获取。

4. 登录成功后必须保存哪些字段。
5. 哪些业务模块依赖 `state.json`。
6. 是否已经存在账号登录接口的相关实现。
7. 是否存在可用于验证的非敏感接口记录。

输出当前认证模块调用关系。

## 3.2 确认登录接口请求结构

研究：

```
POST /authorization/user/manage/login
```

需要确认：

| 检查项       | 需要确认的内容           |
| ------------ | ------------------------ |
| 请求方式     | 是否确实为 POST          |
| Content-Type | JSON、表单或其他格式     |
| 账号字段     | 真实字段名称             |
| 密码字段     | 真实字段名称             |
| 密码处理     | 明文、摘要或加密         |
| 学校标识     | 是否必须提供             |
| 设备信息     | 是否要求设备 ID 等参数   |
| 验证码       | 是否存在图形或短信验证码 |
| 额外认证     | 是否需要其他登录步骤     |
| 返回结构     | Token 和用户信息所在位置 |
| 错误处理     | 密码错误、账号异常等响应 |

### 研究约束

优先使用：

- 仓库已有文档。
- 已经合法获得的非敏感请求记录。
- 官方客户端正常登录过程中可观察的信息。
- 官方公开的接口说明（如存在）。

不得：

- 使用他人账号进行测试。
- 批量尝试账号密码。
- 绕过验证码。
- 绕过设备安全验证。
- 使用真实密码进行不必要的日志记录。
- 将真实凭据上传至第三方分析服务。

如果某个字段无法确定，必须标记为：

```
UNKNOWN / 尚未验证
```

不得猜测后当作已确认事实。

# 四、阶段二：研究密码处理与认证机制

## 4.1 密码处理

检查客户端是否对密码进行处理。

可能存在：

- 直接通过 HTTPS 提交。
- 摘要计算。
- RSA 加密。
- AES 加密。
- 其他客户端认证处理。

上述只是可能性，不代表项目已经确认采用其中某一种。

需要明确：

1. 密码是否经过客户端处理。
2. 使用的算法及参数是否能够从合法客户端行为中确认。
3. 是否需要服务端提供随机数。
4. 是否存在时效性参数。
5. 是否存在服务端认证挑战。
6. 是否支持通过标准 Python 库实现。

如果无法确认，不允许使用猜测算法反复尝试线上登录。

## 4.2 验证码与二次认证

确认是否需要：

- 图形验证码。
- 短信验证码。
- 设备确认。
- 其他人工身份验证。

若存在验证码，应实现正常的人机交互流程。

例如：

```
请输入账号：2024xxxxxx
请输入密码：********

正在验证登录信息……

系统要求短信验证码。
请输入验证码：******

登录成功。
```

不得实现验证码绕过、暴力识别或批量试探机制。

## 4.3 登录错误分类

需要区分：

- 账号不存在。
- 密码错误。
- 验证码错误。
- 认证步骤不完整。
- Token 获取失败。
- 网络超时。
- 服务端异常。
- 账号被临时限制。
- 不支持当前登录方式。

错误信息必须清晰。

不要把所有异常统一显示为：

```
登录失败
```

同时禁止在错误信息中输出密码或完整 Token。

# 五、阶段三：最小可行性验证

验证是否能够：

# 六、阶段四：实现命令行登录模块

如果前面的研究已经确认技术可行，则开始实现。

## 6.1 建议目录

```
lejianPE/
├── auth/
│   ├── __init__.py

│   ├── credential.py
│   └── session.py
├── lejian.py
├── menu.py

└── ...
```

不强制采用上述结构。

Agent 可以依据当前项目规模使用更简单的实现，但不允许将大量认证处理逻辑直接堆积到 `lejian.py`。

## 6.2 模块职责

### login.py

负责：

- 构造登录请求。
- 提交用户认证信息。
- 处理登录响应。
- 处理必要的验证码流程。
- 将登录结果转换为内部会话数据。

### credential.py

负责：

- 读取用户名。
- 安全读取密码。
- 处理用户取消。
- 不回显密码。
- 不记录密码。

建议：

```
import getpass

username = input("请输入账号：").strip()
password = getpass.getpass("请输入密码：")
```

不得要求用户将明文密码写入 `config.json`。

### session.py

负责：

- 生成与现有程序兼容的会话状态。
- 保存 Token。
- 维护必要用户信息。
- 处理登录成功后的状态更新。

不要另外开发一套与现有 `Client.refresh()` 冲突的 Token 管理系统。

# 七、阶段五：与现有认证系统对接

## 7.1 保留 state.json 格式

新认证方式最终仍然生成现有代码可使用的会话数据。

需要兼容：

```
{
  "accessToken": "<access_token>",
  "refreshToken": "<refresh_token>",
  "accessTokenExpires": 1792778769293,
  "schoolId": "<school_id>",
  "semesterId": "<semester_id>"
}
```

这是示意结构。

具体字段需要对照当前 `state.json` 生成代码及实际业务调用要求，不得省略现有程序依赖的字段。

## 7.2 保留 Token 自动刷新

现有：

```
Client.refresh()
Client.ensure_token()
```

应继续正常工作。

新登录模块只负责建立初始认证会话。

理想流程：

```
第一次使用
    ↓
账号密码登录
    ↓
保存 Token
    ↓
后续正常运行
    ↓
AccessToken 即将过期
    ↓
自动刷新 Token
    ↓
持久化新 Token
```

Refresh Token 失效时，再提示用户重新登录。

## 7.3 安全保存

要求：

1. 登录成功前不覆盖原有 `state.json`。
2. 必须验证新会话包含所有必要字段。
3. 保存前备份旧状态。
4. 使用临时文件加原子替换。
5. 保存失败时不破坏原有状态。
6. 不保存明文密码。
7. 不在终端或日志打印完整 Token。
8. 确保 `state.json` 不进入 Git。
