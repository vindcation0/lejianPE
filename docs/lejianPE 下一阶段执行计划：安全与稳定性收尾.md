# lejianPE 下一阶段执行计划：安全与稳定性收尾

> 项目：vindcation0/lejianPE
> 阶段：安全加固与稳定性验收
> 执行方式：交由 Coding Agent 分阶段执行
> 核心原则：不增加新功能、不进行无关重构、不破坏现有抢课业务。

## 一、项目现状与本阶段目标

目前项目已经具备比较完整的工程结构：

- AuthManager：统一认证管理
- CredentialStorage：凭据存储与加密
- StateStore：状态持久化
- RegistrationManager：报名流程管理
- RecoveryManager：异常恢复
- ReconciliationManager：状态对账
- CircuitBreaker：服务端故障熔断
- RetryPolicy：请求重试策略
- InstanceLock：单实例保护
- AuditLogger：审计日志

本阶段不再以增加功能为目标，而是针对现有代码进行安全审查、缺陷修复、自动化测试和真实环境验证。

### 最终目标

1. 消除代码库中可能存在的真实认证材料和个人信息。
2. 确保 DPAPI 加密失败时绝不回退到明文。
3. 保证不同账户之间的会话数据不会相互污染。
4. 提高认证异常的可诊断性。
5. 补齐关键路径自动化测试。
6. 建立自动化测试 CI。
7. 完成真实环境下的多轮 Token 刷新及抢课验证。

### P0-02：修复 DPAPI 加密失败时回退明文的问题

**涉及文件：**

- `core/credential_storage.py`
- `tools/login_cli.py`
- `tests/test_auth.py`
- `README.md`

**问题说明：**

当前 `CredentialStorage.save_credential()` 中：

当用户要求 DPAPI 加密，但加密过程失败时，代码会将 signDigital 以明文方式写入 JSON。

这是不合理的安全降级行为。

加密失败必须停止操作，而不是降低安全级别。

**执行任务：**

- 

  删除 DPAPI 加密失败后回退明文的逻辑。

- 

  加密失败时抛出明确的 CredentialError。

- 

  Windows 默认采用 DPAPI 安全存储。

- 

  DPAPI 不可用或执行失败时，拒绝保存。

- 

  保存前保留原有凭据，不允许失败操作破坏旧文件。

- 

  使用临时文件写入。

- 

  写入完成后重新读取 JSON。

- 

  验证 `signDigitalEncrypted` 存在。

- 

  验证明文 `signDigital` 不存在。

- 

  验证 DPAPI 解密后内容正确。

- 

  验证全部通过后才允许报告保存成功。

- 

  修复 `--encrypt` 成功提示，不能仅根据函数执行完毕就判断加密成功。

**兼容性要求：**

- Windows：默认优先 DPAPI。
- 非 Windows：明确说明 DPAPI 不可用，不得伪装成已加密。
- 如果保留明文兼容模式，必须明确告知用户风险，不能静默降级。

**验收标准：**

| 测试场景             | 预期结果       |
| -------------------- | -------------- |
| DPAPI 正常加密       | 成功           |
| DPAPI 正常解密       | 成功           |
| DPAPI 加密失败       | 拒绝保存       |
| DPAPI 解密失败       | 返回明确错误   |
| 加密失败且旧凭据存在 | 旧凭据保持完整 |
| 加密后检查 JSON      | 不存在明文签名 |
| Windows 默认初始化   | 使用 DPAPI     |

## 三、P1：认证与状态管理可靠性

### P1-01：修复不同账户之间的状态污染

**涉及文件：**

- `core/auth_manager.py`
- `tests/test_auth.py`

**问题说明：**

当前 `save_state_atomically()` 会读取旧 state.json：

```
new_state = dict(old_state) if old_state else {}
```

随后部分身份字段使用旧数据作为 fallback。

例如：

```
"realName": str(
    login_data.get("realName") or new_state.get("realName") or ""
).strip()
```

这可能导致切换账户后，新账户的 Token 与旧账户的个人信息同时存在于 state.json。

**执行任务：**

- 

  明确区分账户身份字段和非身份配置字段。

- 

  新账户登录成功时，不继承旧账户的身份信息。

- 

  对 userId、realName、mobile、organizationUserNumber、campusId 等字段进行一致性处理。

- 

  不允许旧账户身份信息在新账户会话中残留。

- 

  保留正常的原子写入和备份能力。

- 

  检查模拟器同步与命令行登录两条路径的兼容性。

**必须增加的测试：**

场景一：

账户 A 登录，生成 state.json。

账户 B 登录，重新生成 state.json。

验证：

- accessToken 属于 B。
- refreshToken 属于 B。
- schoolId 属于 B。
- userId 不会错误继承 A。
- realName 不会错误继承 A。
- mobile 不会错误继承 A。
- organizationUserNumber 不会错误继承 A。
- campusId 不会错误继承 A。

场景二：

账户 B 部分字段缺失。

验证不会错误使用账户 A 的身份字段填充。

### P1-02：改善学期信息获取的异常处理

**涉及文件：**

- `core/auth_manager.py`
- `tests/test_auth.py`

**问题说明：**

当前 `fetch_semester_info()` 使用：

```
except Exception:
    pass
```

这会隐藏真实错误原因。

**执行任务：**

- 

  不再无条件吞掉异常。

- 

  区分网络异常、HTTP 异常、JSON 解析异常、业务状态失败。

- 

  保留服务端返回的必要诊断信息。

- 

  对敏感字段进行脱敏。

- 

  保持认证异常分类体系。

- 

  semesterId 获取失败时，明确说明失败原因。

- 

  不允许在必要会话字段缺失时写入不完整 state.json。

**验收标准：**

能够区分：

- 网络超时。
- HTTP 401。
- HTTP 500。
- 服务端业务错误。
- JSON 格式异常。
- semesterId 缺失。

同时不能在日志中泄漏 Token 或认证签名。
