**项目：** [vindcation0/lejianPE](https://github.com/vindcation0/lejianPE)

**执行原则：** 最小改动、保持兼容、先测试后提交。

## 一、任务背景

目前项目存在两个问题：

### 问题 1：命令行菜单 2 和 6 功能重复

当前行为：

- 菜单 2：查看活动列表、当前课表占用、已报名活动、符合条件的可抢活动。
- 菜单 6：查看当前教学周、课表占用情况以及下一教学周的占用情况。

菜单 2 已经包含菜单 6 的部分展示功能，职责不够清晰。

### 问题 2：当前教学周依赖静态配置

目前 `lejian.py`：

```
def current_week(cfg, tt):
    return int(cfg.get("current_week") or tt.get("current_week") or 8)
```

`config.json` 中存在：

```
{
  "current_week": 8
}
```

导致程序始终读取配置中的固定周次，不会随着日期自动推进。

项目已经存在日期换算函数：

```
def week_of(date_obj, tt):
    d = datetime.date.fromisoformat(tt["week1_monday"])
    return (date_obj - d).days // 7 + 1
```

应该复用现有日期计算机制，不要重复实现一套周次计算逻辑。

# 三、P0：实现教学周自动计算

## 3.1 修改目标

以 `timetable.json` 中的：

```
{
  "week1_monday": "2026-08-31"
}
```

作为整个学期的日期锚点。

程序根据系统当前日期自动计算教学周。

计算规则：

- 第一教学周周一至周日为第 1 周。
- 每经过一个星期一，教学周自动增加 1。
- 不依赖用户每周修改配置文件。
- 不依赖程序启动时间。
- 电脑关机、休眠或程序长时间未运行后，重新启动也必须得到正确周次。

## 3.2 修改 current_week()

修改文件：`lejian.py`

建议将原来的：

```
def current_week(cfg, tt):
    return int(cfg.get("current_week") or tt.get("current_week") or 8)
```

改为：

```
def current_week(tt):
    today = datetime.date.today()
    return week_of(today, tt)
```

可以根据项目现有结构进一步完善异常处理和学期状态判断。

重要要求：

1. 不再读取 `config.json` 的 `current_week`。
2. 不再使用默认第 8 周作为兜底。
3. 统一复用 `week_of()`。
4. 不允许在多个函数中分别编写周次计算逻辑。

## 3.3 统一修改所有调用位置

检查整个项目中所有 `current_week()` 的调用。

重点检查：

- `cmd_list()`
- `cmd_timetable()`
- `cmd_grab()`

全部统一为动态计算方式。

同时检查其他 Python 文件中是否存在直接读取 `current_week` 的逻辑。

确保：

- 菜单 2 显示正确。
- 菜单 6 显示正确。
- 抢课启动时显示正确。
- 抢课时的周次和冲突判断仍然正确。

特别注意：

`week_of_item()` 根据活动 `startTime` 计算活动实际所属教学周的现有逻辑必须保留。

不能将所有活动都强行归入系统当前教学周。

## 3.4 学期边界处理

不要简单地把计算结果强行限制在 1 至学期总周数。

建议明确区分：

- 开学前：尚未开学。
- 正常教学期间：第 1 周至学期最后一周。
- 学期结束后：已超过设定教学周数。

在显示层提供清晰状态。

对于学期范围之外的日期，不得错误地显示为正常教学周。

不要擅自修改报名提交规则；如果发现抢课窗口与学期范围存在冲突，应明确提示并保留原有安全保护。

# 四、P1：保存和恢复学期总周数

## 4.1 当前问题

`editor.html` 已经有学期总周数输入框：

```
<input
    type="number"
    id="total-weeks"
    value="16"
    min="1"
    max="30"
>
```

但是目前保存课表时没有把 `total_weeks` 写入 JSON。

导致用户设置的学期总周数可能在重新打开编辑器后丢失。

## 4.2 修改涉及文件

- `timetable/models.py`
- `timetable/validator.py`
- `timetable/compatibility.py`
- `timetable/editor.html`
- `tools/editor_server.py`（如有必要）

## 4.3 新版数据格式

建议在现有 Schema v2 基础上增加字段：

```
{
  "schema_version": 2,
  "week1_monday": "2026-08-31",
  "total_weeks": 16,
  "busy_slots": []
}
```

不需要为了增加这个可选字段而随意升级 Schema 版本。

要求：

1. `Timetable` 模型增加 `total_weeks`。
2. `to_dict()` 保存该字段。
3. `from_dict()` 正确恢复该字段。
4. `editor.html` 保存时传入 `total_weeks`。
5. 编辑器读取时恢复 `total_weeks`。
6. 修改总周数后，周次筛选器和自定义周次选择同步更新。
7. 不得破坏现有 `busy_slots` 数据。
8. 旧版 JSON 没有 `total_weeks` 时，默认使用 16，或者遵循项目已经存在的合理默认值。
9. 旧版 Schema v1 的迁移逻辑必须继续正常工作。

注意：

修改总周数不能静默删除已有课程周次数据。

如果已有课表中的周次超出新设置的总周数，应提示用户并要求合理处理，不能擅自修改原始课表。

# 五、P1：校验第一教学周日期

修改文件：`timetable/validator.py`

目前 `week1_monday` 是整个周次计算的基础。

必须确保用户填写的日期确实是星期一。

例如：

```
2026-08-31：星期一，合法
2026-09-01：星期二，非法
```

校验要求：

1. 必须是合法的 ISO 日期格式。
2. 必须是星期一。
3. 不合法时抛出明确的 `ValidationError`。
4. 保存失败时不得覆盖原来的课表。
5. 保持现有备份和原子写入机制。

建议错误提示：

```
第一教学周日期必须为星期一，请检查 week1_monday。
```
