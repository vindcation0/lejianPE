# 2026-10-25 抢课故障报告

> 首次实战（14:00 开抢）期间的服务器故障记录、影响、根因与改进。
> 数据来源：程序日志 `logs/run-20261025.log`、故障前后的人工探测、工单式复盘。

## 一、摘要

**服务器在 14:00:00 开抢瞬间被打崩，持续约 6–7 分钟。**

表现为 HTTP 500 / 502 / 503 混合出现、单次请求从 0.2 秒劣化到 15 秒超时。
程序在此期间基本空转，并对「实际已成功」的提交误判为失败、持续重试。

**最终结果：抢到 3 节（目标 2 节），已退掉 1 节，修正为 2 节。**

## 四、故障特征

### 4.1 错误码分布（来自日志，仅覆盖 14:05 之后）

| 类型 | 次数 | 首次 | 末次 |
|---|---:|---|---|
| HTTP 503 | 26 | 14:06:23 | 14:06:28 |
| HTTP 502 | 6 | 14:06:17 | 14:06:18 |
| 超时（HTTP -1） | 4 | 14:05:20 | 14:06:06 |

> 14:00–14:04 的 500 未被记录，因为当时程序**在拉取失败时不写日志**（已修复，见六节）。

### 4.2 响应时长

| 阶段 | 典型耗时 |
|---|---|
| 正常（故障前） | 0.18–0.25 s |
| 故障中・快速失败 | 0.15–0.25 s（直接 500/503） |
| 故障中・超时 | 15.0 s（当时的超时上限） |
| 故障中・侥幸成功 | **11.6 s** |

### 4.3 错误信息原文

拉取接口被网关打断时，返回体里带着**服务端内网地址**：

```
HTTP 500
syscall:getsockopt(..) failed: Connection refused: /10.23.0.181:8120
syscall:getsockopt(..) failed: Connection refused: /10.23.0.231:8120
```

提交接口：

```
HTTP 502 / HTTP 503
```

业务层（说明请求已穿过网关、被后端处理过）：

```
该类型活动已达到每周上限
该类型活动已达到每日上限
```

## 五、根因分析

### 5.1 直接原因：瞬时并发超过承载

14:00:00 全校同时点击，网关层开始 5xx。后端出现 `Connection refused`，
说明上游服务在高压下直接拒连——不是限流，是**扛不住**。

### 5.2 关键问题：网关错误发生在业务处理之后

这是本次多抢一节的根源：

```
浏览器/程序 ──提交──> 网关 ──转发──> 业务服务（已写入报名）
                        ↑
                    回程失败，返回 503
```

**程序收到 503，但名额已经被扣掉了。** 于是程序判定失败、继续重试，
最终一条请求被重复计入。

### 5.3 加剧因素：我们自己的两个进程

14:03–14:06 期间，旧的 `grab now` 与应急脚本**同时在提交**。
服务端的「每周上限」校验不是原子操作，两个并发请求都能通过检查。

### 5.4 放大因素：超时设置过长

初版超时 15 秒。一次超时 = 一次轮询彻底白等，
4 分钟只完成 20 次轮询，几乎失去竞争能力。

## 六、暴露的自身缺陷

| # | 缺陷 | 后果 | 状态 |
|---|---|---|---|
| 1 | 拉取失败不写日志 | 事后无法还原故障时段 | ✅ 已修 |
| 2 | 超时 15s 过长 | 轮询退化为 15s 一次 | ✅ 已改 6s |
| 3 | 分页两次请求 | 失败概率与耗时翻倍 | ✅ 已改为一次 200 条 |
| 4 | 失败后干等 poll 间隔 | 重试密度低 | ✅ 已改 0.05s |
| 5 | 只信响应码 | 把「已成功」当失败，重复提交 | ⚠️ 部分（见下） |
| 6 | 允许并发多进程 | 突破服务端上限 | ⚠️ 靠操作纪律 |

### 关于第 5 条

根本解法是**提交后用 `isRegister` 复核真实状态**，而不是凭响应码判断。
本次是人工事后复核才发现的，程序自身没有这个闭环。

下一轮应加入：抢满后立刻复核一次，若超额则自动退掉多余的一条。

## 七、改进清单

### 已完成

- 默认超时 15s → 6s；活动列表一次拉 200 条
- `activities()` 内部重试 3 次
- 失败后 0.05s 快速重试
- **新增故障事件日志**：文件 `logs/events-YYYYMMDD.jsonl`，
  按「状态变化」记录，形如
  ```json
  {"t":"2026-10-31T14:00:03","event":"list_fail","http":500}
  {"t":"2026-10-31T14:06:41","event":"list_ok","outage_sec":398}
  ```
  下次故障可以直接算出中断时长与起止点。
- 退课脚本 `tools/cancel_one.py`（按日期精确退，不误伤）

### 待做

- [ ] 抢满后自动复核 `isRegister`，超额自动退课
- [ ] 提交超时（HTTP -1）时，不再立即重试，先复核一次状态
- [ ] 启动时检测重复进程，避免并发提交
- [ ] 记录每次提交的完整请求/响应到独立文件，便于事后举证

## 八、结论

这次「服务器太垃圾」不是借口，是**真实且可复现的运行环境特征**：

1. 开抢瞬间必然过载，5xx 是常态，不是异常
2. 5xx 不代表业务失败，**响应码在此场景下不可信**
3. 唯一可信的事实是 `isRegister` 的最终状态

所以下一轮的设计原则应该是：
**宁可少发、不可重复；发完必复核。**
