## 1. 修改摘要

本阶段严格遵循「分阶段检查、最小改动、测试先行、不进行无关重构」的原则，围绕登录认证、Token 管理、课表冲突、状态机流转与服务端对账五个核心业务方向完成了可靠性优化闭环。

## 2. 问题闭环清单

| 编号 | 核心问题 | 原有表现与风险 | 修复方案 | 验证结果 |
| :---: | :--- | :--- | :--- | :---: |
| **L01** | 登录失败破坏旧会话风险 | 若认证失败时异常处理不周，可能存在部分流程写入残缺 `state.json` | `AuthManager` 保证认证失败绝不触碰现有 `state.json` 文件，并补充专项用例验证 | **PASS** (`test_L01`) |
| **L02** | 签名失效诊断准确性 | 服务端返回 50004 时容易误导用户以为是账号密码错误 | 捕获 50004 与「签名」关键词，明确提示签名材料失效及密码修改后的重新采集指引 | **PASS** (`test_L02`) |
| **L03** | 抓包异常退出遗留代理 | 用户按 Ctrl+C 中断抓包时，模拟器系统代理停留在 `127.0.0.1:8081` 导致模拟器断网 | 引入 `cleanup_resources()` 在 `finally` 块中强制恢复代理至 `:0` 并清除 reverse 映射 | **PASS** (`test_L06`) |
| **TK01** | Token 刷新数据残缺覆盖 | 若服务端刷新接口返回缺少 `accessToken` 或过期时间，可能破坏当前会话 | 在 `Client.refresh()` 增加必要字段与时间戳正整数强校验，数据残缺立即阻断 | **PASS** (`test_TK01`, `test_TK02`) |
| **TK02** | RefreshToken 轮换持久化 | 刷新时就地修改内存变量，若持久化保存异常会导致内存与磁盘状态不一致 | 构造新字典先落盘（生成 `.bak` 备份并通过回读校验）再更新内存 `self.s` | **PASS** (`test_TK03`, `test_TK04`) |
| **TK03** | 并发触发重复刷新冲突 | 多个请求并发发现 Token 临期时同时调用 `refresh()`，导致多次网络请求与 RefreshToken 轮换冲突失效 | `Client` 引入 `threading.RLock()`，实现 `ensure_token()` 线程安全双重检查锁定，只刷新一次并共享新 Token | **PASS** (`test_TK05`) |
| **CF01** | 活动时间解析异常漏洞 | `activity_slot()` 未校验 `st <= 0` 或 `en <= st`，遇到脏数据可能生成错误分钟数 | 增加前置范围校验，时间戳非法时立即返回 `None`，上层拒绝放行 | **PASS** (`test_CF01`) |
| **CF02** | 服务端冲突检查异常漏判 | `check_conflict` 接口超时或 500 时返回 `None`，调用方以布尔假求值误当作「无冲突」继续提交 | 明确采用三态判断：`True` 冲突阻断，`False` 放行，`None` 视为无法确认并安全阻断 | **PASS** (`test_CF02`) |
| **SM01** | 报名提交遇到 401 盲目重试 | 遇到 401 若直接重发 `signUp`，由于报名具有实际副作用，可能导致服务端重复下单 | 请求分类为 `UNAUTHORIZED`，状态机记录 UNKNOWN 并转入只读复核流程，复核确认未报名后才允许重新评估 | **PASS** (`test_SM01`) |
| **SM02** | 报名提交遇到 429 高频重试 | 遇到 429 若高频重发可能招致更严重的 IP 或账号封禁 | 请求分类为 `RATE_LIMITED`，状态机记录 UNKNOWN 并转入只读复核，禁止盲目重发 | **PASS** (`test_SM02`) |
| **RC01** | 对账结果与历史已报混淆 | `ResultReporter` 将服务端返回的全部已报活动算作本轮成功，导致本轮成功数虚高 | 根据本轮尝试活动的 `activity_id` 进行精确求交，严格分离「本轮成功」与「既有历史已报」 | **PASS** (`test_RC01`) |
| **RC02** | 合法空列表误判对账失败 | 当服务端确实无任何已报活动（`total=0, complete=True`）时，旧逻辑误判为「活动列表为空」失败 | 增加 `complete=True and total=0` 检查，合法空列表判定为对账成功（0 节） | **PASS** (`test_RC02`) |
| **RC03** | 异常活动时间静默丢弃漏算配额 | 对账遇到时间戳损坏的已报活动时被 `continue` 跳过，导致无法计入每周/每日配额 | 收集异常活动至 `unparsed_items`，计入已报总数并在报告中呈现，杜绝静默漏算 | **PASS** (`test_RC03`) |

## 5. 生产环境验证边界说明

严格遵循实事求是原则记录离线测试与真实生产服务端的操作边界：

### 5.1 已通过离线自动化测试充分验证的范围
1. **密码登录与信封解密**：AES 信封组装、动态密钥派生、`signDigital` 材料解密，经 A01～A15 与标准向量充分验证；
2. **Token 自动刷新与 RLock 并发控制**：多线程并发调用 `ensure_token()` 仅物理刷新一次，响应残缺拒绝保存，持久化失败内存回滚；
3. **课表冲突半开区间与三态校验**：`08:00~09:35` 与 `09:35~11:10` 不冲突、重叠冲突、奇偶周、不连续周次以及服务端检查接口异常安全阻断；
4. **状态机 UNKNOWN 安全屏障与 401/429 隔离**：提交返回 401/429 时冻结队列，转入只读复核，严禁盲目重发；
5. **服务端逐活动对账与历史口径隔离**：严格按 `activity_id` 区分当前轮次提交与历史既有已报活动，异常时间活动进入 `unparsed_items` 不漏算。

### 5.2 生产服务端尚未且不宜发起破坏性测试的边界
1. **生产真实长效 Token 过期测试**：当前用户生产环境 `state.json` 包含长期有效的日常打卡凭据。为保障用户正常考勤会话不受损，严禁在生产端故意使 Token 失效发起破坏性测试；
2. **生产高频真实密码登录**：学校官方服务端部署了风控监测机制，高频提交账号密码极易触发账号锁定或验证码阻断；
3. **生产真实抢课报名与退课**：生产活动名额受学校学期排课与各学院名额严格限制，禁止向生产环境真实活动发送测试性报名与退课请求。
