## 1.2 本阶段目标

围绕五个核心方向开展可靠性优化：

1. 登录稳定性：保证认证流程可诊断、可恢复，不破坏原有有效会话。
2. Token 自动刷新：保证 Token 续期可靠，避免刷新失败、轮换丢失和重复刷新。
3. 课表冲突判断：保证候选活动不会因为时间计算、数据异常或服务端检查失败而错误放行。
4. 抢课状态机：保证异常情况下不重复提交、不错误释放名额、不丢失未决状态。
5. 服务端结果对账：保证最终报告真实反映服务端报名状态，不把未知结果错误统计为失败或成功。

最终目标：

**即使发生网络中断、程序崩溃、Token 过期、服务端异常、分页数据不完整，也能够尽可能准确地恢复真实业务状态，并且不产生未经确认的重复报名。**

## 3.2 重点优化任务

### TK01：刷新结果完整性校验

检查 `Client.refresh()`。

当前刷新逻辑会更新：

- accessToken
- refreshToken
- accessTokenExpires

需要加强：

1. 验证响应是否包含合法 accessToken。
2. 验证 RefreshToken 是否有效。
3. 验证过期时间是否有效。
4. 验证响应格式和业务状态码。
5. 不允许使用残缺刷新结果覆盖有效会话。

如果服务端没有返回新的 RefreshToken，是否允许继续使用旧 RefreshToken，需要以实际协议行为为依据，不能自行假设。

### TK02：刷新与持久化原子性

重点检查当前 `Client.refresh()` 对 `save_json()` 的使用。

需要确认：

- 保存是否原子化。
- 是否存在临时文件写入。
- 是否存在写入后的回读校验。
- 是否保留原始 state.json 备份。
- 刷新失败是否会破坏原有 Token。

建议参考：

```
AuthManager.save_state_atomically()
```

但不要直接复制两套状态保存逻辑。

建议形成统一的安全会话更新机制：

1. 获取刷新响应。
2. 验证所有必要字段。
3. 构造新的完整会话对象。
4. 持久化并验证。
5. 持久化成功后再更新当前 Client 内存状态。

任何一步失败，都不得将不完整的新会话当作有效会话。

### TK03：避免重复刷新

检查多个请求同时发现 Token 临期时的行为。

目标：

- 同一个 Client 同一时间只执行一次刷新。
- 其他请求等待刷新完成。
- 成功后共享新 Token。
- 失败后明确返回刷新异常。
- 不允许多个刷新请求互相覆盖 RefreshToken。

如果现有单实例运行机制已经足以保证该场景，应以测试证明，不要无意义增加锁。

### TK04：401 自动恢复边界

区分两种请求：

**查询请求：**

允许：

1. 查询返回 401。
2. 刷新 Token 一次。
3. 使用新 Token 重试查询一次。
4. 再次失败则返回异常。

**报名提交请求：**

报名请求具有实际副作用。

禁止：

- 遇到 401 后无条件重新发送 signUp。
- 因刷新失败而无限重复报名。
- 在未确认服务端状态前释放潜在名额。

建议流程：

1. 提交返回 401。
2. 记录认证异常。
3. 必要时刷新 Token。
4. 通过只读服务端接口复核报名状态。
5. 完整确认未报名后，重新执行资格检查。
6. 只有满足安全条件才允许进入 RETRYABLE。

如果服务端响应语义不足以确认请求未执行，则保持 UNKNOWN。

### TK05：Token 失效后的恢复策略

需要覆盖：

- AccessToken 过期。
- RefreshToken 过期。
- RefreshToken 轮换成功。
- 刷新接口超时。
- 刷新接口 5xx。
- 刷新返回残缺数据。
- 新 Token 持久化失败。
- 重启后加载新旧 Token。
- 连续两次 401。

## 3.3 新增测试建议

- TK01：刷新响应缺少 accessToken。
- TK02：刷新响应缺少 expires。
- TK03：RefreshToken 轮换后正确持久化。
- TK04：刷新持久化失败保留旧状态。
- TK05：多个请求同时触发刷新。
- TK06：查询请求 401 只刷新一次。
- TK07：刷新失败后查询不无限重试。
- TK08：报名请求 401 不直接重复提交。
- TK09：程序重启后使用新 RefreshToken。
- TK10：连续 401 后进入安全失败状态。

验收标准：

- Token 刷新不会丢失有效 RefreshToken。
- 不发生重复刷新覆盖。
- 查询请求最多自动恢复一次。
- 报名请求不发生未经确认的自动重复提交。
- 刷新失败时能够安全恢复或要求重新登录。

## 4.2 需要重点检查的问题

### CF01：本地冲突判断准确性

重点检查：

```
TimeSlot.conflict_with()
```

当前使用：

```
self.start_min < end_min and self.end_min > start_min
```

这是一种半开区间判断方式。

需要保证：

- 08:00～09:35 与 09:35～11:10 不冲突。
- 08:00～09:35 与 09:00～10:00 冲突。
- 不同星期不冲突。
- 不同教学周不冲突。
- 相同时间但奇偶周不同不冲突。
- 多段不连续周次正确处理。

不能仅依赖课程名称判断冲突。

### CF02：候选活动时间解析

重点检查：

```
activity_slot()
```

确保：

- 活动时间可以正确解析。
- 开始时间和结束时间合法。
- 缺失时间时不允许静默放行。
- 时间格式异常时记录具体原因。
- 活动时间和课表时间使用统一的分钟单位。

### CF03：候选筛选与提交前二次校验

当前 `pick_targets()` 已经结合：

- 用户课表。
- 配置中的 busy_slots。
- 服务端已报名活动。
- 本轮已成功活动。

但还需要确认：

**候选筛选阶段和真正提交阶段是否使用完全一致的冲突规则。**

要求：

1. 候选进入队列前进行本地冲突检查。
2. 真正提交前重新检查。
3. 重新计算当前教学周。
4. 重新检查每日和每周名额。
5. 重新考虑本轮已经成功报名的活动。
6. 不允许使用过期候选数据直接提交。

### CF04：服务端冲突检查失败时的处理

重点检查：

```
Client.check_conflict()
```

当前实现可能返回：

- True：存在冲突。
- False：没有冲突。
- None：接口异常或无法确认。

但当前调用方使用：

```
if c.check_conflict(act_item.get("id")):
    return False, "服务端判定冲突"
```

并且异常会被忽略。

这存在一个重要问题：

**服务端检查失败可能被当作没有冲突。**

建议明确采用三态判断：

| 结果  | 含义       | 处理               |
| ----- | ---------- | ------------------ |
| True  | 明确冲突   | 禁止提交           |
| False | 明确无冲突 | 继续资格检查       |
| None  | 无法确认   | 默认阻断并记录原因 |

如果用户明确关闭服务端冲突检查，则按照配置执行，但必须保留本地冲突检查。

不能把接口异常当作无冲突。

### CF05：时间和时区一致性

当前项目存在使用 `datetime.fromtimestamp()` 的逻辑。

需要确认：

- 服务端 startTime 的单位。
- 服务端时间戳对应的时区。
- 本地系统时区是否可能与服务端业务时区不同。
- 每日限制是否按照学校业务日期计算。
- 教学周是否始终按照 week1_monday 计算。

不要直接假定所有用户的系统时区一致。

应以接口协议确认的时区为准，避免跨时区造成日期和教学周计算错误。

## 5.2 状态机优化要求

### SM01：明确合法状态转换

建议将状态转换关系明确记录并进行统一检查。

核心状态：

```
PENDING
   |
   v
SUBMITTING
   |
   +------> SUCCESS
   |
   +------> FAILED
   |
   +------> UNKNOWN
                |
                v
            VERIFYING
                |
                +------> SUCCESS
                |
                +------> RETRYABLE
                |
                +------> UNKNOWN
```

RETRYABLE 不代表可以直接重新发送请求。

必须重新执行：

- 报名窗口检查。
- 活动是否仍然有效。
- 名额检查。
- 每日限制。
- 每周限制。
- 课表冲突检查。

### SM02：UNKNOWN 安全屏障

这是项目最重要的安全机制之一。

必须坚持：

**一个报名请求结果未知时，不允许继续提交其他候选。**

以下情况均应该进入安全处理：

- 网络超时。
- HTTP 500。
- HTTP 502。
- HTTP 503。
- HTTP 504。
- 响应格式异常。
- 服务端业务结果不明确。
- 复核接口失败。
- 活动列表不完整。

只有服务端能够明确确认报名状态时，才能解除冻结。

### SM03：报名请求禁止盲目重试

必须严格区分：

查询请求与报名提交请求。

查询请求可以有限次重试。

报名请求不得自动重复发送。

除非已经通过完整服务端状态确认未报名，否则不得重新提交同一活动。

### SM04：HTTP 401 和 429 的明确处理

当前 RequestManager 已经将这两类响应分类为：

- UNAUTHORIZED
- RATE_LIMITED

但需要进一步检查 RegistrationManager 对这两种分类的处理。

要求：

- 401：进入认证恢复与只读复核流程，不允许直接重复 signUp。
- 429：尊重限流，不能进行高频重试。
- 如果服务端是否执行请求无法确认，保持 UNKNOWN。
- 只有完整复核确认未报名后，才能重新评估。

### SM05：并发与状态持久化

检查：

- 同一活动是否可能被重复提交。
- SQLite 状态更新是否原子。
- 状态库不可写时是否阻断报名。
- 多进程启动是否被 InstanceLock 阻止。
- 程序意外终止后是否能恢复 SUBMITTING。
- 状态恢复时是否存在重复统计。

如果现有单实例机制已经覆盖相关问题，优先补测试，不要无意义增加架构。

### SM06：熔断器与 UNKNOWN 配合

需要验证：

- 服务端持续 5xx 后进入 OPEN。
- OPEN 阶段不发送业务请求。
- 冷却结束后进入 HALF_OPEN。
- HALF_OPEN 只允许受控探测。
- 不完整活动列表不能恢复服务健康状态。
- Token 401 不应错误触发服务端故障熔断。
- RefreshToken 失效不能形成无限重试。

## 5.3 新增测试建议

- SM01：非法状态转换。
- SM02：同一活动重复提交拦截。
- SM03：状态库写入失败拒绝提交。
- SM04：提交过程中强制退出。
- SM05：重启恢复 SUBMITTING。
- SM06：重启恢复 UNKNOWN。

- SM08：复核成功解除屏障。
- SM09：完整复核未报名后允许重新评估。
- SM10：复核列表不完整继续冻结。
- SM11：401 不发生盲目重复提交。
- SM12：429 不发生高频重试。
- SM13：多个候选并发提交保护。
- SM14：熔断和 UNKNOWN 同时出现。

验收标准：

- 不完整数据不能解除安全屏障。

## 6.2 重点优化任务

### RC01：区分本地记录与服务端真实数据

必须明确两个数据来源：

**本地 SQLite：**

记录程序尝试做过什么。

**服务端活动列表：**

记录服务端最终实际报名情况。

不能把本地 SUCCESS 直接当成服务端最终成功。

不能把本地 FAILED 直接当成服务端最终失败。

最终结果必须以服务端实际状态为准。

### RC02：完整性检查

当前项目已经有 ActivityList 分页完整性标记。

需要确保最终对账：

1. 所有分页都成功获取。
2. 已获取数量与服务端 total 一致。
3. 没有中途分页失败。
4. 没有重复页或重复活动导致统计异常。
5. 不完整列表不参与最终结论。

尤其需要保留现有规则：

**活动列表中找不到目标活动，不能直接判断为未报名。**

### RC03：空列表处理

重点检查：

```
ReconciliationManager.reconcile()
```

当前空列表会直接返回对账失败。

需要区分：

- 服务端成功返回完整列表，且 total=0。
- 服务端请求失败。
- 返回数据结构异常。
- 分页未完成。
- 数据确实为空但没有完整性证明。

只有完整、合法的空列表才可以作为有效对账结果。

### RC04：异常活动数据处理

当前统计逻辑对部分 startTime 无法解析的活动会直接跳过。

需要避免：

服务端明明存在已报名活动，但由于时间解析失败，最终统计却没有计入每日或每周限制。

建议增加：

- 无法分类的活动数量。
- 无法解析的活动 ID。
- 解析失败原因。
- 对账是否因此降级为不完整。

不允许静默丢弃可能影响配额判断的数据。

### RC05：区分本轮结果和历史报名

当前 ResultReporter 使用服务端返回的已报名活动列表统计最终成功数量。

需要明确区分：

1. 服务端当前总报名数量。
2. 本轮提交并确认成功的数量。
3. 本轮提交后经复核成功的数量。
4. 本轮确认未报名的数量。
5. 当前仍处于 UNKNOWN 的数量。
6. 历史已经报名的活动数量。

特别注意：

不能直接将服务端全部已报名活动数量等同于本轮成功提交数量。

报告中的每个统计数字必须有明确口径。

### RC06：逐活动对账

建议利用 activity_id 建立本地尝试记录与服务端活动列表的映射。

对于本轮每个尝试活动：

| 本地记录   | 服务端状态           | 最终处理         |
| ---------- | -------------------- | ---------------- |
| SUCCESS    | isRegister=true      | 确认成功         |
| UNKNOWN    | isRegister=true      | 复核成功         |
| UNKNOWN    | 完整列表中明确 false | 确认未报名       |
| UNKNOWN    | 活动缺失             | 继续 UNKNOWN     |
| UNKNOWN    | 列表不完整           | 继续 UNKNOWN     |
| SUBMITTING | 无法确认             | 保持未决         |
| 任意状态   | 服务端查询失败       | 不得生成确定结论 |

不要通过活动名称匹配，应使用稳定的 activity_id。

### RC07：对账失败后的报告

必须确保：

- 对账成功才能输出确定的服务端最终结果。
- 存在 UNKNOWN 时必须突出警告。
- 列表不完整时不能输出正常的最终成功结论。
- 无法确认的数量必须单独统计。
- 超额情况必须独立告警。
- 不允许将未知状态错误计入失败数量。

### RC08：时区和配额一致性

核实：

- startTime 的单位。
- 服务端业务时区。
- 每日配额日期计算。
- 教学周计算。
- 特殊活动分类。
- 每周普通活动上限。
- 每日普通活动上限。

对账与候选筛选必须采用统一的日期和教学周计算规则。
