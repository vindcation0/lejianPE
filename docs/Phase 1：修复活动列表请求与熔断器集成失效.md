## 二、必须解决的问题

当前已确认：

`Client.activities()` 在连续请求失败后返回 `complete=False`，而不是向上抛出异常。

主循环随后调用：

```
circuit_breaker.record_success(is_complete=False)
```

但 CLOSED 状态下失败计数会被清零，导致连续服务器故障无法正确触发熔断。

必须修复这个调用链。

## 三、具体要求

1. 建立统一的列表请求故障分类。
2. 确保每次实际 HTTP 请求失败都能被准确识别。
3. 基础设施故障正确累计。
4. 连续故障达到阈值后进入 OPEN。
5. OPEN 状态禁止正常列表轮询。
6. 冷却结束后进入 HALF_OPEN。
7. HALF_OPEN 只允许一次只读健康探测。
8. 只有取得完整列表才能恢复 CLOSED。
9. 不完整列表绝不能被视为健康恢复。
10. 401、403、400 等客户端异常不得被错误归类为基础设施故障。
11. 避免活动列表内部重试与外层轮询退避叠加。
12. 保留现有请求超时和配额业务逻辑。

特别注意：

不要通过简单增加 `record_failure()` 调用解决问题。

必须检查每次底层请求、内部重试、外层轮询之间的计数关系，防止重复统计。

## 四、测试要求

新增或完善测试：

- 连续三次 HTTP 500 触发 OPEN。
- 连续超时触发 OPEN。
- 502、503、504 正确分类。
- 401 不触发基础设施熔断。
- 400 不触发基础设施熔断。
- OPEN 状态不发送正常请求。
- HALF_OPEN 只允许一次探测。
- HALF_OPEN 探测失败重新 OPEN。
- HALF_OPEN 探测成功恢复 CLOSED。
- 不完整列表不能恢复 CLOSED。
- CLOSED 状态下连续故障不能清零失败计数。
- 内部重试不会造成重复累计。
- 完整列表恢复后允许正常运行。

测试必须使用 Mock，不允许调用真实抢课接口。
