# lejianPE：真正零模拟器登录协议研究与实现工作流程

> 项目：lejianPE
>
> 研究目标：实现完全不依赖 Android 模拟器的命令行账号密码登录
>
> 当前阶段：登录协议研究与独立签名能力评估
>
> 最终目标：用户首次使用、修改密码后重新登录，均不需要启动模拟器、ADB 或抓包工具。
>
> 执行原则：证据优先、阶段性交付、避免重复研究、保留现有可用方案。

# 一、项目现状与最终目标

## 1.1 当前已经实现的能力

当前项目并不是完全没有实现免模拟器登录。

已经完成：

1. 用户可以在命令行输入账号和密码。
2. 使用已获取的 signDigital。
3. 动态生成新的登录时间戳。
4. 重新构造 AES 登录信封。
5. 通过 HTTP 请求获取新的 AccessToken。
6. 获取 RefreshToken。
7. 获取 schoolId、semesterId。
8. 保存统一的 state.json。
9. 后续 Token 刷新不需要模拟器。

当前登录流程：

```
首次配置 / 修改密码
        |
        v
官方客户端登录
        |
        v
通过抓包获取 signDigital
        |
        v
保存 credential.json
        |
        v
日常命令行登录
        |
        v
输入账号密码
        |
        v
使用已有 signDigital
        |
        v
生成新的 AES 信封
        |
        v
获取 Token
        |
        v
进入原有抢课系统
```

当前最大的限制：

- 首次配置需要模拟器。
- 修改密码后需要重新获取 signDigital。
- 目前没有独立生成 signDigital 的完整实现。

因此，不能将当前方案描述为真正零模拟器。

## 1.2 最终目标

希望实现：

```
用户启动程序
      |
      v
python tools/login_cli.py
      |
      v
输入账号
      |
      v
输入密码
      |
      v
本地独立生成认证签名
      |
      v
构造动态 AES 信封
      |
      v
调用登录接口
      |
      v
获取 Token
      |
      v
初始化学校和学期信息
      |
      v
保存 state.json
      |
      v
登录完成
```

最终要求：

| 功能       | 目标         |
| ---------- | ------------ |
| 首次登录   | 不需要模拟器 |
| 修改密码   | 不需要模拟器 |
| 日常登录   | 不需要模拟器 |
| Token 刷新 | 不需要模拟器 |
| 查询活动   | 不需要模拟器 |
| 抢课       | 不需要模拟器 |
| 重新配置   | 不需要模拟器 |

不要求用户提前获取 signDigital。

不允许通过分发其他用户的 credential.json 实现免模拟器。

# 二、之前已经走过的弯路：禁止重复投入

Agent 在开始工作前，必须阅读：

```
docs/12-免模拟器登录-结论与弯路总结.md
```

并确认以下结论。

## 2.1 静态反编译原生库

之前已经尝试：

- 解析 ELF 符号表。
- 查找 JNI 函数。
- 还原 JNI 调用链。
- 分析 SHA1 相关函数。
- 分析程序头和代码段熵。
- 检查节区表。

已经确认：

- signDigital 相关实现位于 DexVMP 加固区域。
- 静态分析受到代码段加密和节区表破坏影响。
- 直接通过普通反编译工具还原函数的路线成本较高。

要求：

不要重新从头执行相同的 ELF 符号搜索、节区分析和哈希函数猜测。

除非获得新的 App 版本、未加固实现或其他明确证据，否则不重复这部分工作。

## 2.2 穷举哈希组合

之前已经完成 24,840 种组合测试。

涉及：

- SHA1。
- SHA256。
- MD5。
- 不同字符串拼接顺序。
- 不同分隔符。
- 不同编码。
- 不同盐值。
- 部分设备信息。

全部没有命中。

结论：

简单字符串拼接和常见哈希组合的假设已经被大量实验排除。

禁止继续增加随机组合、随机盐值和随机编码进行无目标穷举。

只有发现新的协议证据后，才允许建立新的验证假设。

## 2.3 旧 AES 信封重放

之前已经验证：

- 原始信封可以在有效期内重放。
- 旧信封超过约一小时后失效。
- 重新生成时间戳和 AES 信封可以继续登录。

因此：

不要再研究如何长期保存原始登录信封。

当前正确方向是保留已经验证的动态信封生成机制。

## 2.4 模拟器 Token 同步不等于签名更新

已经验证：

- 模拟器同步 Token 只会更新 Token。
- 不会自动更新 signDigital。
- 修改密码后旧签名会被服务端拒绝。

因此：

必须区分 Token 更新与认证签名更新。

## 2.5 Frida Hook

之前已经评估过 Frida Hook：

- 技术成本较高。
- 需要特定设备和运行环境。
- 需要额外分析加固代码。
- 对当前日常登录能力没有直接收益。

之前决定暂时放弃。

本轮不应默认重新投入 Frida。

如果后续确实需要动态分析，必须先确认有权分析相关客户端及其认证实现，并完成独立的成本收益评估。

不得以绕过客户端安全机制、设备证明或服务端认证控制为目标。

# 四、第二阶段：signDigital 独立生成可行性评估

优先级：P0

这是本轮最重要的研究任务。

但必须先进行可行性评估，不允许直接投入大规模逆向工作。

## 4.1 明确研究目标

我们真正想解决的问题：

能否在不依赖模拟器、不依赖个人抓包凭据的情况下，使用用户自己输入的账号和密码，通过有授权的协议或官方支持的方式完成认证签名生成？

需要区分：

1. 是否能够从已有合法资料中确定签名生成机制。
2. 是否能够获得官方支持的认证接口或 SDK。
3. 是否存在不依赖设备特定证明的合法认证路径。
4. 是否存在服务端挑战、动态凭据或设备绑定等额外要求。

如果协议要求不可替代的设备证明或服务端授权材料，就不能假设仅凭账号密码一定可以实现。

## 4.2 研究方向

按照优先级开展：

### 方向 A：已有资料和授权接口审查

检查：

- 官方提供的登录文档。
- 已公开的 SDK。
- 官方允许使用的认证接口。
- 已有合法测试环境。
- 当前项目已保存的协议文档。

目标是寻找不依赖模拟器的受支持认证路径。

### 方向 B：协议数据流分析

基于已经获得授权的资料，整理：

- 签名输入字段。
- 输入编码方式。
- 输出格式。
- 是否存在动态上下文。
- 是否存在账户相关参数。
- 是否存在 App 版本相关参数。

重点是建立可验证的数据流模型，而不是继续盲目猜测算法。

### 方向 C：动态分析可行性评估

如果静态资料不足，先评估是否有权在测试环境分析客户端行为。

必须明确：

- 设备和客户端的使用授权。
- 测试账号。
- 数据保护要求。
- 研究范围。
- 预期收益。
- 退出条件。

不得尝试绕过服务端认证、设备证明、反篡改或其他安全控制。

如果研究需要突破这些控制，应停止该路线，转向官方接口或其他受支持方案。

## 4.3 决策门槛

完成评估后，Agent 必须给出以下三种结论之一：

**结论 A：存在可行的受支持方案**

可以进入独立签名实现阶段。

**结论 B：需要额外授权或资料**

暂停编码，先获取必要授权或资料。

**结论 C：当前条件下不可行或投入不合理**

保留现有登录方案，不继续消耗资源。

不能因为研究已经投入时间就强行继续。

## 4.4 本阶段交付

新增：

```
docs/14-signDigital独立生成可行性评估.md
```

必须包含：

- 研究目标。
- 证据来源。
- 当前技术障碍。
- 可行方案。

# 五、第三阶段：设计独立签名模块

优先级：P1

只有第二阶段确认存在合法、可实施的方案后，才进入本阶段。

目标：

让签名生成能力与其他登录业务彻底解耦。

## 5.1 设计接口

建议建立统一的签名提供接口：

```
class SignProvider:

    def generate(
        self,
        account,
        password,
        context
    ):
        raise NotImplementedError
```

这里只定义模块边界。

具体实现必须依据已经验证、且获得授权的协议资料。

## 5.2 兼容现有方案

当前的静态签名凭据方案不能直接删除。

建议保留：

```
auth/
├── sign_provider.py
├── legacy_sign_provider.py
├── native_sign_provider.py
├── login_envelope.py
├── session_manager.py
├── credential_store.py
└── exceptions.py
```

职责：

| 模块                    | 职责                                 |
| ----------------------- | ------------------------------------ |
| sign_provider.py        | 统一签名接口                         |
| legacy_sign_provider.py | 当前已有签名凭据兼容                 |
| native_sign_provider.py | 新的独立签名实现，仅在验证通过后启用 |
| login_envelope.py       | 复用现有 AES 信封                    |
| session_manager.py      | 登录、Token、学校及学期初始化        |
| credential_store.py     | 安全保存必要凭据                     |

注意：

不要为了引入新模块而重写已经稳定的 AES 信封和 Token 管理代码。

## 5.3 安全要求

- 不持久化明文密码。
- 不在日志中记录密码。
- 不在日志中记录完整签名。
- 不上传个人认证凭据。
- 不向其他用户分发个人 credential.json。
- 不允许错误账户复用旧账户签名。
- 不允许新签名生成失败时静默使用其他账户凭据。
- 保留现有 DPAPI 等凭据保护能力。

如果签名本身能够用于认证，必须按高敏感认证凭据处理。

# 七、第五阶段：独立登录测试与验收

优先级：P0

必须区分本地验证和真实服务端验证。

## 7.1 离线测试

至少覆盖：

| 测试             | 预期结果       |
| ---------------- | -------------- |
| 正常签名输入     | 输出格式正确   |

## 7.2 协议一致性验证

只有具备授权的参考实现或测试数据时，才执行协议一致性验证。

重点：

- 同一输入是否得到一致的合法输出。
- 不同输入是否按照协议发生变化。
- 不同上下文是否正确处理。
- 输出编码是否正确。
- 版本差异是否有明确处理方式。

不能通过对真实账号进行高频登录来进行穷举验证。

## 7.3 受控真实环境验证

使用自己的测试账号，并在安全、低频条件下验证：

1. 首次命令行登录。
2. 获取 AccessToken。
3. 获取 RefreshToken。
4. 查询学校信息。
5. 查询当前学期。
6. 查询一个只读业务接口。
7. 保存会话。
8. 退出程序。
9. 重新启动。
10. 使用已保存会话执行只读查询。

对于真实账号密码修改后的验证，必须保证有安全回退方式，不得主动破坏正在使用的有效会话。

## 7.4 核心验收条件

必须全部满足：

- 

  首次配置不依赖模拟器。

- 

  不需要 ADB。

- 

  不需要 mitmproxy。

- 

  不需要预先准备个人 signDigital。

- 

  用户只需要输入账号和密码。

- 

  能够完成完整认证。

- 

  能够获取 AccessToken。

- 

  能够获取 RefreshToken。

- 

  能够初始化学校和学期信息。

- 

  能够生成原有 state.json。

- 

  原抢课系统正常运行。

- 

  原 Token 自动刷新功能正常。

- 

  不影响原有登录方式。

- 

  敏感信息保护测试通过。

如果只能在某些账号、某些版本或某些环境下工作，必须明确标记适用范围，不能宣称已经全面实现。

# 十、风险控制和停止条件

## 10.1 必须保留的现有能力

在整个研究期间，以下功能不得破坏：

- 当前命令行登录。
- credential.json 兼容。
- AES 信封构造。
- Token 自动刷新。
- state.json 原子保存。
- 原有 Client。
- 抢课状态机。
- UNKNOWN 安全屏障。

新功能必须独立开发。

## 10.2 回退机制

如果新方案失败：

```
新独立签名方案失败
        |
        v
明确记录失败原因
        |
        v
保留原有 credential.json
        |
        v
继续使用当前命令行登录
        |
        v
不影响原有抢课系统
```

不能因为研究新签名算法而破坏现有可用登录。

## 10.3 停止条件

出现以下情况之一时，暂停研究并提交评估：

1. 发现必须绕过服务端认证控制才能继续。
2. 发现依赖不可获得的设备证明或授权材料。
3. 需要进行未经授权的客户端安全机制绕过。
4. 现有证据无法支持新的算法假设。
5. 研究工作再次陷入无目标穷举。
6. 研究成本明显超过实际业务收益。

暂停不代表项目失败。

当前登录方案已经具备实际使用价值，不能为了追求理论上的零模拟器而牺牲现有稳定性。

# 十二、最终执行原则

本项目最终目标是实现真正独立的命令行认证，但不能把目标当成已经存在的技术事实。

始终坚持：

1. 已验证的内容不重复研究。
2. 未验证的假设不能直接编码。
3. 不再进行无目标的哈希穷举。
4. 不再反复研究已经证明无效的信封重放。
5. 不因为想实现零模拟器而分发个人认证凭据。
6. 不破坏当前已经可用的命令行登录。
7. 先完成可行性评估，再决定是否进入具体实现。
8. 每个阶段必须有独立交付物。
9. 真实服务端验证与 Mock 测试必须分开记录。
10. 如果官方协议不支持纯账号密码独立认证，应明确报告限制，不通过绕过安全控制强行实现。

**最终目标：让 lejianPE 用户在首次使用、日常使用以及修改密码后，都能够通过命令行完成受支持的独立认证，不再依赖 Android 模拟器和个人抓包初始化。**
