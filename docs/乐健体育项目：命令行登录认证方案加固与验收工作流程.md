# 乐健体育项目：命令行登录认证方案加固与验收工作流程

**项目地址：** https://github.com/vindcation0/lejianPE

**任务名称：** 命令行登录认证安全加固与稳定性验收

**任务优先级：** P0

**任务性质：** 现有认证方案完善，不进行登录协议重新开发。

**核心目标：** 保留当前通过 `signDigital` + 动态时间戳 + AES 登录信封实现的命令行登录方式，完善凭据安全、手动密码输入、异常处理和会话兼容性。

# 一、项目背景与当前技术方案

## 1.1 当前已经实现的方案

项目已经找到了一条不需要每次启动 Android 模拟器即可完成登录的路径。

当前方案的核心是：

```
用户通过合法客户端登录
        ↓
获取 signDigital
        ↓
保存认证材料
        ↓
用户启动命令行登录
        ↓
输入账号密码
        ↓
读取本地 signDigital
        ↓
生成新的时间戳
        ↓
生成 AES 登录信封
        ↓
调用登录接口
        ↓
获取 accessToken
        ↓
获取 refreshToken
        ↓
获取 schoolId、semesterId
        ↓
生成现有 state.json
```

当前已经验证的技术结论：

1. 原始登录信封可以重放，但存在时间限制。
2. 旧信封失效后，重新生成时间戳和 AES 信封可以完成登录。
3. 使用保存的 `signDigital` 和新信封，已经完成过端到端登录。
4. 登录成功后能够调用现有业务接口。
5. 本地 AES 信封实现已经完成 200 次往返自测。

参考：

```
结论：绕开了 signDigital，而不是破解它.md
```

## 1.2 对当前方案的准确定位

必须明确：

当前方案属于：

**基于合法客户端获取的认证材料实现的命令行登录。**

它不是完全独立的纯账号密码协议登录。

本轮不再研究如何破解 DexVMP 加固后的 `hs()`，也不重新设计整个认证协议。

当前工作重点是把已经验证可行的方案变成安全、稳定、易维护的正式功能。

## 1.3 本轮最终目标

完成后希望达到：

```
首次初始化认证材料
        ↓
保存本地敏感认证材料
        ↓
启动命令行程序
        ↓
输入账号密码
        ↓
完成命令行登录
        ↓
生成 state.json
        ↓
正常使用抢课功能
        ↓
Token 过期时自动刷新
        ↓
RefreshToken 失效时重新登录
```

不再需要每次 Token 失效都启动模拟器。

但在新方案经过多个实际使用周期验证之前，必须保留原来的模拟器同步方式作为备用入口。

# 五、第三阶段：手动密码输入端到端验证

**本阶段是当前方案正式验收的关键。**

之前的验证报告已经说明：

使用抓包中的密码完成过端到端验证，但手动输入密码的路径仍需要单独确认。

因此不能直接将现有实现认定为全部验收通过。

## 5.1 密码输入要求

使用：

```
import getpass

username = input("请输入账号：").strip()
password = getpass.getpass("请输入密码：")
```

要求：

- 密码输入不回显。
- 密码不进入日志。
- 密码不写入 credential.json。
- 密码不写入 state.json。
- 用户取消输入时能够正常退出。
- 密码变量在不再需要时尽可能及时释放引用。

## 5.2 必须测试的场景

| 编号 | 测试场景                         | 预期结果                 |
| ---- | -------------------------------- | ------------------------ |
| L01  | 正确账号密码                     | 正常完成登录             |
| L02  | 密码包含特殊字符                 | 正常处理                 |
| L03  | 错误密码                         | 明确提示认证失败         |
| L04  | credential.json 不存在           | 提示初始化认证材料       |
| L05  | credential.json 格式错误         | 明确提示文件损坏         |
| L06  | credential.json 缺少 signDigital | 拒绝登录                 |
| L07  | 用户修改密码                     | 能识别旧认证材料可能失效 |
| L08  | 用户取消输入                     | 安全退出                 |
| L09  | HTTP 200 但业务认证失败          | 正确识别失败             |
| L10  | 网络超时                         | 提示网络异常             |
| L11  | Token 获取失败                   | 不生成不完整会话         |
| L12  | schoolId 获取失败                | 保留旧状态               |
| L13  | semesterId 获取失败              | 保留旧状态               |
| L14  | 服务端返回异常结构               | 明确报错                 |

## 5.3 特别注意 HTTP 200

不能简单使用：

```
if response.status_code == 200:
    print("登录成功")
```

必须同时检查：

- HTTP 状态码。
- 响应 JSON 是否有效。
- 服务端业务状态码。
- 必要 Token 字段是否存在。
- 用户信息是否获取成功。

只有完整认证流程成功，才允许进入下一阶段。

## 5.4 真实登录测试约束

自动化测试默认使用 Mock 响应。

真实登录测试：

- 仅使用用户本人或明确授权的账号。
- 由用户主动发起。
- 控制请求次数。
- 遵守服务端限流。
- 不进行批量尝试。
- 不进行高频密码重试。
- 不绕过验证码或设备验证。

# 六、第四阶段：AES 信封与协议兼容性验证

## 6.1 当前已知情况

当前项目已经完成：

```
login_envelope.py
```

本地 200 次往返自测。

需要明确：

**本地 AES 往返测试不等于服务端集成测试。**

本地测试主要证明算法实现能够完成预期的加解密往返。

它不能单独证明服务端会长期接受这些请求。

## 6.2 检查内容

### AES 信封

- 

  输入输出格式正确。

- 

  加密与解密流程一致。

- 

  时间戳字段格式正确。

- 

  pyd 字段结构正确。

- 

  错误输入不会产生异常泄漏。

- 

  加密失败时不会继续发送无效请求。

### 时间戳

- 

  时间戳使用正确单位。

- 

  使用当前时间生成新信封。

- 

  不复用已经过期的旧信封。

- 

  系统时钟异常时能够提示。

- 

  不依靠随意调整时间来规避服务端校验。

### 请求和响应

- 

  请求 Content-Type 正确。

- 

  登录响应能够正确解析。

- 

  业务错误能够正确识别。

- 

  不会将 HTTP 200 直接当成登录成功。

- 

  不会输出完整敏感请求体。

## 6.3 测试证据分级

最终报告必须区分：

| 证据                 | 能证明什么           |
| -------------------- | -------------------- |
| 本地 AES 往返测试    | 本地算法实现正确性   |
| Mock 登录测试        | 程序异常处理能力     |
| 一次真实登录         | 一次服务端集成成功   |
| 多个时间周期真实登录 | 一定程度的持续兼容性 |

不能把一次成功登录描述为长期稳定。

## 6.4 协议变化处理

如果服务端改变：

- signDigital 认证规则。
- AES 信封结构。
- 时间戳要求。
- 登录响应结构。
- 其他认证要求。

应该明确提示：

```
登录失败：认证材料或认证协议可能已经失效。

建议：
1. 检查账号密码。
2. 检查本地认证材料。
3. 确认官方客户端是否发生更新。
4. 按正常认证流程重新初始化。
```

不得无限重试，也不得尝试绕过验证码、设备检查或服务端安全控制。

建议建立独立认证异常分类。

可以使用：

## 7.1 错误分类

| 错误                   | 处理方式           |
| ---------------------- | ------------------ |
| credential.json 不存在 | 提示初始化         |
| credential.json 损坏   | 提示重新初始化     |
| signDigital 无效       | 提示认证材料失效   |
| 密码错误               | 提示检查密码       |
| 业务认证失败           | 展示安全的错误信息 |

| 用户信息获取失败       | 保留旧会话         |
| schoolId 获取失败      | 保留旧会话         |
| semesterId 获取失败    | 保留旧会话         |
| 网络超时               | 有限重试           |
| 服务端 500/503         | 有限等待并提示     |

## 7.2 不允许的处理方式

禁止：

- 无限重试。
- 错误后自动连续尝试密码。
- 将所有异常统一处理为登录失败。
- 登录失败后清空旧 state.json。
- 将不完整 Token 当成成功会话。

# 九、第七阶段：与现有抢课系统集成

这是必须严格保证的部分。

## 9.1 state.json 兼容

新登录最终仍然必须生成现有项目能够使用的 state.json。

重点字段：

```
{
  "accessToken": "<access_token>",
  "refreshToken": "<refresh_token>",
  "accessTokenExpires": 0,
  "schoolId": "<school_id>",
  "semesterId": "<semester_id>"
}
```

以上只是示意，必须以当前项目真实数据结构为准。

不能擅自删除或重命名现有字段。

## 9.2 安全保存

新登录成功后：

1. 获取完整会话。
2. 验证所有必要字段。
3. 检查 Token 有效性。
4. 获取学校和学期信息。
5. 构建完整 state。
6. 写入临时文件。
7. 验证临时文件。
8. 备份旧 state。
9. 原子替换。

如果任意步骤失败：

**原来的 state.json 必须保持不变。**

## 9.3 Token 刷新兼容

必须验证：

```
Client.ensure_token()
Client.refresh()
```

新登录生成的会话必须可以被现有 Token 管理模块正常使用。

重点测试：

- AccessToken 过期。
- RefreshToken 正常轮换。
- RefreshToken 失效。
- 刷新请求超时。
- 新 Token 持久化失败。

不得另行开发一套与现有刷新机制冲突的 Token 管理系统。

## 9.4 不影响抢课业务

本轮只改造认证模块。

禁止修改：

- 报名接口。
- 每日报名上限。
- 每周报名上限。
- UNKNOWN 安全屏障。
- 服务端熔断机制。
- 特殊活动规则。
- SQLite 报名状态机。
- 课表冲突判断。

认证系统只负责可靠地生成会话。

抢课系统负责安全地使用会话。

# 十、第八阶段：保留模拟器备用方案

本轮不允许直接删除：

```
tools/resync_from_app.py
```

原有模拟器同步方式暂时保留。

建议最终形成：

```
登录方式

[1] 命令行账号登录
[2] 模拟器同步 Token
[3] 查看当前登录状态
[4] 刷新 Token
```

其中：

- 命令行登录作为主要方式。
- 模拟器同步作为备用方式。
- 两种方式最终生成同一套 state.json。

只有满足以下条件，才可以考虑删除模拟器依赖：

1. 手动密码登录通过完整验证。
2. 多次真实登录成功。

让 lejianPE 在不依赖日常模拟器启动的情况下，通过命令行完成认证，并且具备安全的凭据保护、稳定的 Token 管理和可靠的异常恢复能力。
