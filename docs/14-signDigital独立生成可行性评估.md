> 对应《真正零模拟器登录协议研究与实现工作流程》第四阶段。
> 本阶段只做评估，**不写实现代码**。
> 结论必须落在 A / B / C 三者之一，不允许含糊。

## 一、研究目标

要回答的唯一问题：

> **在不破解 DexVMP 加固、不绕过客户端保护性校验的前提下，
> 能否仅凭用户输入的账号密码，在本地生成服务端认可的 `signDigital`？**

注意这个问题的三个限定：

1. **不破解加固** —— 排除"先脱壳再逆向"这条路
2. **不绕过保护** —— 不能靠 hook、内存 dump、改包等手段取巧
3. **仅凭账号密码** —— 不接受预先分发的第三方签名材料

三个限定任缺其一，问题就变成了另一个（且通常违反项目规范）的问题。

## 三、当前技术障碍

### 障碍 1：签名逻辑位于加固区，静态不可达

| 证据 | 数据 |
|---|---|
| `libsportaction.so` R-X 段熵 | 7.19（整体） |
| 高熵窗口 | 33 / 67，峰值 **7.94**（随机上限 8.0） |
| 对照组 `libsecurity.so` | 6.76，0 个高熵窗口 |
| 节区表 | 被破坏为 4 个假节区，整文件标 `SHT_NOBITS` |

`signDigital` 的实现在 `libsportaction.so`，该库由 DexVMP 加固。
**在不脱壳的前提下拿不到可读的指令流。**

### 障碍 2：输入构成未知

24,840 种组合穷举全部失败，说明输入里至少还有一个未知成分。

候选可能包括：

- 包签名摘要（JNI 字符串里出现过 `getSignature` / `getPackname`）
- 设备指纹（android_id、机型）
- 某个预置常量

**但这些都是猜测，没有任何一条被证实。**

### 障碍 3：签名被服务端强校验

`50004 签名不正确` 证明服务端会验证。

这意味着：**随便造一个签名不行，必须真正算对。**

### 障碍 4：签名与密码强绑定

改密码后签名立即失效（实测：`860cce4e4e…` → `0a9d0a78a8…`）。

所以签名不能脱离具体密码被"通用化"。

## 四、可行方案对比

### 方案 A：完整还原 `hs()` 并纯 Python 实现

| 项 | 评估 |
|---|---|
| 前置条件 | 必须脱壳 DexVMP，拿到 `libsportaction.so` 解密后的代码 |
| 工作量 | 高。需要脱壳 + ARM 反汇编 + 还原自定义 SHA1 封装 |
| 成功概率 | 中。脱壳本身不是确定能做成的事 |
| 维护成本 | **极高**。App 一升级加固方案可能变，全部重来 |
| 合规性 | ❌ **触碰规范 10.3 第 3 条**：「未经授权的客户端安全机制绕过」 |
| 结论 | 不采用 |

### 方案 B：运行时取一次签名（Frida / hook）

| 项 | 评估 |
|---|---|
| 前置条件 | root 设备 + frida-server + 一次登录 |
| 工作量 | 中 |
| 收益 | 与现有方案**基本相同**——依然要"跑一次客户端"，只是从抓包换成 hook |
| 是否解决首次依赖 | ❌ 没有。仍然需要一次客户端登录 |
| 结论 | 不采用（收益为零） |

### 方案 C：维持现有方案 + 补强易用性

| 项 | 评估 |
|---|---|
| 前置条件 | 无 |
| 工作量 | 低（已有 `capture_login.py` 一键化） |
| 覆盖场景 | 首次配置 ✅ / 改密码 ✅ / 日常 ✅ / Token 刷新 ✅ |
| 剩余成本 | 改密码时开一次模拟器，一学期 1–2 次 |
| 结论 | **采用** |

### 方案 D（补充）：走官方渠道

向学校体育部 / 乐健客服申请**接口授权或独立客户端接入**。

| 项 | 评估 |
|---|---|
| 成本 | 沟通成本为主，技术成本接近零 |
| 成功概率 | 低（面向个人的开放接口通常不提供） |
| 但 | 这是**唯一完全合规**的"真零模拟器"路径 |
| 结论 | 值得一试，不作为工程承诺 |

## 六、成本估算

以方案 A 为例（最激进的一条）：

| 阶段 | 预估投入 |
|---|---|
| 脱壳 DexVMP | 数天到数周，且结果不确定 |
| 定位 `hs()` 与输入构造 | 1–3 天（脱壳成功后） |
| 还原自定义 SHA1 封装 | 1–2 天 |
| 用真实样本验证 | 半天 |
| **合计** | **约 1–4 周，成功概率中等** |
| 之后每年维护 | 每次 App 大版本更新后重来一遍 |

对比收益：**每学期节省 1–2 次、每次约 3 分钟的模拟器操作。**

成本收益比极差。

## 七、决策结论

### 结论 C：当前条件下不可行或投入不合理

**理由（按权重排序）：**

1. **合规红线**：独立生成的唯一技术路径是破解 DexVMP 加固层。
   这与规范 10.3 第 3 条「需要进行未经授权的客户端安全机制绕过」
   以及第二节「不得以绕过客户端安全机制为目标」直接冲突。
   **这一条单独就足以终止方案 A。**

2. **成本收益失衡**：1–4 周投入 + 每年维护，换取每学期少开两次模拟器。

3. **不存在更轻的合法路径**：无官方 SDK、无开放平台文档；
   第三方逆向项目「已失效」的标注也印证了这类实现的脆弱性。

4. **现有方案已覆盖核心诉求**：日常登录、抢课、刷新全部不需要模拟器，
   残留依赖仅限"密码变更"这一低频事件。

> 需要说明的是：结论 C 里的「不可行」是指
> **「在项目自定的安全与合规约束下不可行」**，
> 而非「技术上绝对做不到」。如果放弃这些约束，方案 A 在技术上有中等成功概率。
> 但那样做就违背了本项目的执行原则。
